# Step1 G3：GPU 后端接入现有 Step1 Viewer 产品路径

**日期：** 2026-09-20 · **分支：** `v15-interactive-channel-workspace` · **起止 HEAD：** `9d78d1c`（未提交）

**范围：** 只做接线与生产接管。G1 显示层与 G2/G2.1 供给适配器被挂进既有 `Step1WholeSlideMount`，使用既有 `Step1ViewerHost`/`ExploreController`/ViewBox、既有 `Step1TileProvider`/`TileScheduler`/raw cache 和既有产品 UI 入口。没有新 UI、没有新 scheduler/cache/事件总线，没有修改 `ui/main_window.py`、科学算子、来源规则或 Save/handoff。**自动化退出门已完成，等待用户真机验收；G4 未开始。**

## 1. 接线结构

```
现有 Step1ViewerHost / ExploreController / ViewBox      ← 相机、输入、平移缩放的唯一所有者
  → 现有 Step1TileProvider / TileScheduler / raw cache  ← 唯一的供给与调度
    → Step1GpuBinding（G2/G2.1）                        ← 只消费公开端口，产出 immutable SourceDescriptor
      → Step1GpuLayer（G1）                             ← ViewBox viewport 的 sibling overlay
        → 现有 Step1 Viewer tab
```

用户入口完全不变：原 Viewer tab、原 Overlay/Fusion 按钮（`mount.set_mode()`）、原 Channels 行、原 Intensity 窗口、原 patch 按钮、原 Tissue Preview、原 Step0↔Step1 相机同步。没有新增任何按钮、窗口、tab、状态栏入口或设置面板。

### 相机与输入

- GPU widget 的父对象就是既有 ViewBox 的 `graphics.viewport()`；`WA_TransparentForMouseEvents` 为真，Qt 的命中测试不会把它选为接收者。
- 没有第二个 ViewBox、第二个 controller、第二个窗口。`binding.provider/scheduler/controller` 与 `stack.provider/scheduler/controller` 是同一批对象。
- 视口只有一条链：G2 binding 订阅 controller 既有的 `interaction_event`/`gesture_quiet`/`snapshot()`。mount 在 GPU 后端下**不再**连接 `gesture_quiet`（那条连接只为驱动 CPU 合成），因此不存在重复提交同一 viewport。
- Step0↔Step1 shared camera 与 Tissue Preview 视框仍由 mount 原有的 `publish_camera()`/`publish_view_rect()` 经既有 `sigRangeChanged` 发布。

### 科学/显示 spec

唯一来源仍是 `ui/step1_draft_spec.py::build_spec(...)`。mount 的 `_gpu_display_snapshot()` 只做一层薄转换：把 `build_spec` 返回的 dict 字段逐个复制进不可变的 G1 `DisplaySnapshot`（mode / mappings / weights / colors / groups / group_weights / nucleus），不改任何数值、不重新实现任何规则。draft 驱动 Viewer，`committed_snapshot()` 不被写入；Search/Generate 仍读 committed。

### 哪些通道算"科学活动"——由既有合成规则决定

`_gpu_spec_channels()` **直接调用** `viewer/step1_compose.py` 的
`overlay_channels(weights)` 与 `fusion_channels(groups, group_weights, nucleus)`——
与 CPU coordinator（`ui/step1_compose_coordinator.py`）规划时用的是同两个函数。
drop 规则只有一处定义：通道权重 `0.0`、组权重 `0.0`、nucleus 权重 `0.0` 都不读取、
不映射、不合成；显式 `0.0` 仍保留参与状态，只是当前不贡献像素。

**G3.1 收口（复核 blocker）：** 初版 G3 在 mount 里另写了一份 Fusion 通道判断，
把所有组成员和任意非空 nucleus 都算进来，没有过滤三种零权重。后果是：某个零权重
通道若缺 Intensity 映射，GPU 路径仍会向共享服务请求自动求窗、在 badge 上显示
"正在计算该通道窗口"、并做本不需要的 overview 工作。它不会读取瓦片也不会显示像素
（G2 binding 后面还有正确过滤），但违反 C1.1 的"不映射"契约，也与"不得重复造科学
判断"冲突。修复只做一件事：删掉那份重复实现，改为调用上述两个既有函数。

### 缺失 mapping

`_note_gpu_missing_windows()` 找出 spec 中科学活动但没有 window 的通道，经既有 `Block01DisplayServices.request_mapping_seed()` / `mapping_seed_pending()` 请求 seed，以 `(source, channel)` 去重（与 CPU coordinator 同一规则）。mount 不计算 percentile、不建第二套 seed cache；window 到达后经共享 `mapping_changed` 触发一次 GPU refresh；既有 badge 继续说明"正在计算 window"的通道。

## 2. CPU 合成如何停止，rollback 如何保留

GPU 后端启动成功时，`Step1ComposeCoordinator`、`Step1ComposeBinding`、`Step1ComposedLayer` **根本不会被创建**——不是创建后停用。证据：`mount.coordinator is None`、`mount.compose is None`、`mount.layer is None`，因此没有 CPU compose worker、没有 `tile_composed → Step1ComposedLayer` 连接、没有 CPU RGBA composed tile 发布，mapping/weight/colour 变化也不可能同时触发两套合成。

旧 CPU 路径一行未删、一行未重写，仍是完整的 rollback/fallback：

- `_start_cpu_backend(stack)` 就是原来的 `open()` 主体，GPU 起不来时原样执行，backend 记为 `cpu-fallback`；
- 旧 patch widget 仍被 `install()` 保留并隐藏，`restore_legacy()` 不变；
- `tests/test_step1_viewer_mount.py` 的 16 项 C4 退出门改为显式 `gpu=False` 构造，继续逐像素验证这条 CPU 路径——它现在是 rollback 路径的门。

后端状态只读诊断：`mount.backend` ∈ {`gpu`, `cpu-fallback`, `legacy`}，`mount.gpu_status()` 另带真实失败原因、环境报告、纹理预算与 binding 统计。GPU 初始化失败会写 `logging.warning` 并明确记为 `cpu-fallback`；不存在"静默降级仍报告 GPU 成功"。

## 3. 512 MiB 固定演示预算与实测峰值

`ui/step1_viewer_mount.py` 中的明确命名常量：

| 常量 | 值 | 作用 |
| --- | ---: | --- |
| `DEMO_GPU_RAW_TEXTURE_BYTES` | `536,870,912`（512 MiB） | G1 raw texture LRU 硬上限 |
| `DEMO_GPU_COARSE_TILES_PER_CHANNEL` | `1024` | 每通道完整 coarse 瓦片数上限 |
| `DEMO_GPU_COARSE_BYTES_PER_CHANNEL` | `33,554,432`（32 MiB） | 每通道完整 coarse 字节上限 |
| `DEMO_GPU_FINE_TILES_PER_VIEWPORT` | `256` | 当前视口精层瓦片数上限 |
| `DEMO_GPU_FINE_BYTES_PER_CHANNEL` | `16,777,216`（16 MiB） | 每通道当前视口精层字节上限 |

八个通道同时吃满两个 per-channel 上限是 384 MiB，仍在 512 MiB 之内。**fail closed 而不是降级**：单次提交的 active working set 装不下时，`_TextureLru.prepare` 抛 `Step1GpuLayerError`，binding 不发布该帧并记录 `last_error`；某通道的完整 coarse 超预算时该通道被标记 unavailable。两种情况都由既有 badge 说明（`notice()` 新增的一句），既不丢通道、不降精度、不回落 raw，也不自动上调显存预算。G3/G4 前不得自动提高，G4 才能依据真机测量调整。

实测（3 通道演示 rig，24 张 level-1/level-0 纹理）：

| 项 | 观测 |
| --- | ---: |
| 预算 | `536,870,912` bytes |
| 峰值字节 | `7,077,888` bytes（占预算 `1.3 %`） |
| 峰值纹理数 | `27` |
| 淘汰次数 | `0` |
| 关闭后 textures / bytes | `0` / `0` |

这是合成金字塔上的数字，**不是**真实 57 通道全 slide 的显存需求；生产 VRAM 预算仍是 G4 的事。

## 4. 生产挂载 widget 的真实 GPU 像素

证据取自生产挂载 widget 自己的 `QOpenGLWidget.grabFramebuffer()`，不是 FBO 内部测试接口、不是 submit 次数、不是假 controller。

| 项 | 观测 |
| --- | --- |
| backend | `gpu`（reason 空） |
| `gl_vendor` / `gl_renderer` | `NVIDIA Corporation` / `NVIDIA GeForce RTX 4090/PCIe/SSE2` |
| `gl_version` / `glsl_version` | `4.6.0 NVIDIA 535.309.01` / `4.60 NVIDIA` |
| Qt actual context | OpenGL `3.3` Core；PyOpenGL `3.1.10` |
| `software_renderer` | `false` |
| 抓取帧 | `478 × 638 × 4`，sha256[:16] `e4d0fdeb962e3cd7`，最大 RGB `42` |

**关于 alpha 的诚实说明：** `grabFramebuffer()` 返回的是 widget 合成后的图像，Qt 把 alpha 填成不透明，因此它能证明"GPU 像素进了生产 widget"，但不能回答"这个像素是不是透明"。ROI 外透明只由 G1 层自己的 FBO readback 回答（同一帧 `alpha ∈ [0, 255]`），并且只用于这一个问题，从不单独充当"画面已上屏"的证据。

## 5. 无中央扩散（生产 mount 路径）

CD3 先完整准备并显示；启用 CD8 后，其 9 块完整 coarse **按中央先到、外围后到**交付：`(1,1) → (0,0) (1,0) (2,0) (0,1) (2,1) (0,2) (1,2) → (2,2)`。每块交付后读取生产 widget framebuffer。

| 步骤 | 交付 | framebuffer sha256[:16] | 与 CD3-only 基线逐像素一致 | CD8 红色最大值 |
| --- | --- | --- | --- | ---: |
| 0 | CD3-only 基线 | `e4d0fdeb962e3cd7` | —(基线) | `0` |
| 1 | **中央** `(1,1)` | `e4d0fdeb962e3cd7` | `true` | `0` |
| 2–8 | `(0,0) (1,0) (2,0) (0,1) (2,1) (0,2) (1,2)` | 全部 `e4d0fdeb962e3cd7` | 全部 `true` | 全部 `0` |
| 9 | **最后一块** `(2,2)` | `afdd52d0b84c2f04` | `false` | 有效区最小值 `28` |

第 9 步之后：有效区 `100,488` 像素，其中**每一个**像素的 CD8 贡献都 `> 0`——一次覆盖完整有效区域；有效区之外 CD8 最大值 `0`；CD3 的绿色平面与基线**逐像素相同**；同帧 FBO alpha 仍为 `[0, 255]`，ROI 外保持透明。

局部 fine：放大到 level-0 后精层到达，`fine_channels` 非空而两个通道的 `coarse_channels` 仍在、descriptor 中每个通道仍带 coarse——fine 只提高局部清晰度，不替换完整粗层，也不让任何通道消失。

## 6. Overlay / Fusion / Intensity 的读取与上传 delta

### Overlay / Fusion 对照 C1

参照值用**同一次提交的 descriptor**：按 G1 shader 的世界坐标最近邻采样规则在 numpy 中重建每个通道的屏幕空间数组，再交给 CPU 侧同一个 `viewer.step1_compose.compose()`。比较的是公式，不是两个重采样器。

| 模式 | 生产 widget RGB 与 C1 最大绝对差 | alpha 与 C1 |
| --- | ---: | --- |
| Overlay | `1` LSB | 逐像素相等 |
| Fusion | `1` LSB | 逐像素相等 |

### 模式切换

| 项 | 观测 |
| --- | ---: |
| provider read delta | `0` |
| scheduler request delta | `0` |
| raw upload delta | `0` |
| CPU compose delta | `0` |
| Overlay 绿色最大值 → Fusion 绿色最大值 | `42 → 0` |

Fusion 只写红蓝；切换后一个绿色像素都不剩，说明没有上一模式的残留（GPU 每次提交都从清空的目标重画）。

### Intensity 实时路径

真实路径 `ChannelDisplayState.set_mapping()` → `mapping_changed` → mount → G2 binding → `Step1GpuLayer` → 生产挂载 widget framebuffer。Overlay 与 Fusion 各连续 5 次改变（Min、Max、Gamma 组合）：

| 模式 | 每次改变的 (read, request, upload, cpu-compose, gpu-submit) delta | framebuffer 改变 |
| --- | --- | --- |
| Overlay | `(0, 0, 0, 0, +1)` × 5 | 5/5 |
| Fusion | `(0, 0, 0, 0, +1)` × 5 | 5/5 |

没有重新引入 C4.5c 的 raw callback、waiting epoch 或 coalescing 架构：每个 `mapping_changed` 直接用已驻留的 raw texture 重新提交一次。

## 7. 导航、相机与 Tissue

- GPU viewport 的 world rect 与 ViewBox 自己的 `viewRange()` 逐值相等，patch 与空降之后仍然相等。
- patch 按钮与 Tissue Preview 点击都经同一个 `host.jump_to` → 一个 controller，**立即**产生目标位置的 scheduler 请求（断言跳转后立刻有新请求）。
- 中键平移/缩放走 controller 既有路径；`view_rect_l0()` 与 `camera_sink` 继续发布，Tissue Preview 当前视框继续移动。
- 全程 `mount.host.stack.controller` 与 `view_box` 对象身份不变，`mount.coordinator is None`（没有第二条 viewport 调度链）。

## 8. activate / deactivate / source / close

| 门 | 观测 |
| --- | --- |
| 离开 Step1 后改 mapping、颜色、权重 | GPU submit delta `0`，read delta `0` |
| 返回 Step1 | submit delta 恰好 `+1`（一次完整 snapshot 刷新） |
| 来源未变 `sync_source()` | 返回 `False`；layer/binding/stack 对象不变；read delta `0`；coarse 未丢 |
| 来源变化 `sync_source()` | 先 dispose 旧 binding、旧 layer 从旧 ViewBox 断开并释放 GL names，再由既有 viewer binding 重建 stack（携带相机），新 layer/binding 起在新来源上；全部 descriptor 的 plane identity 都是新 source；相机在 5 % / 2 px 容差内保留 |
| 正常 close | `gpu_layer`/`gpu_binding` 置空，layer textures `0`、bytes `0`，binding 二次 dispose 报 `already_disposed`，之后 `refresh_display()` 不再产生提交；`controller._marker_visible` 回到 `True` |
| GPU 初始化失败 | backend `cpu-fallback`，`reason` 带真实异常原文，已建资源被释放，既有 CPU whole-slide 合成打开并真的画出瓦片 |

`close()` 被 MainWindow 拒绝的路径未改动：`Step1WholeSlideMount.close()` 仍只在被调用时执行，C4.4 已验收行为由 `tests/test_step1_viewer_takeover.py`（19 passed）保护。

每个变异临时施加于白名单文件，跑强制 GPU 的 `tests/test_step1_gpu_takeover.py` 后精确还原（还原后 md5 与改动前一致）。

| # | 变异 | 结果 |
| --- | --- | --- |

| 5 | display 改变触发 raw upload | 红：模式门 + Intensity 门 + 无双重工作门失败 |
| 6 | 模式切换残留上一模式像素 | 红：C1 对照门 + 中央扩散门 + Channels 门失败 |
| 7 | deactivate 后仍 submit | 红（见下） |

## 12. blocker 与 advisory

**G3.1 已修复复核提出的唯一 blocker**（mount 重写 Fusion 通道判断，导致零权重通道仍触发 Intensity 求窗）；修复只改 `_gpu_spec_channels()` 一个函数，改为调用既有科学函数，未动 GPU layer、G2 binding、provider、scheduler、cache、Step0、科学公式与共享 Intensity 服务。新增的四个门是：

- 通道权重 `0.0` 不请求 seed，且不出现在 badge；
- 组权重 `0.0` 不请求 seed；
- nucleus 权重 `0.0` 不请求 seed；
- 改为正权重后只请求一次 seed（再刷一次也不会重复请求），window 到达后该通道正常加入画面。

这四个门对修复前的实现全部转红（见 §11 第 11 项）。

**当前无其他 blocker。** advisory（只记录，未扩写任务）：

1. **既有 `ExploreController` 仍为相机/基础单通道层发出自有请求**（本轮 rig 中 `9` 个）。G3 不修改共享 controller/scheduler，如实记录给 G4。
2. **窗口尺寸变化到下一次交互之间，FBO 沿用旧尺寸**：`paintGL` 以 `GL_NEAREST` 把旧尺寸 FBO 拉伸到新 widget 尺寸，直到下一次 pan/zoom/jump 触发重新提交。G3 不新增第二条 viewport 链来处理它，交 G4 判断是否需要。
3. **`grabFramebuffer()` 的 alpha 由 Qt 合成为不透明**，ROI 外透明只能由 G1 FBO readback 回答（见 §4）。
4. **`tests/test_step1_viewer_mount.py` 现在测的是 rollback 路径**（显式 `gpu=False`）。产品默认路径的门在 `tests/test_step1_gpu_takeover.py`。
5. **PyOpenGL 3.1.10 仍未进入依赖清单**；它只按 G1 授权固定在 `fusion_test2` 演示环境。生产依赖声明需单独批准。
6. **PyOpenGL 依赖清单**按复核意见列为 G4 发布收口项。
7. **未测**：compositor/vsync、input-to-display 延迟、FPS、真实 57 通道全 slide 的冷准备与 VRAM 峰值。这些是 G4 的内容，不得从本报告的数字推导。
