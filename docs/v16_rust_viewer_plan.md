# Step1 查看器改用 Rust 内核：方案（v1，2026-10-11）

状态：已经 Fable（5.1 medium）审核，审核意见已合并（见 §7）。待用户确认；确认前不动产品代码。

## 0. 决定与目标

- 用户裁决（2026-10-11）：停止在 Python 上继续优化 Step1 查看器的手感，改用 Rust。§45 的 Python 第 1 步方案作废，不实施。
- 目标：Step1 查看器在至少 20 个通道下，拖动、缩放、停手清晰的手感达到 Odon 水平。验收沿用 §44：
  - 每种手势和 Odon 同场 A/B 配对，不比 Odon 差；
  - 停手 50 ms 内看不出切换作为目标线，单独报告；
  - 3 通道不能比现在差；69 通道作为压力测试。
- 先服务器，后 RTX 3060 笔记本。笔记本是 **WSL2 + Mesa D3D12 驱动 + X11**（`docs/next_window_handoff.md:76-91`），不是 Windows 原生，验收不预先放宽。

## 1. 为什么只换读图不够

| 现象（真正 20 通道，§44/§45） | 在哪一段 | 只换读图能解决吗 |
|---|---|---|
| 一块图读完要 8–20 ms，真正用 CPU 约 3.5 ms | 读图线程抢 Python 全局锁 | 能 |
| 放大停手后界面卡 104–289 ms，界面线程只干了 50–75 ms | 界面线程抢不到锁（饥饿） | 部分能 |
| 一次发布 15–26 ms；规划每片 9–22 ms | Python 记账 | 不能 |
| 向下拖动、单格缩小、甩动几乎不读图，仍要 74–124 ms 才清晰 | 发请求、交付、上屏节奏 | 不能 |
| 69 通道下界面时间几乎全在规划和发布（§38） | Python 记账 | 不能 |

Odon 的做法（读源码，只参考设计）：
- 读图用最多 6 个 Rust 线程，和界面互不打扰（`render/tiles.rs:129-134`）；
- 读完放进队列，界面每帧一次取完；作废的请求由读图线程自己跳过（`tiles_raw.rs:192-197`）；
- 每帧最多发 256 个请求，位置由近到远、同位置各通道一起（`app.rs:13187, 15103`）。16 个通道以上时，粗层和过渡层每通道每帧只发 1 块，并关闭预取（`app.rs:120-122, 13030-13036`）；
- 画到哪块就当场上传，不设上传额度（`tiles_gl.rs:215-240`）。

**路线 B 去掉的是 Python 记账和抢锁；去不掉的是 pyqtgraph 处理滚轮和拖动的那一段**（见 §5 第 4 条）。

## 2. 路线比较

| 路线 | 做法 | 结论 |
|---|---|---|
| A 只做 Rust 读图模块 | PyO3 模块替换读文件和解压 | 不够：记账和节奏仍在 Python |
| **B Rust 查看器内核，嵌在现有 Qt 画布里** | Rust 负责规划、请求、读图、缓存、上传、绘制，在现有 QOpenGLWidget 的 GL 上下文里画；Python 只传镜头和显示设置 | **采用** |
| C 独立 Rust 进程加原生窗口 | 嵌入原生窗口 | 不选：pyqtgraph 的 ROI 等叠加层画不到它上面；还要进程通信 |
| D 整个软件改 Rust | 重写 | 不选：工期和风险不成比例 |

## 3. 路线 B 的设计

### 3.1 Rust 内核负责什么

新建 crate `fusion_viewer_core`，用 PyO3 + maturin 做成 abi3 wheel，一份通吃 Python 3.10+。

1. **图源**：
   - 原始 OME-TIFF 和 qptiff：Python（tifffile）解析一次文件结构，把每级的偏移表、长度表、压缩方式、预测器、数据类型传给 Rust（沿用 `raw_tile_provider._ChunkPlan`）。Rust 只做 pread、解压（LZW 用 weezl；deflate 用 flate2 加 zlib-ng 后端；zstd；不压缩）和预测器还原。
   - 校正产物（zarr v2，默认 Blosc lz4 加 shuffle，f32，1024² 块）：第 0 级直接读块，sidecar coarse 平面直接切片；**其余各级按 `box_downsample_valid` 的语义在 Rust 里现算**（块以第 0 级原点对齐，只对有效像素求均值）。容差见 §3.3。
   - 标签（`<u4`，Blosc lz4）：在 R3 处理。
2. **准入和规划**：把现有绑定层决定"画什么"的规则搬进 Rust：
   - 层级选择和"分辨率受限"；
   - 只画粗层的情况；
   - 沿用旧块（carry）；
   - 更细的替身块只在目标块到位前画；
   - 总预算裁剪。

   排序为位置由近到远、同位置各通道一起；粗层原子显示（每通道整层一起出现）。
3. **请求和取消**：Rust 线程池，服务器 6 线程，笔记本按核数，最多 6。规划写入"当前需要"集合，读图线程开工前自己核对，过期的跳过，不回报界面。
4. **缓存**：
   - CPU 端按字节计上限，和 Python 现有缓存（原始 512 MB、校正 2 GB）合计，不超过资源档位（DEV 档 10 GB 内存、6 GB 显存）；
   - 显存用量报给 `gpu_memory`，隐藏和内存压力时释放的流程照旧。
5. **显存布局**：**移植现有的虚拟纹理设计**（数组纹理加页表，再加 meta/params 纹理，`step1_gpu_vt.py`、`step1_gpu_vt.frag`），格式分 u8、u16、f32 三族，带有效区域。不采用 Odon 的"每块一张纹理"：现有的跨块平滑和"逐像素一致"的验收都依赖虚拟纹理。
6. **上传和绘制**：
   - `paintGL` 里 Python 调一次 `core.paint(...)`，调用期间释放 Python 锁；
   - GL 函数通过 Qt 的 `QOpenGLContext.getProcAddress` 加载（Python 一次性传入），保证和 Qt 的上下文一致；进出时保存、恢复视口和裁剪状态；
   - 上传额度：有输入时约 4 ms；没有输入时不限，单帧封顶约 30 ms。两个数都作为实测参数，在薄切片阶段定下来；
   - Overlay、Fusion（含分组最大值或求和、细胞核）、平滑、ROI 外接框裁剪和多边形模板（奇偶规则；多边形不合法时仍按外接框裁），从现有 `ui/shaders` 移植。这是我们自己的代码。
7. **重画通知**：用 `socket.socketpair()` 加 QSocketNotifier。图块到了 Rust 写一个字节，Qt 事件循环立刻醒，不轮询，Linux 和 WSL2 都能用。
8. **记录**：阶段名和 `utils/tile_trace.py` 一致（req/start/read/done/recv/gpu/present/cov），时钟用 `clock_gettime(CLOCK_MONOTONIC)`，和 Python 的 `time.monotonic()` 可以直接比较，现有 `a9_tiletl.py` 不用改就能分析。
9. **状态上报**：`stats()` 给出现在的状态提示和测试用到的字段：unavailable、last_error、base_overflow_channels、resolution_limited、admitted_level、ideal_level，以及覆盖情况（wanted/shown）。

### 3.2 Python 一侧

- 新的 `Step1CoreLayer(QOpenGLWidget)` 和一个薄绑定，对 mount 和测试提供和现在一样的公开接口：initialized、init_error、attach、is_resident、stats、readback_rgba_for_test。mount 用开关在旧路径和新路径之间整体切换。
- 不改的部分：
  - 显示映射和缺失窗口的补算；
  - 缺失产物的原因；
  - A1/A7 镜头门；
  - Step0 查看器、Tissue Preview；
  - 暂停和恢复的编排、提示文字；
  - 镜头仍由 pyqtgraph ViewBox 掌管。
- 预分割的 montage（`montage_gpu.py`）继续用旧的 Python 图层。两套合成必须逐像素一致，并且都服从 `gpu_memory.set_smooth`。
- 现有 Python GPU 路径保留为回退：模块缺失、加载失败或读文件出错时自动退回，日志写明原因。何时退役由用户决定。

### 3.3 正确性约束

- 原始图块：无损解压，和 Python 路径逐字节一致。测试覆盖两个真实文件，以及合成的各压缩方式、预测器、边缘不整块、u8/u16/f32。
- 校正产物的现算层级：Rust 的求和顺序和 numpy 的成对求和不同，结果可能在最后一位有差别。验收容差定为相对误差 ≤ 1e-6，且显示到屏幕后的 8 位颜色完全一致。做不到就把这部分留在 Python，并报告。
- 显示：同一组快照下，新旧两条路径的截图逐像素比较，误差为 0，有差异逐项说明。需要一个"已稳定"的确定状态才能比较。
- 保持已验收的行为：
  - ROI 外不画；
  - 校正产物缺失时给提示；
  - 粗层原子显示；
  - 离开 Step1 不画；
  - A1/A7 镜头门；
  - 笔记本 D3D12 每个进程约 5 个 GL 上下文的限制（GPU 测试一个进程一条）。

## 5. 风险（按严重程度排序）

1. **读图速度**：要追上 Odon 的热放大，Rust 读图必须做到约 1.2 ms/块。R0 实测，不达标就停下报告。
2. **笔记本的 WSL2/D3D12 驱动**：上传速度、垂直同步、每进程约 5 个 GL 上下文的限制。GL 探针提前到 R0 在笔记本上跑。
3. **功能对齐的范围和测试改写量**：工期风险，所以 R3 单列，并且用薄切片先回答值不值得做。
4. **pyqtgraph 的输入路径还在 Python**：每格滚轮都要走 pyqtgraph 的处理、`ExploreController._on_range_changed`，以及 Tissue Preview 的视框重画（`step1_viewer_mount.py:1216-1276`）。手势中响应中位数预计从 12 ms 降到 8–10 ms，Odon 是 7.3 ms，不一定追平。若这是最后的差距，另立块评估。
5. **释放、再拿 Python 锁的代价**：paint 返回后要重新拿锁，其他忙碌的 Python 线程（Step3 标签构建、校正计算）会让界面等最多 5 ms。在薄切片阶段测心跳间隔。
6. **内存和显存记账**：Rust 缓存要和 Python 缓存合计，并报给 `gpu_memory`。
7. **依赖和环境身份**：分割引擎的身份哈希包含 `requirements-pip.txt`（`seg_runner/runner.py:71`）。把 Rust wheel 加进去会改变引擎身份，需要裁决（见 §6）。服务器装 rustup 需要联网。
8. **许可证**：Odon 是 GPL-3，只参考设计，不拷代码和常量。每个 Rust 模块写明参考了 Odon 的哪些设计。依赖的 crate（pyo3、glow、weezl、flate2+zlib-ng、zstd、blosc-src）都是 MIT、Apache、BSD 或 zlib 许可，兼容。

## 6. 需要用户确认的事项

1. 采用路线 B，按 R0 → R1 → S（薄切片）→ R2 → R3 → R4 → R5 的顺序，薄切片不过就停。
2. 按 AGENTS 规则 4 授权新增的读图线程、缓存、调度模块（Rust 内核）。每个阶段开始前再报文件范围。
3. 现有 Python GPU 路径保留为回退，直到你决定退役。
4. 校正产物现算层级的容差：相对 1e-6 且屏幕颜色一致；做不到就留在 Python。
5. Rust wheel 怎么进环境：
   - 推荐：写进 `requirements-pip.txt`，接受分割引擎身份变一次。如实记录，最干净；
   - 或：单独安装，不进这两个文件，身份不变，但环境记录不完整。
6. 在服务器上安装 Rust 工具链（rustup，联网，装在 /root/.cargo）；笔记本的 WSL2 里也要装。
