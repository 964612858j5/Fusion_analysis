# Step1 G3.2b.4B2：冷 Patch 为什么比冷 Tissue 空降慢（只读诊断）

**日期：** 2026-09-21 · **分支：** `v15-interactive-channel-workspace`
**起止 HEAD：** `9d78d1c`（未提交；未 reset/checkout/restore/clean/stash/rebase/amend）

**本块只测量，未修改任何生产行为。**

## 0. 结论

**冷 Patch 慢的唯一原因是视口几何，不是入口本身、不是额外产品动作。**

- **Patch 的成本是常数**：`show_patch()` 把相机设为**整个 patch bbox**，不管用户当时
  在哪个缩放。实测固定 `1465×1088` 世界像素、**12–16 块可见瓦片**。
- **Tissue 的成本跟着用户当前缩放走**：`_on_step1_tissue_navigate()` 读当前
  `viewRect()`，取 `min(宽,高)` 作为落点方形边长，**保留用户的缩放**。
- 用户点 patch 的时候通常是**放大着的**，于是 Tissue 只要 2–6 块瓦片、Patch 一律 12 块。

**决定性证据（B2）：让两者落到完全相同的最终视口后，差距消失**——两轮各自
`158.2 / 107.4 ms` 与 `160.9 / 168.6 ms`（12 块瓦片、44 vs 43 次读取、都真冷），
Patch 并不更慢。

**缩放扫描（C）量化了这一点：**

| 用户当时缩放（视口短边 L0） | Tissue 瓦片/耗时 | Patch 瓦片/耗时 | Patch ÷ Tissue |
| ---: | ---: | ---: | ---: |
| **300** | **2 / 42.6 ms** | 12 / 136.6 ms | **3.21×** |
| 700 | 6 / 81.8 ms | 9 / 94.7 ms | 1.16× |
| 1500 | 20 / 219.5 ms | 12 / 153.9 ms | **0.70×**（Tissue 反而更慢） |
| 3000 | 6 / 150.1 ms | 16 / 168.8 ms | 1.12× |

缩放 1500 那一行是反证：当用户视口**比 patch bbox 还大**时，**Tissue 更慢**。
因果变量是**视口面积**，不是哪个入口。

**被否定的假设：** Patch 没有启动任何 legacy loader、没有跑
`_ensure_channels_cached`、没有跑 `_refresh_patch_preview`；两条路径的 hidden
`ExploreController` 请求数**按视口面积等比例**出现，不是 Patch 独有；没有重复读取、
没有迟到拒收、没有取消。

**诚实边界，逐条：**

- Tissue 用的是 overview 点击**真正发出的那个信号**，不是私有函数。G3.2b.3 已经
  证明真实 `QTest.mouseClick` 打在该画布上恰好产生这个信号；本块没有再把 popup 的
  overview 架在真实切片上，因为那一段两条路径**并无不同**。
- **"冷"= 本次运行从未访问过的区域**（新区域首次产品访问 / 进程内冷路径）。
  **没有清除 OS page cache**（需要 root，且会干扰其它窗口），因此本文**没有任何
  数字被称作磁盘冷读**。
- GUI 心跳是 GUI 线程上的 5 ms `QTimer`，其最大间隔是事件循环跑不动的真实时长，
  **不是** input-to-photon 延迟。
- 自然 paint 是离屏 widget 的 Qt 呈现事件；离屏下它很少发生（多轮为 `0`），
  所以**"一次完整清晰出现"这一条本块不以 paint 计数为证**，仍以 G3.2a/G3.2b
  已验收的门为准——本块未改生产代码，那些门未受影响。
- **最终像素与 C1 reference 本块未重测**：没有改动任何生产代码，像素不可能变化；
  0 LSB 的等价证据属 G3.2b.4A，仍然成立。
- 会话自动保存**保持开启**（它本身是被测对象之一），但输出目录指向 `/tmp` 的
  scratch 目录，**真实项目一个字节都没写**。

### 关键设计教训（第一轮失败，如实记录）

第一次编排是「Patch → Tissue → Tissue → Patch …」而**不重置相机**。结果毫无差异
（两者都是 `1465×1088`、12 块瓦片、READY 157 vs 162 ms）——因为**第一次 patch 点击
之后相机就是 patch 大小了，之后每次 Tissue 都继承这个大小**，两个入口变成了同一个
测量。这正是之前"合成 benchmark 用相似矩形所以看不出差别"的同一个陷阱。

改正：**每次测量前把相机停回同一个放大过的停车位**（`host.jump_to(2600, 2600, N, N)`，
该区域只在停车时访问、从不作为落点），然后落到一个从未访问过的目标。

## 4. C 组：差距如何随用户当时的缩放变化

每个缩放各测一次冷 Tissue 和一次冷 Patch，落点均为从未访问过的区域。

| 停车短边 (L0) | Tissue 视口 / 瓦片 / ms / 读取 | Patch 视口 / 瓦片 / ms / 读取 | 比值 |
| ---: | --- | --- | ---: |
| **300** | `404×300` / **2** / **42.6** / 15 | `1465×1088` / 12 / **136.6** / 44 | **3.21×** |
| 700 | `942×700` / 6 / 81.8 / 29 | `1465×1088` / 9 / 94.7 / 32 | 1.16× |

## 5. 两条完整时间线（C1，缩放 300，同一对冷落点）

相对用户输入事件，单位 ms。

| 阶段 | Tissue（2 块瓦片） | Patch（12 块瓦片） |
| --- | ---: | ---: |
| T5 首个 scheduler request | 3.61 | 3.51 |
| T4 首个 binding request | 8.11 | 13.14 |
| T7 当前视口请求全部发出 | 8.14 | 13.32 |
| T6 首个 provider read 开始 | 8.23 | 8.16 |
| T6b 首个 provider read 结束 | 17.60 | 25.02 |
| T8 首个目标 fine 瓦片到达 | 25.27 | 26.95 |
| T1 槽返回（UI 路由 + 相机 + 规划） | 32.37 | 24.45 |
| T10b 首次 GPU submit | 42.51 | 24.81 |
| T10 首次 raw texture 上传 | 42.49 | 59.05 |
| **T9 当前视口目标 fine 全部到达** | **42.57** | **136.56** |
| GUI 最长无响应 | 42.5 | 108.7 |

分段解读：

- **UI 路由 + 相机更新 + 规划**：两条路径都在 `3.5–13 ms` 内发出第一个请求。
  **入口本身不是瓶颈。**
- **I/O / 解码 / corrected 归约**：worker 读取累计 Tissue `181.8 ms`（corrected 2 次
  共 36.4 ms + raw 13 次共 145.4 ms），Patch `545.6 ms`（corrected 12 次共 176.0 ms +
  raw 32 次共 369.6 ms）——**3.0× 的 worker 秒数**，与 3.21× 的墙钟比值吻合。
- **GPU 上传与绘制**：首次 submit 在 25–43 ms，上传按瓦片数等比例，都不是主导。
- **T8 → T9** 才是差距所在：Tissue `25→43 ms`（2 块），Patch `27→137 ms`（12 块）。
  **纯粹是瓦片数量。**

## 7. 候选方案（**只提出，未实施**）

### 方案 A：保持现状——Patch 显示完整 bbox

- **用户看到**：整个 patch，一次到位。这是现在的语义，已真机验收通过。
- **需要读取**：恒定 12–16 块瓦片（本演示数据）。
- **还能优化多少**：把 §7.C 的 hidden 请求去掉后，读取由 44 降到约 12（-73 %），
  预计目标层就绪从 ~164 ms 降到 ~60–90 ms 量级——**推算，未实测**。
- **是否仍慢于 Tissue**：在用户放大时**仍会慢**，因为它的视口本来就更大。
  这是语义的必然代价，不是缺陷。

### 方案 B：Patch 保持当前缩放，以 patch 中心空降

- **用户看到**：不保证一次看见整个 patch；放大时只看到 patch 的一部分。
- **为什么接近 Tissue**：它就变成了 Tissue——同一入口、同一视口大小、同一瓦片数。
  实测等价条件下 `42.6 ms`（缩放 300）对现在的 `136.6 ms`。
- **相机与选中状态**：`_select_preview_patch` 的按钮勾选、`_preview_patch_idx`、
  `_selected_step1_patch_idx` 与 session save 都与相机无关，原样保留。
- **需要用户明确批准**：**是。** 这是产品语义变更，与"patch 是一个锚点，
  显示整个 patch"的既有裁定冲突。
- 最小改动点：`ui/step1_viewer_binding.py::show_patch()` 一处（或
  `ui/main_window.py::_select_preview_patch` 处改为调用 `jump_to_point`）。
  **一行级回滚**：改回 `host.jump_to(y0, x0, x1-x0, y1-y0)`。
  风险：与已验收的"patch 锚点"行为冲突；Step0↔Step1 相机同步、Tissue 视框
  都读同一个相机，需重跑相机与视框保护门。

### 方案 C：去掉 hidden `ExploreController` 的不可见请求（**对两条路径都有效**）

- **哪条请求链**：GPU 接管期间 `set_marker_visible(False)` 只把旧图层设为
  opacity 0，`_issue_raw_requests()` 照常发 level+1 underlay 与 prefetch ring。
- **是否产生可见像素**：**不会**（opacity 0）。
- **实测占比**：Patch 每次 32–37 个 binding 从未请求过的 RawKey，占全部读取的
  **73 %**（44 中的 32）；Tissue 18–22，占 **79 %**（28 中的 22）。
- **最小公共 request gate**：`viewer/explore_view.py::_issue_raw_requests()` 增加一个
  与 `set_marker_visible(False)` 配对的"不可见就不发"判据。
- **影响**：`viewer/explore_view.py` 是 Step0 全图、compare 面板、Step1 共用模块；
  必须保证回到旧渲染器 / CPU fallback / Step0 页面时请求流原样恢复。
- **风险**：较高（共用模块）。**回滚**：一个布尔开关加一处判据。
- 这就是 G3.2b.4B 报告里已经记过的第二号 blocker，**本块未实施**。

**按实测耗时贡献排序：**

1. **方案 C**（去掉 73–79 % 的不可见读取）——对 Patch 和 Tissue 都有效，
   不改任何产品语义，但要动共用模块；
2. **方案 B**（Patch 改为保留缩放）——能把 Patch 直接降到 Tissue 的水平，
   但是**产品语义变更，须用户裁定**;
3. **方案 A**（保持现状）——Patch 的成本是其语义的必然结果。

**不打包成一次大改。** C 与 B 相互独立，可分别裁定。

## 8. 诚实缺口

- 本块的绝对毫秒（Patch 中位 **163.9 ms**、Tissue **91.3 ms**）**远小于用户真机
  报告的 2 s 与 <1 s**。本块用的是**单通道** `CD22`；用户真机通常有**多个通道**
  同时显示，每通道的瓦片工作量按通道数相乘。**比值 1.8–3.2× 才是本块能证明的量**，
  绝对值不能直接对上真机。这一点没有被掩盖，也没有据此外推。
- 未测：多通道下的绝对耗时、真机窗口尺寸下的瓦片数、用户实际点击 patch 时的
  典型缩放。若要把绝对值对上真机，需要用户给出他点 patch 时的缩放习惯，
  或在真机上记录一次。
