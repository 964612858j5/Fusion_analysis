# v16 A2b-probe 报告：OME-TIFF 与 OME-NGFF 0.4，两边各用格式适配的读取器

**状态：用户裁定 (b)，2026-09-30。** OME-TIFF 仍是规范原始数据，zarr / NGFF 只用于派生栅格；A2b（`NgffSource` / 导入 / `NgffScanReader`）不做；不再进行任何 NGFF 相关的测试、找补或参数搜索；`~/fusionflux/bench_a2b/` 的 JSON 与比对记录保留作档案。

## 1. 结论

**按预先写好的采纳规则逐行判定，结论是 (b)：不采用 NGFF 作规范原始存储**（v2.2 §5.7 (b)：OME-TIFF 仍是规范原始数据；zarr / NGFF 只用于派生栅格）。**等你确认。**

- 决定性的是**第 2 行**：viewer 的其他预注册项必须都 ≤ 1.05 × TIFF。
  - 原图上 8 种布局**全部**不满足：第 1、2 层视口平移（冷）和通道切换，NGFF 慢 1.16–1.56×。
  - 合成大图上两种候选也不满足：通道切换 1.26–1.55×，第 2 层平移（热）1.24–1.38×。
- 合成大图上**第 1 行也不满足**：第 0 层视口平移（冷）NGFF 慢 1.14–1.18×，超过 1.05×。
- 其余各行在最佳布局上都满足：Step4 端到端、fusion、磁盘、科学结果。

这不是「NGFF 全面更慢」。结果是分化的：第 0 层上的分析型读取 NGFF 明显更快，交互型的小读取（尤其是粗层）更慢（§4）。规则要求的是**全面不回退**，所以结论是 (b)。

## 2. 做了什么（与申请一致）

- **布局**：第 0 层分块 512 / 1024 / 2048 × Blosc-lz4 / zstd（clevel 5，SHUFFLE），共 6 种；第 1 层及以上都是 512。C1 选出 1024 后，再加 BITSHUFFLE 的 lz4 / zstd 两种，共 8 种。
- **读取器**：
  - TIFF 产品路径（`RawTileProvider`、`TiffTileReader`、`OMETIFFLoader`，原样）；
  - TIFF 同类优化：按 TIFF 分块直接解码、块缓存、扫描预读；
  - NGFF 通用 zarr（A0 那种）；
  - NGFF 适配：按块直接读字节、Blosc 解码、块缓存、扫描预读。
- **资源预算两边相同**：8 线程、预读 1 块、块缓存 512 MiB，关闭 Blosc 自带线程。块缓存在每次计时运行前清空。
- **基线**：每一行都取 **TIFF 两个成绩中较好的那个**。
- **协议**：沿用 A0：同样的种子和工作负载；1 次预热、3 次冷、3 次热，取中位数；冷读前 `sync` + `fadvise` + `fincore` 核对。
- **检查点**：
  - C0 通过；
  - C1 没有触发 1.5× 提前停止线（最佳布局的 Step4 端到端 ≈ 0.6–0.7×）；
  - C2 完成。
  - 全程约 2 小时，远在 4 天时间盒之内。

## 6. 从数据里学到的（供以后参考，不改变判定）

1. **A0 的「NGFF 慢一倍」不是格式本身的问题。** 用 ≥ 1024 的第 0 层分块和适配读取器之后，Step4 端到端反而快约 30–40%，原始扫描快约 2×，大 ROI 快 2–2.7×。
2. **A0 的体积问题来自一个无效的设置。** uint8 上的 SHUFFLE 什么都不做；BITSHUFFLE 让 zstd 副本降到源 TIFF 的 0.94×，lz4 降到 1.22×，速度基本不变。
3. **NGFF 输在粗层的小块交互读取。** 第 1 / 2 层在两种格式里都是 512 分块，NGFF 冷读仍慢 1.2–1.6×。推测原因是 NGFF 每个分块一个文件，冷读要逐个打开，而 TIFF 在一个已打开的文件里 pread；这一点**没有单独测**。改粗层的分块或存储方式不在封闭清单里，按申请没有尝试（不为 NGFF 找补）。
4. **TIFF 自身还有明显的读取余量。** 按 TIFF 分块直接解码的同类优化读取器，在区域读、平移、通道切换上比产品路径快约 2×（例如原图 ROI 2048² 14.8 → 7.4 ms，通道切换 64 → 29 ms）。Step4 端到端基本相同（9.10 → 9.03 s），因为产品的 `TiffTileReader` 本来就是这么读的。**按申请只记入待办，v16 不实现。**
5. fusion 以计算为主，两种格式、各种读取器都在 16–18 s，看不出存储的差别。
