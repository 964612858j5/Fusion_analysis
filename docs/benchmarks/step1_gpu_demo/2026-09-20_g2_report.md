# Step1 G2：完整粗层与既有瓦片供给适配验证

**日期：** 2026-09-20

**范围：** G2 仅新增测试可达的 `Step1GpuBinding`，把已存在的 Step1 provider/scheduler/raw-cache 供给转换为 G1 可消费的 immutable `SourceDescriptor`。没有 production mount、MainWindow、Step0、共享 UI、viewer/scheduler/cache/provider/source 修改，也没有 G3/G4。

## 结论与边界

`Step1GpuBinding` 已完成独立验证：它只消费注入的公开 provider、scheduler、controller 和 caller-built snapshots；不读取私有 controller/scheduler/cache 状态，不创建第二个 scheduler/raw cache/source authority，不接管相机或 display state。它仍没有被任何生产模块导入或挂载。

完整粗层以每 channel 的全量 `RawKey` transaction 准备，并且只在最后一个有效结果到达后发布；局部 fine 也以当前 viewport、channel、epoch 的完整 transaction 提交。无论 coarse/fine 是否完成，已发布的其他 channel 数据不会被擦除。源、handoff、binding revision、generation 与 viewport epoch 均在 GUI-thread 接收边界逐项复核，迟到结果不发布。

## 实现与权属

### 公开供给边界

- 注入 `provider.source_identity()`、`num_levels`、`level_shape()`、`level_downsample_yx()`、`source_table`；每个 `RawPlane.identity` 精确使用既有 `RawKey`。
- 仅调用 `TileScheduler.request(TileRequest, callback)` 和 `cancel_generation()`；不检查 scheduler 私有 pending/cache/controller 数据。
- 仅消费 `controller.snapshot()`、`interaction_event`、`gesture_quiet` 与 `grid`。宿主必须在公开 source replacement 后显式调用 `source_changed()`，销毁前显式调用 `dispose()`；G2 不猜测私有生命周期。
- scheduler callback（包括同步 cache hit 或 worker callback）只 emit 本地 `Qt.QueuedConnection` signal。只有 GUI-thread `_accept_result()` 可以改变 binding transaction 或调用 G1。

### 完整粗层、fine 与预算

- 由 `provider.num_levels - 1` 与公开 level shape/grid 枚举每个 active channel 的完整粗层；预先检查 tile 数和 float-plane bytes budget。任一未到/错误/budget-refused channel 不会以 partial coarse 出现在 descriptor 中。
- 原始 float array 保持 `NaN`，并以 `valid=np.isfinite(array)` 构造 G1 plane。world rectangle 由原始结果 shape、tile address 和无取整 `level_downsample_yx()` 推导。
- 每次 pan/zoom/patch/Tissue 公开 snapshot 都使用其当前 `level`/`visible_tiles` 计划 fine；`NAVIGATOR_JUMP` 立即请求，不等待 quiet。旧 fine generation 被取消且仍由 epoch/revision fence 拒绝。
- `refresh_display()` 对已有 resident planes 只重提 G1；它不请求 scheduler/provider，也不触发 G1 raw upload。仅 display newly-active、尚无 coarse 的 channel 可开始其首次 coarse 准备。
- corrected decision 但不存在 product 的 channel 被标记 unavailable，绝不 raw fallback；原始 source 和 corrected product 的 ROI 边界保持既有 `Step1TileProvider` 规则。

独立审核对上述 G2 实现给出两个必须收口的 blocker。本节记录这两项的处理、证据与仍未测的边界。除 `ui/step1_gpu_binding.py`、`tests/test_step1_gpu_sources.py`、本报告、`docs/step1_gpu_demo_plan.md` 与新增的 `2026-09-20_g2_1_gates.json` 之外，没有任何文件被修改。

### Blocker 1：完整 coarse 可能被连续 fine 请求饿死

**通俗说明。** 原来新通道的完整粗层请求排在「最后再做」的位置（priority 100），而当前画面需要的精层排在「马上做」的位置（priority 0）。只要用户一直平移或缩放，就会不断产生新的精层请求插到粗层前面，新启用通道的完整粗层可能永远轮不到。

**现在的规则。** 只要还有任何一个通道的完整粗层没做完，**从那一刻起**新发出的精层请求就排到粗层后面（priority 200）；在那之前已经排进队列的精层保持原来的位置，照常先做完。最后一个粗层事务一完成，精层立刻恢复到原来的最前位置。粗层自己的位置（priority 100）不变。

实现只有三个常量和一处「当前是否还有粗层在做」的判断，全部在 `ui/step1_gpu_binding.py` 内：`PRIORITY_FINE_FOREGROUND = 0`、`PRIORITY_COARSE = 100`、`PRIORITY_FINE_DEFERRED = 200`，加上公开只读的 `coarse_pending_channels()`。

**为什么没有改 scheduler。** `TileScheduler` 已经提供了需要的全部语义：RawKey 就绪队列是按 `priority` 的最小堆、同一优先级内 FIFO，`cancel_generation()` 丢弃尚未开始的排队项，`request()` 按 key 单飞去重。已经排队的条目本来就不应该被重新排序（那会改变 scheduler 的公共行为，也会打断其他消费者），因此唯一需要的动作是**把新发出的精层请求放到更靠后的一层**——这完全是调用方的选择。没有新增 scheduler、线程池、队列、令牌桶、仲裁器或状态机，没有读取 scheduler 的私有 heap/pending，`viewer/scheduler.py` 零改动。

**验证。** `test_new_channel_complete_coarse_is_not_starved_by_continuous_pan_fine` 使用**真实** `TileScheduler`（`io_workers=1`）+ 真实 `Step1TileProvider` + 可控公开 raw 金字塔（24×24 / 12×12，tile 4，粗层 3×3=9 瓦片）。A 先完成并显示；启用 B 后 B 的 9 块粗层入队；随后经公开 `interaction_event` 连续发出 24 次 PAN。判定依据是**单个真实 I/O worker 的实际读取顺序**，不读 scheduler 私有状态：

| 观察项 | 结果 |
| --- | --- |
| B 启用后连续 PAN 次数 | `24` |
| B 粗层请求次数 | `9`（每块恰好一次） |
| B 启用后发出的精层请求优先级分布 | `{200: 96}`，前台 `0` 为 `0` 次 |
| B 启用后 scheduler 未完成条目（24 次 PAN 后） | `queued 12 / running 1 / total 13`，再追加 12 次同区域 PAN 后不变 |
| B 启用后的实际读取顺序 | 前 `9` 次全部是 B 的 level-1 粗层，之后才出现 level-0 精层 |
| B 完整粗层完成 | `true` |
| 出现过部分 B 的 descriptor | `0` |
| A 缺席的 descriptor（首次发布之后） | `0` |
| 粗层完成后的下一次 viewport 更新 | 精层恢复 `priority 0` |

`NAVIGATOR_JUMP` 在粗层进行中仍然**同步立即**请求目标瓦片（测试断言跳转产生的请求恰好是目标 tile `(4, 4)`），只是排在粗层之后；空降位置本身由已完整的粗层承接。未完成请求有界：scheduler 按 tile 身份去重，binding 每个 epoch 取消被替换的上一个 epoch，因此追加一整轮同区域 PAN 后未完成条目数完全不变。

### 变异闸门

每个变异临时施加于 `ui/step1_gpu_binding.py`，运行强制 GPU 的 `tests/test_step1_gpu_sources.py` 后精确还原（还原后 md5 与改动前一致）。

| 变异 | 结果 |
| --- | --- |
| 粗层恢复为被连续 fine 永久压后的优先级策略（fine 永远 `priority 0`） | 红：公平性门 + partial coarse framebuffer 门失败 |
| 部分 coarse 提前进入 `SourceDescriptor` | 红：原子粗层门 + 公平性门 + framebuffer 中间帧门失败 |
| fine 到达时删除本通道 coarse | 红：公平性门 + framebuffer fine 保护门失败 |
| 某通道 fine 到达时擦除其他通道 | 红：既有 G2 硬件门 + 公平性门 + 新 framebuffer 门失败 |
| ROI 外 NaN 被填成有效像素（`nan_to_num` + valid 全真） | 红：新 framebuffer 门的 ROI alpha 断言失败 |

诚实记录：单独把 `valid` 掩码翻成全真而**不**动 values，测试不会变红——因为 ROI 外在 `Step1TileProvider.read_tile` 里本来就是 NaN，而 G1 shader 以 NaN/Inf 判定无效，`valid` 掩码在该路径上是冗余的第二道保险。这是既有设计的事实，不是本次新增缺陷，也没有据此改动任何产品代码。
