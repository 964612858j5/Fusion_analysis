## 0. 一句话结论

`_prepare_centre_floors()` 无条件请求 `HOT_METHODS` 的**两种**方法。floor 侧按设计只保留
**一个可替换的后台等待值**，所以**最后一个请求赢得等待位** —— 而最后一个永远是 `cucim`。

当用户已经在看 cuCIM 时，那个最后的 cuCIM 请求是**前台正在算的同一件事**的副本：
它顶掉了等待位里的 TopHat，然后在前台把 cuCIM 存进 cache 之后被正确地当作
「已缓存」丢弃。**TopHat 因此从未被准备。**

TopHat 在屏时同样发生顶替，但幸存下来的恰好是前台**没有**在算的那个方法，所以正向通过 ——
**是固定顺序的运气，不是设计。**

## 3. 为什么自动化此前没抓到：本机上竞态根本不会发生

**自然时序下（`biopsy.ome.tif`，无注入延迟）四条轨迹全部通过**，包括 cuCIM→TopHat。
原因由事件序列直接给出（PD1，修复前）：

```
13857.4 START   cucim  fg=True          ← 前台 floor 开始
14454.4 RESULT  cucim  fg=True          ← 597 ms 就结束了
14816.7 START   tophat fg=False         ← HOT 此时才开始问（晚了 362 ms）
14817.6 PREPARE tophat cached=False  job_running=False
14817.7 PREPARE cucim  cached=True   ← 前台已经缓存好了，直接返回 False
```

`_prepare_centre_floors()` 只在 `_hot_idle()` 为真时才动手，即 HOT 的瓦片批次做完之后 ——
在这张演示切片上，那已经是前台 floor 完成之后。**竞态窗口在本机上是关着的。**
用户真机那张切片大得多，前台 floor 远慢于 HOT 的瓦片批次，窗口就是开着的。

**这本身就是一条发现：不是「测过了没问题」，而是「这台机器测不到」。**

## 4. 强制打开窗口后，缺陷逐事件复现

`--slow-floor 400`：只在 **floor worker 线程**、且只对 floor 自己那个整层数组上 sleep

**不改任何决策、key 或像素。** `--dwell 9000` 把静止时间放长到与被拖慢的工作相称。

**修复前 —— PD1，cuCIM 在屏（与真机第 2 条一致）：**

```

19813.0 PREPARE cucim  cached=False running=cucim   slot: tophat -> cucim    ← 被顶掉
20976.6 RESULT  cucim  fg=True                      ← 前台把 cuCIM 存进 cache
```

**这就是 §十二.4 要求的「TopHat 后台请求被替换的直接证据」：**
`slot: tophat -> cucim`，且那次 cuCIM 请求的 `running_request.method == "cucim"`，
`has_cached_floor == False` **仅仅因为前台还没算完**。

## 5. §四 七问的逐条回答（全部有证据）

1. **TopHat 是否先进入后台等待位？** 是。`slot: None -> tophat`（19812.9）。
2. **随后的 cuCIM 请求是否替换了它？** 是。`slot: tophat -> cucim`（19813.0）。
3. **那个 cuCIM 请求是否其实对应前台正在负责的当前方法？** 是。同一时刻
   `running_request = {method: cucim, foreground: true}`。
4. **Original 为什么能准备两种？** 它没有前台 floor job：
   `PREPARE tophat cached=False job_running=False running=None slot: None->None`
   —— 第一个请求**立即开跑**（不占等待位），第二个才进等待位，于是两个依次完成。
5. **正向 TopHat→cuCIM 为什么恰好通过？** 同样被顶替
   （`slot: tophat -> cucim`，running=tophat），但幸存的 cuCIM **不是**前台在算的方法，
   所以前台 tophat 落地后 `NEXT waiting=cucim already_cached=False` → 真的跑了。
   **是固定顺序的运气。**
6. **是否存在参数 / source identity / level / stride 不一致？** 否。全部 key 都是
   `…|L2|s1`，`tophat|(1,)` 与 `cucim|(3,)` 分别是各自参数在 level 2 的 effective 值。
7. **问题是否只在 HOT 的请求选择？** 是。floor cache key、worker、scheduler 全程行为正确 ——
   等待值被替换是**按设计**的「后来者取代先来者」，被丢弃也是**正确**的去重。
   错的只是 HOT 请求了一件不该由它请求的事。

不需要改 `explore_view.py`（2 不触发）；不需要第二槽/队列/cache/scheduler/worker/状态机

## 6. 最小修复，以及为什么不需要新状态

`viewer/multichannel_prefetch.py`，`_prepare_centre_floors()` 内，一处：

```python
shown = snapshot.method
for method, base_param in self._method_params(spec):
    if method == shown:
        continue
    ...
```

- **屏幕上那个方法已经有主了** —— 前台自己的 floor 路径负责它。HOT 不再去请求它，
  单个等待位就只会装真正没人负责的那一个。
- **不是换顺序**：换顺序只会把失败从一个方向搬到另一个方向。
- **没有写死方法名**：判断来自 `snapshot.method`，所以 Original（没有方法、没有前台 floor）
  仍然两种都准备；`HOT_METHODS`、spec 参数、`prepare_floor_async()` 全部沿用既有。
- **不新增状态**：没有第二等待位、没有队列、没有 running-request registry、
  没有 token/authority/journal/状态机；floor key、`_floor_cache_limit`、
  `FLOOR_MAX_PIXELS`、前台 floor 生命周期、worker/scheduler/provider/算法一律未动。

**修复后 —— 同一条 PD1，同一组设置：**

```

19798.7 PREPARE tophat cached=False running=cucim   slot: None -> tophat   ← 只问 TopHat
20952.2 RESULT  cucim  fg=True
20952.9 NEXT    waiting=tophat already_cached=False
20952.9 START   tophat fg=False                     ← TopHat 真的被准备了
22902.6 RESULT  tophat fg=False
```
