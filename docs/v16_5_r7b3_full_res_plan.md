# v16_5 R7b-B3 计划：校正通道的全分辨率也存一份 16 位、512 一块（第三版，codex 第二轮审核通过，待用户批准；B2、B3 实施需分别说"开始"）

上级：`docs/v16_5_r7b_corrected_read_plan.md` v4（已批准；B1 已授权，B2 需用户说"开始 B2"）。
用户 2026-10-14：B3 计划和 B1 一起写。本计划只写设计和启动条件，实施另需用户明确说"开始 B3"。

## 0. 为什么（R7a 证据，`a9_bench/r7a/R7a_results.md`）
- 用户真实项目冷读，校正通道一次全分辨率读取平均 34.8 ms：
  - 读文件段 26.7 ms，其中线程 CPU 只有 0.8 ms，以等待为主；
  - LZ4 6.3 ms，unshuffle 1.0 ms；
  - 每次交给程序约 1.2 MB 压缩数据，要解压 4 MiB 浮点数据，再从中取 1 MiB 用。
- OME-TIFF 一个图块约 0.13 MB，读一次 15.6 ms。
- B1（块复用、线程数）能省掉重复读取和解压，但省不掉第一次读这 1.2 MB。
- B2 的中间层只改善等待期间的顶替画面，全分辨率本身仍然要读这 1.2 MB。
- 在用户的数据上（R6 抽样），校正值都是 0–251 的整数：全分辨率存成 16 位整数，数值和显示语义可以无损（§1）。抽样估计每个 512 块压缩后约 0.18 MB，这只是估计。
- 512 存储块从数组自己的原点起算，屏幕图块从全片原点起算；ROI 原点不对齐 512 时，一个屏幕图块可能跨 2×2 个存储块。不影响无损，但影响读取量和块复用收益，测量时对齐和不对齐都报告。

## 1. 内容
- 在 B2 的 `corrected_display.zarr` 里，每个校正通道再加一个 stride 1 的数组 `s1`：全分辨率、16 位无符号整数、512×512 一块、blosc-lz4 + shuffle。
- **形状和原点**：
  - `s1` 的形状等于浮点校正数组的实际形状，原点等于它的原点；
  - 现有读取范围是"区域包围框和数组实际范围的交集"（Rust `reduce.rs` 和 Python 都如此），`s1` 必须保持完全相同的范围；
  - 浮点数组形状和包围框不一致时，不生成 `s1`，照旧读浮点（不靠补零扩成包围框大小）。
- **资格检查**：读浮点数组的全部逻辑样本，包括缺失块文件代表的 fill 值（现有读取把缺块读成 fill，不是失败）。
  - 全部有限、在 0–65535 之间、都是整数（fill 值也要满足），才生成；
  - 否则整个通道不生成 `s1`，也不生成 B2 的各层，日志写明原因；
  - NaN、Inf 一律整通道拒绝。
- **缺块和 fill**：
  - `s1` 的 fill 值等于浮点数组的 fill 值（转成整数）；
  - 浮点缺块的位置在 `s1` 里写成 fill 值；
  - 全是 fill 的块可以不写文件（和 zarr 规则一致，读时返回 fill）；
  - 边缘块按 zarr 规则存整块大小、读时截掉。
- **多边形外**：Step0 在多边形外写的是 0 样本，读取层照样当作样本，最后画的时候再裁掉（`search_ctrl.py`）。`s1` 原样保存这些 0，读取和最后裁切的规则都不变，不改成无效。
- **无损的含义**：16 位转回 32 位浮点后数值相等（0–65535 全部取值已核对），显示语义一致；不承诺 `-0.0` 这类浮点位模式也保留。
- **发布**：
  - 一遍流式处理可以边检查边写；
  - 必须在全通道资格通过、全部写完、落盘抽验通过之后才写 `complete`；
  - 末尾才发现不合格的，`s1` 和同一次生成的 B2 各层都不发布（不写 `complete`，删除未完成的输出）。
- **落盘抽验**：
  - 写完后重新读取、解码落盘的 `s1`，抽查约 1% 的块，至少 1 块，必须包括边缘块和源块（1024）边界两侧的块，和浮点逐像素比较（`s1` 的 512 块和源块同原点，不存在跨源块边界的 `s1` 块；跨界的读取窗口在合成回归里验证）；
  - 任何一块不等，整个通道作废；
  - 这是抽验，不是全量证明。合成项目上做全量对照，真实项目不要求再全量读一遍。
- 身份、完成标记、来源失效、`--in-place` 补建保护、缺 `source_identity` 跳过：沿用 B2.1、B2.3。
- **空间检查**：
  - 按本次要生成的 `s1` + B2 各层 + 边缘整块 + 临时文件，用保守的压缩比（试点之后取试点实测的最大值加 20% 余量；第一次试点时没有实测值，按整块未压缩字节加 10% 开销算，最保守）算峰值增量；
  - 在目标文件系统上检查可用空间，不够就不生成，日志写明；
  - 生成中途遇到磁盘满，停止，不发布完成标记，科学产品不受影响；
  - 48 GB 只是估计，不作准入依据。

## 2. 读取
- **Rust**（`step1_tile.rs` / `corrected.rs`）：目标层是全分辨率、通道有有效的 `s1` 时，读 `s1`（16 位转成现有的 32 位浮点图块），否则照旧读浮点数据。
  - 有效区域的规则和读浮点时完全一样：包围框外无效；包围框内、多边形外是有效的 0 样本，最后沿用现有的渲染裁切。不修改读取或渲染机制。
- **Python 后备路径**：同样认 `s1`。
- 块复用缓存（B1.1）同样适用：键是 `s1` 数组的目录 + 块坐标。缓存里存的是转换后的 32 位浮点，按每样本 4 字节记账，不按磁盘上的 16 位大小算。
- 只有 `s1` 不会给 B2 的过渡层带来资格；B2 的 carry、请求顺序、退出规则照旧。
- 现在有四处只在 stride > 1 时才查保存的层，要接通 stride 1：
  - Python 解析（`step1_source.py` 拒绝 stride ≤ 1）；
  - Python `read_tile`（只在 stride > 1 查）；
  - 清单传递（`step1_core_adapter.py` 只传 stride > 1）；
  - Rust `corrected_tile`（只在 stride > 1 选层）。

## 4. 验收
- **数值**：
  - 合成项目上，每个生成的通道 `s1` 和浮点全分辨率逐像素全量相等；真实项目做 §1 的落盘抽验。
  - 停稳画面逐像素相同，适用条件：同一来源、相机、显示参数和后端；当时的目标层确实是全分辨率；比较区域已由全分辨率图块覆盖并显示；并且确认开着时真的读了 `s1`（统计读 `s1` 的次数大于 0），避免两边都退回浮点而假通过。
  - 缩小或预算降级时显示的是 B2 的舍入层，不在这条承诺内（B2 在两档倍数停稳时同样要求逐像素相同，因为那时显示的也是全分辨率）。
  - R6 的真实项目参考图继续有效；有差异先报告，不靠重拍参考图掩盖。
- **性能**（R6 的尺子，参数冻结；用户真实项目副本，两档倍数，冷读 S1、S2 各 3 轮）：
  - 全分辨率读取的字节数、读取时间、排队时间相对 B1 结束时的变化；
  - 拖动中糊的面积、最差一帧、跳变、新边缘变清楚时间。
  - 目标沿用 R7b §2（S2 ≤ 2%、S1 ≤ 0.5%，两档倍数分别达到），B2 和 B3 一起完成后整体评估。
  - 只做了 B3、没做 B2 时，单独报告 B3 的贡献，不作通过与否的判定。
  - B2、B3 一起做时，在同一个 B2 配置下开关 `s1`（`BLOCK01_STEP1_DISPLAY_S1=0`）对比，单独看出 B3 的贡献。
- **回归**：
  - 缺失、过期、未完成、dtype 不符、抽查不等的 `s1` 都退回浮点路径；
  - 非对齐 ROI、ROI 多边形、奇数尺寸、边缘块；
  - 非零 fill、合法的 0、65535、NaN/Inf 拒绝、浮点数组形状和包围框不一致时跳过；
  - 合成项目上确认分割和分析仍读浮点数据；
  - Python 和 Rust 两条路径一致。

## 5. 不做的、回退
- 不改浮点校正结果，不改分割和分析读取的数据，不改原图，不加界面。
- 回退：
  - 设 `BLOCK01_STEP1_DISPLAY_S1=0`（Python 和 Rust 两条路径都认，重新打开或重绑来源时生效，不新增动态切换），或删除 `s1` 数组，全分辨率就回到读浮点；
  - B2 的中间层不受影响，仍是 16 位；
  - 删除整个 `corrected_display.zarr` 会同时撤掉 B2，不能用来单独看 B3 的贡献。
