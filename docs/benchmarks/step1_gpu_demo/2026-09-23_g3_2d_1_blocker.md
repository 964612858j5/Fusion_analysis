## 2. 根因

`ui/step1_draft_spec.py::build_spec()` 里两条分支的语义不一致：

- **Overlay 分支**：`channels = [ch for ch in visible_channels(state, scope) if ...]`
  —— 勾选参与。
- **Fusion 分支**：直接取 `domain.effective_config()` 的 `groups` / `group_weights` /
  `nucleus`，**完全不看 `visible_channels`**，于是取消勾选的 DAPI 仍以
  `nucleus=('DAPI', 1.0)` 进入快照。

`ui/main_window.py::_effective_fusion_config()` 的注释「Display visibility has no vote in it」
描述的正是这个旧语义——它对**持久科学配置**是对的，但**当前显示快照**不该照单全收。
用户 2026-09-23 的新裁定把勾选定义为「当前是否显示」，两种模式一致。

## 4. 为什么停下：最小修改落在白名单之外

本块允许改的生产文件只有 `ui/main_window.py`。它能修好**第三、第四**行（Tissue Preview、
legacy contributor 集合），**但改不到用户实际抱怨的 GPU Viewer**：
那条链上的 `_gpu_display_snapshot()` 在**冻结的** `ui/step1_viewer_mount.py` 里，
它调用的 `build_spec()` 在 **`ui/step1_draft_spec.py`**——该文件既不在允许清单，也不在冻结清单。

**申请追加白名单：`ui/step1_draft_spec.py`（仅 `build_spec()` 的 Fusion 分支）。**

- **为什么是它：** GPU Viewer 与 CPU compose **共用这一个构造器**，在这里加 gate
  等于「一处修好两个显示面」，**不会产生第二套 visibility authority**；
  该文件顶部已经导入并在 Overlay 分支使用 `visible_channels(state, scope)`，
  不需要新增依赖。
- **改动形状（未实施）：** Fusion 分支取 `effective_config()` 之后，
  用 `visible_channels(state, scope)` 过滤 —— group contributor 需「有效权重 > 0 **且**已勾选」；
  nucleus 需「weight > 0 **且** nucleus 通道已勾选」，否则在**快照里**表现为 `("", 0.0)`。
  `domain.effective_config()` 与模型中的 nucleus/weights **一律不改**，
  重新勾选时直接从模型恢复。
- **同时在 `ui/main_window.py`（已授权）** 给 `tissue_render_snapshot()` 的 Fusion 分支和
  `_fusion_weighted_channels()` 加同一条 gate，四个面语义一致。
- **风险：** `build_spec()` 也服务 CPU compose 与其它 Step1 消费者；
  过滤只影响**当前帧的贡献者集合**，不影响 `effective_config()`、Fusion Settings 与 Save。
  Overlay 分支一行不动。
- **回退：** 去掉 Fusion 分支那一个过滤即恢复今天的行为；无新增状态、无新增文件。
- **另有一条既有门需要按新裁定改写并写明**（不是偷偷放宽）：任何断言
  「Fusion 不受勾选影响」的旧门，例如 `_effective_fusion_config()` 注释所描述的语义门。
  改写前会先在报告里列出具体门名与改动理由。
