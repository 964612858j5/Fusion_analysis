# Step1 G3.2b.4：首次 Patch / Tissue 冷空降准备过慢 — 真实分段测量

**日期：** 2026-09-21 · **分支：** `v15-interactive-channel-workspace`
**起止 HEAD：** `9d78d1c`（未提交，工作树继续，未 reset/checkout/stash/restore）

## 0. 结论摘要（本块**未实施任何生产修复**）

本块按要求**先测量**。测量在**真实演示级数据**上完成：真实 OME-TIFF
金字塔、真实 Step0 写出的 cuCIM/tophat 校正产物、生产 `Step1WholeSlideMount`
/ `Step1ViewerHost` / `build_step1_stack` / `TileScheduler` /
`ExploreController` / `Step1GpuLayer` / `Step1GpuBinding`，以及两个公开导航
入口 `mount.show_patch()` 与 `mount.jump_to_point()`。

三条结论：

1. **冷 Patch 与冷 Tissue 空降确实走同一条底层路径**（源码与实测双重确认）。
2. **主导成本有两处，都不在本块白名单内**：
   - **校正来源的归约**（`viewer/step1_source.py::reduce_corrected`）：一个
     cuCIM 通道的**完整粗层要 8.29 s**，同一张片子的 raw 通道只要 **0.03 ms**
     （相差约 2.7×10⁵ 倍）；四个校正通道 **31.94 s**。这就是"首次启用通道
     准备过慢"的真正来源。
   - **GPU 接管期间仍然全速运行的旧 `ExploreController` 请求流**
     （`viewer/explore_view.py::_issue_raw_requests` 的 level+1 underlay 与
     prefetch ring）：每次冷空降多出 **20–24 个 GPU binding 从未请求过的
     RawKey**，占单通道冷空降全部 provider 读取的 **62 %**。这些瓦片的像素
     **永远到不了屏幕**——GPU 接管时旧图层被 `set_marker_visible(False)` 设成
     不透明度 0，只是没有停止它的 I/O。
3. **白名单内没有可消除的实质浪费。** `Step1GpuBinding` 在一次冷空降中是
   **12 请求 → 12 唯一 RawKey → 12 次真实读取 → 12 次纹理上传，零重复**；
   热返回 **0 读取 / 0 上传 / 1 次 submit**。G3.2a/G3.2b 的时机修复已经把
   binding 自己造成的串行等待清掉了。

因此本块**触发停止条件 #1**（"主瓶颈在 provider / source reduction / 共享
cache"），按 §七.5 与 §九 停止，不实施越界修复，最小追加授权方案见 §7。

**诚实边界（重要）：** 单通道冷空降的实测"当前视口目标层就绪"中位数是
`198.9–294.3 ms`，**这本身算不上"明显过长"**。真正把体验推到用户所说的
"明显过长"的是两件事：**（a）** 校正通道**第一次出现**要等 8.29 s 的完整粗层；
**（b）** 演示的多通道叠加把每次冷空降推到 `425–557 ms`、GUI 最长无响应
`288–430 ms`。下面逐项给出数据。

## 2. 冷 Patch 与冷 Tissue 是否共用路径：**是**

**源码上：** 两个公开入口在第二跳就合流，之后完全同一条路径。

```
mount.show_patch(bbox)        mount.jump_to_point(y, x, size)
        │                                   │
        └──► Step1ViewerBinding.show_patch  └──► ...jump_to_point
                    │                                   │
                    └───────────► host.jump_to(y0,x0,w,h) ◄──┘
                                        │
                        stack.controller.jump_to()  (viewer/explore_view.py)
                                        │
                                  _move_camera()
                          ├─ ViewBox.setRange(rect, padding=0)
                          ├─ _motion_timer.stop()
                          ├─ _issue_raw_requests()      ← 旧管线在这里发请求
                          ├─ _emit_interaction("NAVIGATOR_JUMP")  ← binding 在这里规划
                          └─ _settle_timer.start()
```

`Step1GpuBinding._interaction_event()` 收到 `NAVIGATOR_JUMP` 后立即
`update_viewport()`（停掉仍在跑的 motion timer，G3.2a.4 的行为）。两条入口
唯一的差别是传进去的矩形。

**实测上：** 同一通道下，冷 Patch 与冷 Tissue 的目标层、目标瓦片数、请求来源
构成、读取条数、上传数、submit 数**逐项同形**（见 §3 表）。**§二.1 的问题
回答为"是"。**

## 4. 时间到底花在哪一段

### 4.1 首次启用一个通道：**校正归约是绝对主导**

`complete coarse` = 该通道最粗层（L3，`304×340`，tile 512 → **1 块**）的完整
事务。它是一个通道"第一次出现"的前置条件。

| 通道 | 来源 | 完整粗层墙钟 | 该阶段 worker 读取累计 |
| --- | --- | ---: | ---: |
| `CD8` | raw | **0.03 ms** | 138.6 ms |
| `CD22` | corrected (cuCIM) | **8 293.56 ms** | 38 932.7 ms |
| `CD22+CD4+PD1+FOXP3` | 四个 corrected | **31 936.37 ms** | 247 800.9 ms |

原因在 `viewer/step1_source.py` 的设计里写得很清楚，也确实正确：
**校正产物没有金字塔**，只有一张 ROI 形状的 level-0 数组。所以 L3 的那一块
粗层瓦片必须把**整张 1.70 GB 的校正数组**按 `stride = 64` 归约一遍
（`reduce_corrected`，`4 Mi` 元素一片，共约 100 片）。raw 通道则直接读金字塔
自己的 L3，一次 `304×340` 的读取——这就是 0.03 ms 与 8.29 s 的差别来源。

只读复测（单线程，页缓存已热）：

| 操作 | 实测 |
| --- | ---: |
| `reduce_corrected(整片, stride=64)` | **4.51 s**（进程冷时 7.95 s） |
| 同样结果改用 reshape 分块求和 | **1.30 s**，`valid` 完全一致，`max|Δ| = 7.63e-06` |
| `reduce_corrected(512² L0 瓦片, stride=1)` | `15.4 / 7.0 / 10.6 ms` |
| 同一块只做 `region.read()` | `2.7 / 1.2 / 1.2 ms` |

也就是说：**stride=1 的校正 fine 瓦片走了一条它根本不需要的归约路径**
（`np.add.at` 逐像素散射累加），成本是直接切片的约 **6 倍**；而完整粗层用
`np.add.at` 比等价的 reshape 分块求和慢约 **3.5 倍**。两处都在
`viewer/step1_source.py`——**本块只读文件**。

### 4.2 一次冷空降：等待几乎全在"排队 + 读取"

- 输入事件 → binding 发出第一个 RawKey 请求：**18.0–21.7 ms**（含公开调用
  本身），不是瓶颈。
- **binding 自己的目标层瓦片在共享队列里的排队时间中位数**：单通道
  `10.8–33.8 ms`，**四通道 96.7–219.5 ms**。四通道下 8 个 worker 要吞
  `48 个 binding 瓦片 + 20–24 个不可见的旧瓦片`，排队直接变成主导项。
- GPU submit `33.1–51.3 ms`、首次纹理上传 `57.2–274.2 ms`、GUI 最长无响应
  `99.6–430.3 ms`。**GUI 线程没有执行任何 provider 读取或归约**——读取全部
  发生在 worker 线程（ledger 记录了每条读取的线程名，无一在主线程）。
- **descriptor 首次完整可发布 = 目标层全部就绪**：这是 G3.2b/G3.2b.1 的
  "首次出现即清晰"契约，本块未改动，实测 `late = 0`（无迟到结果上屏）。

## 5. 重复工作：有，而且不小——但不是 binding 造成的

### 5.1 binding 侧：**零重复**

一次冷空降内：`12 请求 → 12 唯一 RawKey → 12 次真实读取 → 12 次上传`。
`duplicate_real_reads_of_one_key = {}`（五次 Patch、五次 Tissue、两种来源、
三种配置，全部为空）。**同一 RawKey 在一次动作里最多被真实读取一次**，
scheduler 的单飞去重生效。

### 5.2 旧 `ExploreController` 侧：**每次空降 20–24 个永远不上屏的 RawKey**

GPU 接管时，`ui/step1_viewer_mount.py::_start_gpu_backend()` 调用
`stack.controller.set_marker_visible(False)`。该方法的文档写明它是
**"Visibility only"**——它把旧图层的不透明度设为 0，**但不取消任何请求，也不
改变共享 controller 的行为**。于是每一次 `_move_camera()` 仍然照常执行
`_issue_raw_requests()`，发出：

| 旧管线发出的东西 | 优先级 | 在 Step1 是否真的发出 | 像素能否上屏 |
| --- | ---: | --- | --- |
| level+1 **underlay**（`_issue_raw_underlay`） | `0 + i` | **是**（`method is None` → `_wants_precise()` 假 → `_raw_layer_visible()` 真） | **否**（opacity 0） |
| 当前层可见批 | `200 + i` | 是 | 否（但 RawKey 与 binding 的 fine **相同**，被单飞去重，不算浪费） |
| **prefetch ring**（1 圈，`RAW_PREFETCH_RING_TILES = 1`） | `700 + i` | **是** | **否** |
| precise/corrected 批（`_issue_settled_request`） | — | **否**（`method is None`，空转） | — |
| directional prefetch | — | **否**（需要 `_wants_precise()`） | — |

实测每次冷空降，**旧 controller 发出 32–40 个请求，其中 20–24 个是 binding
从未请求过的 RawKey**（underlay 在 L1，ring 在 L0）。它们是**真实读取**：

| 配置 | 一次冷空降 provider 读取 | 其中只为旧图层读的 | 占比 |
| --- | ---: | ---: | ---: |
| CD22 单通道 | 32–40 | **20–24** | **≈62 %** |
| CD8 单通道 | 32–40 | **20–24** | **≈62 %** |
| 四个 cuCIM 通道 | 68–88 | **20–24** | **≈29 %** |

在校正通道上这尤其贵：underlay 在 L1（`stride = 4`），一块 512² 瓦片要归约
`2048²` 个 level-0 像素——实测单块最高 `113–202 ms`，正是每次动作里最慢的
那几条读取。

**这是已证实的、确定无用的浪费。** 但消除它必须停掉旧 controller 的请求流，
而这条流在 `viewer/explore_view.py`（四个页面共用）。

## 6. 目标层 fine 是否被无理由地延后

- **优先级本身基本正确：** binding 的 fine 在没有 coarse 在途时是
  `PRIORITY_FINE_FOREGROUND = 0`；旧管线的可见批 `200+`、ring `700+` 都排在
  它后面。唯一能插到前面的是 underlay 的**第一块**（`RAW_UNDERLAY_BASE_PRIORITY = 0`，
  且 `_issue_raw_requests()` 在 `_emit_interaction("NAVIGATOR_JUMP")` **之前**
  执行，所以它在同一优先级档里先进先出地占到前面）；underlay 的第 2 块起是
  `1, 2, 3…`，已经排在 binding 的 fine 之后。
- **真正的延后不是优先级，是吞吐：** 8 个 I/O worker 被"binding 需要的瓦片 +
  20–24 块不可见瓦片"同时占满，binding 自己的目标层瓦片排队中位数因此从
  单通道的 `10.8–33.8 ms` 涨到四通道的 `96.7–219.5 ms`。
- **公平策略没有问题：** `fine_requests_by_priority` 显示冷空降时 fine 全部
  走 `0`（前台档），没有被 G2.1 的 coarse 让路规则误降级；`fine_budget_refused`
  全程为空；`late = 0`。

## 7. 白名单内能不能修：**不能**（按 §九 停止）

### 7.1 binding / mount 内已无实质浪费可消除

按 §七 的优先级逐条核对：

| # | 方向 | 结论 |
| --- | --- | --- |
| 1 | 同一公开动作内的重复请求/读取/归约/上传 | **不存在**（12→12→12→12，重复读取字典恒为空） |
| 2 | binding 自己造成的串行等待 | **已在 G3.2b 消除**；本块实测首个 binding 请求在 18–22 ms，fine 不再等 coarse |
| 3 | 复用已驻留的 raw / GPU 数据 | **已是最优**：真热返回 0 读取 / 0 上传 / 1 submit |
| 4 | 调整本 binding 既有请求的时机或 priority | 可做，但**收益是次要的且不解决主因**——见下 |
| 5 | 主瓶颈在共享 scheduler / provider / corrected reduction | **成立 → 停止** |

关于方向 4：理论上可以把 binding 的目标层 fine 改成一个负的优先级数字，让它
一定排在 underlay 第一块之前。但这**只挪动了一块瓦片的次序，没有消除任何一次
读取**：20–24 块不可见瓦片照样要跑完、照样占满 worker。按本块 §七 末句
"不得为了'有改动'而做微优化"，**不做**。

### 7.2 为什么现成的公开接口不能用

`ExploreController.suspend_for_production(reason, ...)` 确实能让
`_issue_raw_requests()` 一行不发（`if ... or self._suspended: return`），而且
是公开方法。但它**同时**做三件在本块明确禁止的事：

1. `self.view.view_box.setMouseEnabled(False, False)` —— **锁相机**，直接摧毁
   已验收的连续平移/缩放（保护门 2、3、9）。
2. `self.view.set_status_text(self._suspend_badge_text())` —— 写一条可见状态

## 9. 最小追加授权方案（**本轮未实现，等待用户裁定**）

按"用户可见收益 ÷ 风险"排序。

### 方案 A（收益最大）：校正粗层归约改用等价的分块求和

- **改哪里：** `viewer/step1_source.py::reduce_corrected()` 的内层累加，
  把 `np.add.at(sums.ravel(), flat, ...)` 换成对齐到全局网格后的
  `reshape(bh, stride, bw, stride).sum(axis=(1,3))`。**公式不变、网格锚点
  不变、有效样本归一化不变**。
- **已实测收益：** 整片 stride=64 归约 `4.51 s → 1.30 s`（**-71 %**）；
  `valid` 掩码逐元素一致，`max|Δ| = 7.63e-06`（float32 舍入，非公式改变）。
  四通道首次启用由 `31.9 s` 降到约 `9 s` 量级。
- **风险：** 中等——它是 Step1 显示与 CPU C1 参考共用的科学归约。必须
  逐像素比对全部现有 coarse 门，并确认 `≤1 LSB`。
- **回滚：** 单函数内一段，逐笔可撤销。

### 方案 B：`stride == 1` 时不做归约

- **改哪里：** `viewer/step1_source.py::read_tile()` 的 corrected 分支，
  `stride == 1` 时直接用 `region.read(...)` 的结果与有效掩码，不进
  `reduce_corrected`。`stride == 1` 的"块平均"在数学上就是原像素。
- **已实测收益：** 每块 L0 校正 fine 瓦片 `7–15 ms → 1.2–2.7 ms`（约 **-80 %**）。
  冷空降里每通道 12–16 块都吃这个收益。
- **风险：** 低——`stride == 1` 时 `box_downsample_valid` 本来就已经短路返回
  原值，这只是把 corrected 分支对齐到同一条既有语义。
- **回滚：** 一个 `if`。

### 方案 C：GPU 接管期间停掉旧 controller 的**不可见**请求流

- **改哪里：** `viewer/explore_view.py`，给 `_issue_raw_requests()` 增加一个
  与 `set_marker_visible(False)` 配对的"不可见就不发"判据，或增加一个只读
  开关由 `ui/step1_viewer_mount.py::_start_gpu_backend()` 在现有那一行旁边
  打开（`_stop_gpu_backend()` 关上）。**不锁相机、不写状态文字、不 join 任何
  线程**——这正是不能直接用 `suspend_for_production()` 的三点。
- **预期收益：** 每次冷空降少 20–24 次真实读取（单通道约 **-62 %** 的读取量，
  四通道约 **-29 %**），并把 binding 目标层瓦片的排队中位数从 `96.7–219.5 ms`
  往下压。**未实测**——本块没有实现它，所以这是**推算不是结论**。
- **风险：** 较高——`viewer/explore_view.py` 是 Step0 全图、compare 面板、
  Step1 共用的模块。必须保证回到旧渲染器（`_stop_gpu_backend()` 之后、
  CPU fallback、Step0 页面）时请求流原样恢复。
- **回滚：** 一个布尔开关加一处判据。

**三条都超出本块白名单，未实现。**

## 12. blocker 与 advisory

**blocker（需用户裁定，本轮未修）：**

1. **校正来源的完整粗层要 8.29 s / 通道**（四通道 31.94 s），raw 同位置
   0.03 ms。这是"首次启用通道 / 首次进入准备过慢"的**主因**，位于
   `viewer/step1_source.py::reduce_corrected`。方案见 §9.A / §9.B。
2. **GPU 接管期间旧 `ExploreController` 每次空降仍发起 20–24 次永远不上屏的
   真实读取**（单通道占全部读取的 62 %），位于
   `viewer/explore_view.py::_issue_raw_requests`。方案见 §9.C。

**advisory：**

1. `Step1GpuBinding._descriptor_history` 仍无上限增长（G3.2b 已记，本块复现：
   四通道十次空降后 `descriptor_publications` 已达数百）。长会话内存增长源。
2. `RAW_CACHE_BYTES = 512 MiB` 在四个校正通道下**不足以跨十次空降保住一个
   patch**（§3.3 的 `hot-P1-1`）。演示若要保证"回到看过的 patch 立刻出现"，
   需要用户裁定是否调整该预算——**本块未调**。
3. 旧管线的 underlay 优先级 `RAW_UNDERLAY_BASE_PRIORITY = 0` 与 binding 的
   `PRIORITY_FINE_FOREGROUND = 0` 同档，且 underlay 先入队，所以 underlay 的
   第一块总是抢在目标层之前。只影响一块，未据此改动。

**本块没有发现任何需要扩写威胁模型的内容；上述两条 blocker 都是正常公开
产品路径可复现的性能缺陷。**
