## 1. 现状和原因（已核对）
- 数据来自 R4 第 2 轮（`bench_a9/tiles_q4w_2.jsonl`），以最后一次注入为 0：

  | 时刻 | 视野 | 要的块 / 已在显存的块 |
  |---|---|---|
  | +1.1 ms | 倒数第二格的视野 | 240 / 138 |
  | +12.7 ms | 最终视野 | 180 / 126 |
  | +82.1 ms | 最终视野 | 180 / 180 |

  - 最终画面在 +83.6 ms 上屏；
  - 注入后上屏的几帧传的块数依次是 16、17、17、16、18、3，第一帧在注入前 1.6 ms 开始，还属于上一格的视野；
  - 程序收到最后一格比注入晚约 6.7 ms（5 轮 2.5–10.9 ms）。
- 读图不是瓶颈：5 轮的最后一块都在停手前 12.2–14.3 ms 读完。
- 限制主要来自一条规则：程序收到输入后 60 ms 内，每帧上传的截止时间是"开始上传后 1.5 ms"。
  - 代码位置：`ui/step1_core_binding.py` 的 `INPUT_HOT_S = 0.060`、`HOT_UPLOAD_MS = 1.5`，传给核心。`frame.rs` 的 `paint` 用 `input_hot()` 判断；
  - 不热时，截止时间是"这一帧开始后 12 ms"（`FRAME_BUDGET_MS`）。
- 截止时间只管普通的块，而且是在每传一块之前检查：
  - 粗层的完整替身（mandatory）不受截止限制，也能越过一般的扩容等待；
  - 页表同步、合成，以及标签自己的 3 ms 额度，都在上传之后。

  所以"12 ms"不是一帧耗时的上限，只是普通块上传的截止时间。
- 重绘节奏也是一个因素：
  - 一帧还有没传完的块时，用一个 16 ms 的单次定时器请求下一帧（`ui/step1_core_layer.py` 第 270 行），然后再经过事件循环和上屏；
  - 实测停手后约每 20 ms 开始一次绘制（第 2 轮绘制开始于 +10、22、41、60、81 ms，这是开始时刻，不是上屏时刻）；
  - 改上传预算不会让下一帧来得更早。
- 连续放大每 30 ms 一格，共 10 格。所以从第一格到程序处理完最后一格后 60 ms，整个过程都按 1.5 ms 走。
- 1.5 ms 这个数是 R1 从 Python 版本照搬的。§45 第 1 步曾批准另一套：
  - 预算按状态分："最近一帧内有输入"约 4 ms，"没有待处理输入"约 12 ms，热窗口缩到一帧；
  - 那是接收、规划、扫描、上传、页表同步共用的预算，没有带进 Rust 核心。

  R5 只借用其中的数值，只用在上传截止上，不是恢复整套方案。
- 一块上传约 0.04–0.09 ms（R4 日志：1.5 ms 内传 17–35 块）。
- 估算（待测，不是保证）：如果停手后约 20 ms 就不再"热"，剩下的约 50 块大概在停手后第二、三帧（约 +40 ms）传完。
- 同一个"热"判断还管预留显存块（`top_up` 在热的时候不预留）。每块第一次使用要让界面停 55–64 ms（§48）。如果这条也跟着缩短，放大两格之间（30 ms）就可能预留一块，造成手势中卡顿。

## 2. 改法
1. **把"上传热窗口"和"输入热窗口"分开**（Rust）：
   - `Config`（`viewer.rs`）新增 `upload_hot_s`。`viewer.rs` 加一个 `upload_hot()`。`frame.rs` 的上传截止时间改用它；
   - `input_hot()`（60 ms）照旧只管 `top_up` 预留显存块；
   - 扩容条件 `growth_quiet_s`（0.3 s）和粗层替身的例外都不变；
   - `py/config.rs`：配置里没有 `upload_hot_s` 时，取 `input_hot_s`，行为和现在完全一样；
   - 判断"现在热不热"和"截止时间是多少"写成不依赖 GL 的小函数，便于测试。
2. **Python 绑定**（`ui/step1_core_binding.py`）：
   - 新常量 `UPLOAD_HOT_S`，传给核心；
   - 只在测量时用的两个开关（同 §43 的调参开关先例），都用毫秒写：
     - `BLOCK01_A9_RUST_UPLOAD_HOT_MS`：上传热窗口，换成秒写入 `upload_hot_s`；
     - `BLOCK01_A9_RUST_HOT_UPLOAD_MS`：热时每帧上传，保持毫秒写入 `hot_upload_ms`（核心按毫秒读）；
   - 绑定建核心时，把实际用的 `upload_hot_s`、`input_hot_s`、`hot_upload_ms`、`frame_budget_ms` 记一条测量日志（`rust.config`），用来核对测到的是哪套数值；
   - 本计划获批后，按 §4 第 1 条的初选结果改默认值，不另等批准；初选结果会先报告给用户。
3. **候选设置**：

   | 候选 | 上传热窗口 | 热时每帧上传 | 影响 |
   |---|---|---|---|
   | A（现在） | 60 ms | 1.5 ms | 对照 |
   | B | 20 ms | 1.5 ms | 程序收到输入超过 20 ms 后就用 12 ms 截止。停手后会提前；放大、缩小两格之间（30 ms）的后一帧可能也会 |
   | D | 60 ms | 4 ms | 收到输入后 60 ms 内每帧多传。手势中和停手后 60 ms 内都受影响 |
   | C | 20 ms | 4 ms | B 和 D 合起来，借用 §45 的数值 |

   - 20 ms 比一帧（16.7 ms）稍长。上传热窗口和输入热窗口都从程序处理输入的时刻算起，不是从注入算起。连续拖动（每 8 ms 一次输入）始终是"热"；放大、缩小（每 30 ms 一格）两格之间可能有一帧"不热"，要看处理延迟和重绘时机，不保证每个间隔都有；
   - 优先顺序 B、D、C：
     - B 只在已经没有新输入的帧上多传，不加重手势中每一帧，对手势中响应的影响面最小；
     - D 加重手势中的每一帧；
     - C 两者都改。
4. **不做的**：
   - 改上传顺序（现在粗层替身先传，细层按绘制顺序）；
   - 改重绘节奏（16 ms 定时器）；
   - 预读相邻层、改读线程、改显存分配；
   - 改 Python 后备路径（`step1_gpu_binding.py`）；
   - 标签的上传额度（3 ms，§53）。

   测完如果发现剩下的差距在这些地方，只报告，不扩大范围。

## 3. 风险
1. 不再"热"的帧，普通块可以一直传到这一帧开始后 12 ms。之后还有页表同步、合成、标签工作，这一帧没有固定上限。下一格的响应可能变慢，靠测量看响应的 95% 线、最长和超过 50 ms 的次数。
2. 每次绘制的 95% 线会变长，69 通道更明显。列出变化。
3. 显存预留的时机不变（仍按 60 ms 的输入热窗口），但不能保证没有扩容等待：
   - 粗层替身的例外和 0.3 s 的扩容条件都还在；
   - 预算变大不能解决"没有空位"的等待。

   测量里要分开两种原因：
   - 等扩容：`deferred_growth`，以及 `gpu.grow` 出现的时刻；
   - 预算用完：只对没有 `capacity_exceeded`、没有 `error` 的帧，用 `deferred` 减去 `deferred_growth`。只用于本次没有标签的 Step1 测量；Step3 的 `deferred` 还包含标签的延后，按标签冒烟的结果单独解释；
   - 有容量不足或出错的帧单列，按产品结果保留。

   现在的 `gpu.frame` 测量日志没有 `deferred_growth` 和 `capacity_exceeded`。要在 `ui/step1_core_layer.py` 的这条日志里补上这两项（只加日志字段，不改行为）。
4. 标签：上传额度独立（3 ms），不改。但同一帧里通道块传得多，帧会变长，所以冒烟要看空档和每帧工作。
5. Python 后备路径：不改。确认测量里出现后备，按产品结果计入。
