# v16_5 R6 调查计划：拖动全过程清晰度（第五版：第四版已批准；§12 补充 codex 三轮审核通过，待用户批准）

只调查、只量，不改产品的行为。改法等调查结果出来，另写计划。

## 0. 背景和用户的决定（2026-10-13）
- R5（81046c5）之后，用户在 TMA4 上人工验收：
  - 快速拖动时，视野边缘明显"先糊后清"；
  - 从缩略图点到远处、落地后马上拖，最明显；
  - 整体观感仍然远不如 Odon。
- 和 codex 讨论的结论：
  - 现有的及格标准只量"开始动多快"和"停手后多快稳定"，不量"手还在动时画面是什么样"，所以纸面领先不代表观感领先。
  - 程序的工作方式能解释"先糊后清"：
    - 缺的图块先用粗图或保留的旧图顶上，等清晰图块到了再替换；
    - 没有视野外的预读圈，也不按拖动方向预读；
    - 请求是从视野中心往外排的，替补时会保留更清楚的旧图，但都受预算限制。
  - Odon 为什么看起来好，目前没有证据。
  - 日志里的 `exact_fraction` 是按图块个数算的比例，不是屏幕面积。
- 用户的决定：
  1. 代表性设置：TMA4，开 5 个通道 CD45RO、KI-67、Vimentin、TROP2、CD8；
  2. 最在意的是"全过程始终清晰，尽量消灭糊变清的跳变"，和 smooth 模式无关；
  3. 用同一份 OME-TIFF 和 Odon 公平对比：`/sdb1/cop/Kevin/test4/FINALRUN_updated_TMA4_Scan1_bgcorrected.ome.tiff`。
     qptiff 的对比留到以后另做。

## 1. 要回答的问题
1. 两个场景里，从操作开始到停手后稳定，我们和 Odon 在每个阶段各有：
   - 多大面积、多长时间没到最终样子；
   - 多少次"糊变清"的跳变，每次多大、多突然；
   - 画面跟手的程度：显示的位置落后手多少。
2. 如果我们比 Odon 差，差在哪一环。每块可以归到一类，也可以是"混合"或"未知"：
   - 图块还没读出来；
   - 读出来了，但没传上显卡（每帧上传预算）；
   - 传上去了，但这一帧没画它；
   - 出帧本身断了；
   - 顶替选得不好：明明有更清楚的旧图，却用了更粗的。
3. 从 Odon 画面上能看到的表现：
   - 等待时显示的是粗图、空白，还是保留的旧图；
   - 新露出来的边缘是不是已经清楚。
   - 截图分不清它是预读、缓存，还是读得快，所以这些只作为观察和猜测，不当结论。

## 2. 固定的设置（两个应用相同）
- **画布**：两个应用都用 1307×788 的画布，同现有测量工具（`a9_odon_bench.py` 的 CANVAS）。窗口位置固定。
- **放大倍数**：用"每个原图像素占几个屏幕像素"来定，两个应用设成一样，每轮开始前从相机读回来核对。用户 2026-10-14 定了两档，所有场景两档都做：
  - **常用档 1.315**：用户当时开着的 block01 界面的倍数。界面没有显示倍数的地方，是把那张截图和原图的 KI-67 通道配准量出来的（吻合度 0.956，中心在原图 (18130, 12304)）。
  - **最大档 2.0**：比常用档再放大约 1.5 倍。界面没有放大上限，"最清晰的那一级"取这个值。
  - 两档用的都是原图最细一级的数据，区别只是每个图块在屏幕上占多大、拖同样距离要换多少图块。
- **通道**：
  - 5 个通道按名字指定，记下各自在文件里的序号；
  - 显示范围都是 0–255 线性；
  - 颜色尽量设成一样，记下两边实际的颜色、权重和叠加方式。
  - 我们的程序关掉 smooth 模式。
- 两个应用只是像素值一样，显示效果做不到完全一样，所以每个应用只和自己的最终画面比，不跨应用比像素。

## 3. 场景
- **起点和目标**：事先在组织上选好，写进场景文件。每轮用不同但固定的一组，两个应用用同一组。路径上要有组织细节，不在空白区。
- **S1 快速连续拖动**：
  - 一次"划"：在画布内按下，以固定速度划 900 像素，在终点松开；然后不按键把鼠标移回起点，停 50 ms 再划下一次。
  - 连续划 4 次，方向相同，图像一路往没看过的区域走。
  - 这和"一口气连续拖 2 秒"不一样：两次划之间有回手的空档，程序可以趁机补图。报告里把"划动中"和"回手"两个阶段分开算。
  - 跟手的落后量，按"按下状态下累计移动的距离"算，不按回手后鼠标的绝对位置算。
  - 三种速度：每 8 ms 移动 10、20、40 像素，即每秒 1250、2500、5000 像素。
  - 现有注入程序松开前会把鼠标移回原处，所以要加一种新的"划"动作：在终点松开、不按键移回。
  - 每次都核对：实际移动的距离、时间、松开的位置；相机实际走了多远（从两个应用的相机读数或截图配准得到）。
- **S2 跳到远处后马上拖**：
  - 我们这边：点全片缩略图上的目标位置。
  - Odon：如果有可以点的概览图，就点它。没有的话用控制接口 `set_camera` 直接跳，结果标明"替代操作，不等同于界面操作"。
  - 开始划的时刻：两个应用都在发出跳转操作（点击或控制命令）后固定 100 ms 开始划，不等画面变清楚。
  - 三个时刻都记下来，两个应用用同样的方法：
    1. 发出跳转的时刻（注入记录，或控制命令发出的时刻）；
    2. 应用确认的时刻（我们是日志，Odon 用控制命令跳转时是接口返回；Odon 用点击概览图时没有这个时刻，记为"无"。只作参考，两者不等价）；
    3. 画面真正到达目标位置的时刻：事后从截图配准得到，两个应用一样算。
  - "落地到开始划"的实际间隔按第 3 个时刻算出来报告。如果画面还没到目标位置就开始划了，单独标出来。
  - 划 2 次，速度每秒 2500 像素。
- **冷读和热读**：
  - 冷读：清掉图像文件的系统页缓存，重启应用，不预热，直接做场景。
  - 预热重放（原来叫"热读"）：同一个应用进程里，先把同一条路径慢慢走一遍。每到一格都停住，等到加载完成（判定方法同参考图）。然后回到起点，再正式做一遍。
    - 走一遍不能保证所有图块都还留在内存和显卡里，所以不叫"全热"。
    - 能拿到的驻留证据要报告：我们这边用显卡里的图块数和缓存命中，Odon 没有这类数据就写"无"。
  - 所以"没看过的区域"只在冷读里成立。预热重放量的是"都走过了，还会不会糊"。
- **轮数**：每个应用每种条件 3 轮，两个应用交替跑。先跑一次试点，再定最终的时间估计。

## 4. 新尺子：手还在动时，画面离最终样子差多少
- **截图**：
  - 从操作开始前 0.5 s，一直截到停手后 2.5 s（和现有的停手观察窗口一样），对画布整块连续截图，每张记时间。
  - 先存进内存，事后再分析。按每秒 60 张、1307×788 算，大约每秒 250 MB，所以每轮存完马上写盘，再开始下一轮。
  - 截图节奏在第 0 步定死，正式测量不再改：
    - 目标是每秒 60 张；
    - 间隔超过 25 ms 的不超过 5%，最长间隔不超过 50 ms；
    - 截图带来的开销：Odon 没有出帧记录可读，所以两个应用都用同一个旁观指标：现有的细条截图工具（`a9_pixwatch.py`）看到的画面更新间隔。
      分别在开着整屏截图和不开时各量一次，95% 线多出的部分不超过 2 ms，两个应用都要满足。
      细条工具本身也是截图，也有一点开销；它只能看到画面变化，看不到真正的出帧，这些写进限制。
    - 达不到就停下来报告，不自己降低频率。降频会改变能分辨的最短时间，要和用户、codex 重新商量。
    - 能分辨的最短时间就是截图间隔，比它更快的跳变看不出来，写进限制。
  - 画面没变的截图也保留，用来算"冻住"的时间。
  - 截图里画面变化的间隔，代表"能看到的更新"，不等于屏幕真正的刷新间隔，写进限制。
- **参考图**：
  - 用另一个应用进程，在同样的设置下，沿整条路径一格一格移动。每格要同时满足两条才截图：
    - 应用说加载完了：我们这边是日志里目标级覆盖完整、没有未完成的请求；Odon 用控制接口 `get_loading_state` 报告空闲；
    - 画面不再变化：连续 1 s 截图不变。
  - 最多等 15 s，超时的格子作废重截，重截 2 次还不行，这一块区域不评分，并在报告里列出。
  - 截好的格子拼成一张大参考图。
  - 相邻格子至少重叠 25%，重叠区检查接缝：两张在重叠区的差异要很小，不然这一格重截。
  - 每个应用用自己的参考图。做完参考图后关掉应用、清页缓存，再做正式测量。
  - 参考图本身的清晰度也要报告：例如两个应用参考图的细节能量各是多少。自己和自己比只能说明"有没有到最终样子"，不能说明最终样子本身清不清楚。
- **定位**：每张截图在参考图里的位置，用图像配准求出，只求平移，精确到小于一个像素。
  - 用的是这一帧实际显示的位置，画面跟得慢不会被误算成"糊"。
  - 但画面跟得慢本身也要单独报告：显示位置和手的位置差多少，以及画面冻住的时间。这样冻住的清晰画面不会被当成好表现。
  - 配准不可信的帧：匹配分数低，或者和相邻帧的位置跳得不合理，记为"无法定位"。
    - 这可能是工具的问题，也可能是产品画面本身太糊或太空，所以不因此重跑。
    - 报告它们的时间占比，并给出一个上下界：把它们全部当"不合格"算一次，全部当"合格"算一次。
    - 如果两个应用的上下界有重叠，足以改变"谁更好"的结论，这一项就记"无法判定"。
- **哪些块要评分**：只看参考图，把有组织细节的块标出来。参考图上就是空白的块不评分，两个应用用同样的规则。
  - 移动中的截图如果在这些块上是空白、全黑或者饱和，算"不合格"，不剔除。
- **逐块比较**：把截图分成 32×32 像素的小块，和参考图同一位置比。
  - 指标用细节能量比（截图和参考图的高频能量之比）加结构相似度。
  - "不合格"的门槛在第 0 步定，见 §6。
- **"糊变清"跳变的定义**：
  - 按组织坐标跟踪每一块，不按屏幕坐标。
  - 跳变：这一块的质量在相邻两张截图之间突然变好，提升量超过一个门槛。
    - 门槛在第 0 步定，并且有一个下限：细节能量比至少提升 0.2，不能因为静止时抖动为零就把门槛定成零。
    - 相邻两张截图间隔超过 25 ms 时，中间可能有看不到的逐步变化，这种只算"可能的跳变"，和确定的跳变分开报告。
      跳变次数给出上下界：只算确定的为下界，加上可能的为上界。
    - 慢慢变好、在门槛附近来回抖，都不算。
  - 同一次画面更新里，相邻的跳变块合并成一个跳变事件。
  - 每个事件报告：质量提升了多少、面积多大、跳变前糊了多久。
  - 还没变清楚就移出视野的块，单独计数，不算"后来变清楚了"。
  - 到观察窗口结束（停手后 2.5 s）还没变清楚的块，也单独计数，记为"到最后仍然糊"。
- **报告的数字**（按场景、速度、冷热、阶段分开）：
  1. 有效面积占比，以及"无法定位"的时间占比；
  2. 时间加权的"不合格"面积比例；
  3. 最差一帧的比例，并把最差那一帧存下来；
  4. 跳变事件：次数、面积、提升幅度；
  5. 新露出来的边缘：每一帧新进入视野的那一条，多久变清楚；还没变清楚就移出视野的单独计数；
  6. 跟手：显示位置落后多少，画面冻住了多久；
  7. 截图里画面的更新间隔。
- **附带**：每个条件选一轮，把两个应用的截图并排做成短片，再画"质量随时间变化"的曲线，标出跳变，方便用户直接看。

## 5. 我们这边的原因对应
- 现有日志只能看到按图块个数的覆盖率和上传记录，看不出屏幕上每一块是用哪个图块画的。所以要加诊断日志。
- 请求、读取、读完这几个阶段在 Rust 核心里，已经有 `trace.rs` 的阶段记录（req / start / read / done / recv / gpu、cov / present / paint），Python 只是把它们导出。这次沿用它，只补两样：
  1. 每帧和"上屏"的对应：这一帧的编号、相机位置、对应哪一次上屏；
  2. 每个格子实际用了哪个图块：每个通道、每个格子用的是目标级还是顶替，顶替用的是哪一级，当时有没有更清楚的旧图可用。
- 只加日志，不改行为，默认关闭，只在测量时打开。新代码放一个小模块，不超过约 300 行。
- 日志本身的开销要量：开和不开各跑一次同样的场景，比较出帧和截图得分。差别明显的话，归因只用开日志的那几轮，并且在报告里说明。
- 归因：拿截图里"不合格"的块，对到同一时刻、同一位置的格子状态，归到 §1 第 2 问的类别里。
  - 一个 32×32 的块可能跨几个格子和几个通道，可以记"混合"。对不上的记"未知"。
- 两个已有机制，单独回答为什么没挡住跳变：
  - 从中心往外排序的请求；
  - 保留更清楚的旧图。

## 6. 第 0 步：工具验证（先做，不过关就不进正式测量）
1. 确认 Odon 能不能用 5 通道、0–255、指定颜色打开；有没有可以点的概览图；`set_camera` 能不能把放大倍数设成和我们一样。
2. 新的"划"动作：在两个应用上各试一次，核对实际距离、时间、松开位置、相机走的距离。
3. 截图：测间隔和开销，达到 §4 的要求。
4. 参考图：
   - 拼接后接缝检查通过；
   - 在参考图范围内随机取 20 个停稳的位置截图，配准误差小于 0.5 像素。
   - 配准还要在模糊的截图和只加载了一部分的截图上测：用两个应用真实的过渡帧，人工核对 20 张的位置。
5. 门槛标定。位置分两组：一组用来定门槛，另一组用来验证，两组都不参加正式测量。
   - 停稳的画面：不合格面积不超过 2%。
   - 移动中配准和重采样带来的误差，用两种方法量，不依赖"预热后一定都在内存里"：
     1. 合成移动：从参考图上按 S1 的速度、带小数像素的位置连续截取，做成一串假的移动画面。这时不合格面积不超过 5%，跳变事件接近 0。
     2. 我们的程序上，再找一段确实全部驻留的真实移动：日志证明这段时间里没有新的请求、读取和上传，用它复核同样的标准。Odon 没有这类证据，只用第 1 种。
   - 人为制造、两个应用一样的退化：把各自参考图截下来的画面缩小 2 倍、4 倍再放大，检出率至少 80%。
   - 慢慢变清楚：用两张图按比例渐变混合，做成一串画面，不能被算成跳变。
   - 真实的过渡帧：两个应用都用冷读刚跳过去的真实画面，人工在 20 张上标出糊的区域，和工具的判断对比，报告一致率。
   - 我们的程序没有现成的"强制显示粗一级"功能，这次也不加，只用上面这几种。
   - 达不到就调指标，调完在验证组上再测一次，把最终参数写进报告。
6. Rust 诊断日志的开销测一次。
7. 试点：两个应用各跑 S1 中速冷读和 S2 冷读各一次，走完全部分析流程，然后重新估时间。
8. 第 0 步的结果和最终参数交 codex 核对，通过后才开始正式测量。

## 7. 规则（沿用 R4、R5）
- 第二块屏幕 VGA-2-1 在测量期间关掉，测完恢复；不和其他界面测试同时跑。
- 冷读每次启动前清页缓存。
- 只有测量方面的证据才重跑：截图间隔不达标、注入出错或位置不对、屏幕检查没过、参考图作废。最多 3 次重跑，失败的那次保留。
- "无法定位"的帧多，不算测量失败，不重跑，按 §4 的上下界处理。
- 程序出错、退回 Python 路径，都算产品结果，不重跑。
- 正式测量开始后，不改尺子的任何参数。

### 12.4 B 组：去第 3 步再回来，然后拖（只量我们）
- 用 A 组的 S1 路线。总共 4 次划，每次 900 像素，每秒 2500 像素。前 2 次叫"前段"，后 2 次叫"后段"。

- **S3a（第 3 步回原处）**
  - 开始前先在第 1 步把整条路线预热一遍，再回到起点停稳。
  - 切到第 3 步，在第 3 步里先向右划 1 次，再向左划 1 次（相机应回原处），停 3 s。
  - 切回第 1 步，停 1 s，然后做 4 次划动。
  - 核对：回来时第 1 步的中心、倍数、画面位置和离开前一致，差多少都记下。
  - 对照 S3a-ctl：同一个进程状态，同样的预热，但那两次来回划在第 1 步里做，等待时间相同（停 3 s，加上相当于切换步骤的时间，再停 1 s）。
  - 两者的差别 = "去了一趟第 3 步"本身的代价，和位置无关。
- **S3b（像用户那样，在第 3 步拖到别处）**
  - 第 1 步只在起点停稳，不预热整条路线。
  - 切到第 3 步，做"前段"2 次划，相机移到第 1 步没显示过的地方。
  - 停 3 s，切回第 1 步，停 1 s，做"后段"2 次划。
  - 事先核对：后段经过的区域和第 1 步起点画面在原图坐标上不重叠。日志核对第 1 步在切换前没读过后段区域的图块。
  - 对照 S3b-ctl：第 1 步同样只在起点停稳，然后直接跳到"前段结束的位置"（第 1 步自己的跳转），停的时间和 S3b 从切回到开始划一样（1 s），再做后段 2 次划。
