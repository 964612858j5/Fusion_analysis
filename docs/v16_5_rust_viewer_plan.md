## 1. 为什么要把整条每帧通路搬出 Python

| 现象（真正 20 通道，§44/§45） | 在哪一段 | 只换读图能解决吗 |
|---|---|---|
| 一块图读完要 8–20 ms，CPU 只用约 3.5 ms | 读图线程抢 Python 全局锁 | 能 |
| 放大停手后界面卡 104–289 ms，界面线程只干了 50–75 ms | 界面线程抢不到锁 | 部分能 |
| 一次发布 15–26 ms，规划每片 9–22 ms | Python 记账 | 不能 |
| 向下拖动、单格缩小、甩动几乎不读图，仍要 74–124 ms | 发请求、交付、上屏节奏 | 不能 |
| 69 通道下界面时间几乎全在规划和发布（§38） | Python 记账 | 不能 |

路线 B 去掉的是 Python 的记账和抢锁；去不掉的是 pyqtgraph 处理滚轮、拖动的那一段（§9 第 4 条）。

## 2. 路线与五条实施契约

采用**路线 B**：Rust 查看器内核，在现有 QOpenGLWidget 的 GL 上下文里绘制。
不选的路线：
- A：只换读图，记账和节奏仍在 Python；
- C：独立进程加原生窗口，ROI 叠加层画不到上面；
- D：整个软件重写。

五条契约（全程有效）：
1. **Rust 负责查看器的性能核心**：规划、读图、解码、缓存、纹理、绘制、统计。镜头、显示设置和科学来源的最终决定权仍在现有产品对象。Python 每次只交一个轻量的不可变快照，不参与逐图块的读取和调度。
2. **Qt 的 GL 上下文是唯一的图形上下文**。Rust 不建第二个窗口或第二个 GPU 上下文；GL 资源的销毁、重建、帧缓冲和状态恢复都有明确测试（§3）。
3. **先做原始 uint8 的 Rust 端到端薄切片**（S-Raw）。完整 Zarr、Fusion 或 Step3 迁移都不是第一次性能证据的前提。
4. **只用真正 20 通道的新配对基线**；保留 3 通道不退步、69 通道压力测试。
5. **旧的 Python GPU 路径是独立回退**，不和 Rust 同时作为活跃查看器运行，避免双份缓存、重复读盘和显存占用。

另外，目标是把性能核心抽出来，**不是把 Python 的全部内部实现逐层翻译成 Rust**。每项功能搬进 Rust 前，先确认它在每帧热路径上。

## 3. Qt 与 Rust 的 OpenGL 硬契约

| 环节 | 规则 |
|---|---|
| GL 线程 | GL 的创建、上传、绘制、销毁只在 GUI 线程、Qt 上下文为当前时执行（initializeGL / resizeGL / paintGL 内，或显式 `makeCurrent`/`doneCurrent` 之间） |
| 后台读取 | Rust 读图线程只生成 CPU 数据，从不调用 GL |
| GL 函数加载 | 通过 Qt 的 `QOpenGLContext.getProcAddress`（Python 在 initializeGL 时一次性传入），保证和 Qt 的上下文一致；Linux、WSL2、原生 Windows 一套做法 |
| 帧缓冲 | 最终画到 `QOpenGLWidget.defaultFramebufferObject()`，不假设 0 号帧缓冲就是窗口（现有代码 `step1_gpu_layer.py:1900` 已这样做） |
| 尺寸 / DPI | resizeGL 时同步目标尺寸、视口和设备像素比 |
| 重新挂载 | reparent 时 Qt 可能重建上下文：接 `QOpenGLContext.aboutToBeDestroyed`（现有代码没有接，需新增），在其中使全部纹理、VAO、FBO、程序失效并释放；新上下文里按需重建 |
| 关闭顺序 | 先停通知，再停读图线程、清空队列，然后在当前上下文里释放 GL 资源，最后销毁 Qt 控件 |
| GL 状态 | 受影响的状态有：帧缓冲绑定、程序、VAO、数组缓冲、混合、模板、裁剪、视口、当前纹理单元及其绑定、像素存储参数。R0 的测试用完整的 glGet* 快照比对 paint 前后；产品热路径不做大量同步查询，只按已知值设置和复位自己改动过的状态 |
| 绘制时长 | 释放 Python 锁不等于释放 GUI 线程：paint 期间 Qt 收不到鼠标事件。每次 paint（含上传）有总时长上限：有输入时约 4 ms，没有输入时不超过一帧（约 12 ms）。具体数值在 S-Raw 实测确定，前提是界面心跳间隔 < 20 ms；不设 30 ms 的单帧上限。 |
| 失效 | 上下文丢失或初始化失败：报告原因，按 §5.3 回退 |

R0 用真实控件测：首次显示、resize、DPI 变化、reparent、隐藏后返回、关闭；在同一上下文和帧缓冲里，另一个绘制者（模拟 Step3 标签层）和 Rust 共存；以及上面列出的每个 GL 状态在 paint 前后不变。真实 Step3 标签叠加在 R3 测。

## 4. 数据输入契约：SourceManifest

Python 在打开项目、切换来源、保存校正产物后生成一份**不可变的 SourceManifest**；Rust 在整个查看期间只按它工作，不回调 Python 查来源。

内容：
- **数据集身份**：优先复用现有的 `SourceIdentity`（`viewer/tile_types.py`）和产品修订信息，不另造一套身份体系。只补操作系统层面的文件一致性检查：文件大小、修改时间、文件编号（Linux inode / Windows file ID）。
- **每通道、每级的几何**：形状、块大小。
- **解码元数据**：偏移表、长度表、压缩方式、预测器、数据类型（沿用 `raw_tile_provider._ChunkPlan`）。
- **ROI**：外接框、多边形。
- **每通道的来源决定**：原始 / 校正 / 缺失，由现有 `Step1SourceTable` 给出，含缺失原因。
- **校正产物**：
  - 路径；
  - `source_identity` 和修订标识；
  - 第 0 级区域；
  - sidecar coarse 平面的 stride、完整标记、身份一致性检查结果（沿用 `Step1SourceTable.coarse_plane` 的检查）。
- **有效性规则**：有效区域、NaN。
- **修订**：沿用现有的来源身份和产品修订（如校正产物的 `source_identity`、交接修订号）作为缓存键的一部分，任一变化，旧图块全部失效。

Rust 打开文件时核对数据集身份，和 manifest 不一致就拒绝读、报告原因、按 §5.3 回退，避免"Python 解析的文件和 Rust 后来打开的不是同一个版本"。

校正产物在第 0 级以外的层级：
- Rust 复现 `reduce_corrected` 的全部语义：第 0 级原点对齐、分块累加、有效像素计数、sidecar 选择，而不是另写一个近似的均值；
- 精度要求见 §7。

**不改**：已保存的校正 zarr、科学定量结果、Step4 的读取规则。

## 5. 内核设计

### 5.1 Rust 内核负责的部分

新 crate `fusion_viewer_core`（PyO3 + maturin，目标 abi3-py310，只适用于带 GIL 的 CPython；R0 实际构建并导入验证；每个操作系统各编一个 wheel）。释放 GIL 后执行的 Rust 代码里不带任何 Qt 或 Python 对象；渲染始终在 GUI 线程：
1. **图源**：
   - TIFF（deflate、LZW、zstd、不压缩，含预测器）；
   - 校正 zarr v2（Blosc lz4 + shuffle，f32），含现算层级；
   - 标签（`<u4`，Blosc lz4，R3）。
2. **准入和规划**：
   - 层级选择、分辨率受限、只画粗层、沿用旧块；
   - 细替身只在目标块到位前画；
   - 总预算裁剪；
   - 位置由近到远、同位置各通道一起；
   - 粗层原子显示。
3. **请求和取消**：
   - 线程池：服务器 6 线程，笔记本按核数，最多 6；
   - 规划写入"当前需要"集合，读图线程开工前自己核对，过期的跳过。
4. **并发**：
   - 读图线程解码时不持有任何 paint 也要拿的锁；
   - 结果走有界队列（固定容量，满了读图线程等待，不丢当前目标块）；
   - paint 只做非阻塞取出，从不等待一个没完成的解码。
5. **缓存**：
   - CPU 端按字节限额，和 Python 现有缓存（原始 512 MB、校正 2 GB）合计，不超过资源档位；
   - 显存用量报给 `gpu_memory`。
6. **显存布局**：移植现有虚拟纹理设计（数组纹理加页表，加 meta/params 纹理），u8/u16/f32 三族，带有效区域。不采用"每块一张纹理"：跨块平滑和逐像素一致验收依赖虚拟纹理。
7. **绘制**：Overlay、Fusion（分组最大值或求和、细胞核）、平滑、ROI 外接框裁剪和多边形模板（奇偶规则；多边形不合法时仍按外接框裁）、标签。着色器从现有 `ui/shaders` 移植（我们自己的代码）。
8. **重画通知**：
   - 合并通知：只在"没有待处理通知"变成"有"时写一个字节；
   - 写入不阻塞，Python 收到后一次读空；
   - 通知只表示"请重画"，不表示数据已上屏；
   - 机制见 §6。
9. **记录**：阶段名和 `utils/tile_trace.py` 一致（req/start/read/done/recv/gpu/present/cov）。时钟用单调时钟，并和 Python 的 `time.monotonic()` 对齐（Linux 用 `clock_gettime(CLOCK_MONOTONIC)`，Windows 用 `QueryPerformanceCounter`），现有 `a9_tiletl.py` 能直接分析。

### 5.3 回退

- **初始化失败**（模块缺失、版本不符、GL 探测失败、manifest 核对失败）：直接用旧路径，日志写明原因。
- **运行中失败**（解码反复出错、GL 上下文丢失）：
  1. 停通知；
  2. 通知读图线程退出（它们在下一个图块前检查，不等待正在进行的 I/O）；
  3. 释放 GL 资源；
  4. 整体重新挂载旧查看器。

  鼠标交互和 Qt 绘制路径上不做无限等待的 join。线程退出和 GL 释放分阶段进行：GL 立即在当前上下文释放；线程在后台退出，关闭程序时最多等一个有限的时间。

  不在半幅旧画面上混入另一条路径。
- 旧路径平时只作备用，不同时运行。何时退役由用户决定。
- **Rust 模式下旧的 Python 图块服务不启动**。现在 `build_step1_stack`（`ui/step1_viewer_host.py:457-495`）先建 `TileScheduler`，它的构造函数立即启动读图线程和计算线程（`viewer/scheduler.py:194-201`）。Rust 模式下：
  - 保留唯一的 Qt 镜头和 `ExploreController`，不另建镜头；
  - 旧的 Python 图块调度器推迟到真正回退时才创建或启动；
  - 控制器自己的图块请求（`explore_view.py:2039, 2081`，受 `_wants_precise()` 控制）在 Rust 模式下不发出。

  只改 Step1 的构造和接管边界，不改 Step0。改动涉及调度器的启动方式，需要授权（§10）。

## 6. 跨平台约束（原生 Windows 和 WSL2）

本次验收只在服务器和 WSL2 笔记本上做，但开发中必须做到：
- **不用只在一个系统上有的接口**：
  - 定位读：Linux 用 `FileExt::read_at`，Windows 用 `seek_read`，封装成一处；
  - 文件身份：inode 或 file ID；
  - 路径用 `PathBuf`，不拼字符串。
- **重画通知**：
  - Python 建 `socket.socketpair()`，把写端的句柄交给 Rust；
  - Rust 在 Linux 上按 fd 写，在 Windows 上按 SOCKET 写（`socket2` 封装）；
  - Qt 用 QSocketNotifier 读；
  - 两个系统同一套逻辑；
  - 写明 socket 的所有权（Python 持有两端，Rust 只借用写端）和关闭顺序（先让 Rust 停写，再关两端）；
  - 读到空数据要正确处理（Qt 可能把 socket 设成非阻塞）；
  - Windows 的 64 位 SOCKET 句柄要正确传递。
- **GL**：只通过 Qt 加载函数，不调用 GLX/WGL/EGL 的专有接口；着色器版本和扩展按现有代码的最低要求（R0 记录）。
- **构建**：
  - 从 R1 起，GitHub 自动构建同时编 Linux 和 Windows 两个 wheel；
  - Windows 上覆盖：wheel 安装、模块导入、同一 TIFF 样例的解码、通知机制冒烟测试；不含 GL，不设性能门槛，不作验收；
  - 需要在仓库里新增一个工作流文件（§8 待批）。
- 原生 Windows 的 GL 驱动行为、文件读取性能和部署方式，在以后单独的块里验证。

## 7. 正确性和像素契约

- **原始 uint8/uint16 TIFF**：和现有 Python 读取逐字节一致。测试覆盖两个真实文件，以及合成的各压缩方式、预测器、边缘不整块。
- **校正数据的现算层级**：
  - 数值比较用绝对加相对误差：|a − b| ≤ 1e-6 + 1e-6·|b|；
  - 有效性掩膜完全一致，NaN 和全无效块单独测；
  - ROI 几何一致。
- **最终 GPU 稳定截图**：新旧路径逐像素比较，需要一个确定的"已稳定"状态。有差异就定位到降采样、着色器运算次序或 GL 格式，不放宽成"肉眼差不多"。
- **保持已验收的行为**：
  - ROI 外不画；
  - 校正产物缺失时给提示；
  - 粗层原子显示；
  - 离开 Step1 不画；
  - A1/A7 镜头门；
  - D3D12 每进程约 5 个 GL 上下文的限制（GPU 测试一个进程一条）。
- **测试**：
  - 不预先批准大规模改写断言；
  - 保留旧路径的黄金图像、来源身份和生命周期测试；
  - 新的 Rust 测试验证同样的外部行为；
  - 只有真正依赖内部对象的测试才做定向迁移，每次迁移前列出清单。

## 9. 风险（按严重程度排序）

1. **S-Raw 达不到继续的条件**：说明瓶颈不只在 Python 记账。到时停下报告，不继续做功能对齐。
2. **笔记本的 WSL2/D3D12**：上传速度、垂直同步、每进程上下文数量限制。R0 就在笔记本上测。
3. **paint 占用 GUI 线程**：上传和绘制太长会挡住鼠标事件。用每次 paint 的时长上限和心跳间隔管住。
4. **pyqtgraph 输入路径还在 Python**：每格滚轮要走 pyqtgraph 的处理、`ExploreController._on_range_changed`，以及 Tissue Preview 的视框重画（`step1_viewer_mount.py:1216-1276`）。手势中响应中位数预计 8–10 ms（Odon 7.3 ms），不一定追平；若是最后的差距，另立块评估。
5. **释放、再拿 Python 锁**：paint 返回后要重新拿锁，其他忙碌的 Python 线程可能让界面等最多 5 ms。S-Raw 测心跳间隔。
6. **范围膨胀**：防止把 Python 的全部内部实现翻译成 Rust，变成两套庞大的查看器。每项功能先证明在热路径上再搬；旧路径只做回退。
7. **内存和显存记账**：Rust 缓存和 Python 缓存合计，并报给 `gpu_memory`。
8. **依赖记录**：把 Rust wheel 写进 `requirements-pip.txt`，会改变分割运行记录里的环境指纹（`engine_provenance` 的 `env_lock_hash`），**不改变**判断"是否同一分割引擎"的行为身份（`engine_identity` → `engines.behavior_identity`，`seg_runner/runner.py:32-38`）。v1 这里写错了，已更正。
9. **许可证**：Odon 是 GPL-3，只参考设计，不拷代码和常量；每个 Rust 模块写明参考了哪些设计。依赖的 crate（pyo3、glow、weezl、flate2+zlib-ng、zstd、blosc-src、socket2）都是 MIT、Apache、BSD 或 zlib 许可。

## 10. 需要用户确认的事项

1. 采用路线 B 和 §2 的五条契约；顺序为 R0 → S-Raw → R1 → R2 → R3 → R4 → R5，S-Raw 的继续条件按 §8。
2. 按 AGENTS 规则 4 授权新增的 Rust 内核：读图线程、缓存、调度。每个阶段开始前由执行窗口再报文件范围。
3. 旧的 Python GPU 路径保留为独立回退，不同时运行，何时退役由你决定。
4. 精度契约按 §7。
5. Rust wheel 写进 `requirements-pip.txt`，作为有版本的依赖记录（只改变环境指纹，不改变引擎身份）。
6. 在服务器和笔记本 WSL2 上安装 Rust 工具链（rustup，需要联网，装在 /root/.cargo 或用户目录）。
7. 从 R1 起在仓库新增 GitHub 自动构建工作流，编 Linux 和 Windows 两个 wheel。
8. Rust 模式下推迟创建或启动旧的 Python 图块调度器（只在回退时启动），并且控制器在 Rust 模式下不发自己的图块请求（§5.3）。这会改调度器的启动方式和 Step1 的构造边界，按规则 4 需要你授权。
