# v16 A0-2：存储决策基准（OME-TIFF vs OME-NGFF 0.4）

日期：2026-09-29。分支 `v16`，产品代码 = `9999601`（未改动）。依据：`docs/v16_A0_application.md` v2 §3 A0-2（工作负载在开跑前已预注册，运行中没有改动）与 v2.1 §2.3 的采纳规则。
脚本：`scripts/bench_v16_a0_storage.py`。驱动：`~/fusionflux/bench_a0/run_all.sh`。原始 JSON：`~/fusionflux/bench_a0/results/`（主结果）、`results_supplementary/`（补充）。

> **v2.2 说明（2026-09-29，用户批准）**：下面第 1 节的结论针对的是 A0 测的 **NGFF v0 实现**：(1, 512, 512) 分块、通用 zarr 读取器、只测原始读取的 Step4 扫描。**它不是对 NGFF 架构的否决。**规范存储由最多 2 天的 A2b-probe 决定，采用新的、开跑前写死的采纳规则（`docs/FusionFlux_v16_PreTMA_Architecture_Gate_v2.2.md` §5.6–§5.7）。本报告的数字不改，作为 A0 的原始记录。

## 1. 结论

**采纳规则不通过。NGFF 不作为新项目的原始像素平面。** 按 v2.1 §2.3，**A2b（NgffSource + 入库）和 Gate 2 的 NGFF 部分移入 backlog**；A2a（PixelSource + OmeTiffSource）照常进行。

| 规则（主判定：合成大图，Blosc-lz4） | 要求 | 实测 | 结果 |
|---|---|---|---|
| 收益：冷随机 ROI 2048²，单次读取中位数之比 TIFF ÷ NGFF | ≥ 1.5× | **1.30×**（13.46 ms / 10.35 ms） | 不满足 |
| 收益：第 0 层视口平移，冷总耗时之比 | ≥ 1.5× | **1.46×**（0.026 s / 0.018 s） | 不满足 |
| 不回退：Step4 顺序扫描，NGFF ≤ 1.10 × TIFF | 冷 / 热 | 冷 **1.95×**（45.6 s / 23.3 s），热 **2.55×**（55.5 s / 21.8 s） | **不满足** |
| 不回退：Step1 fusion 读 | 冷 / 热 | NGFF 更快：冷 0.52×，热 0.82× | 满足 |
| 体积：NGFF ÷ 源 | 由用户判断 | lz4 **2.01×**（7.48 GB 对 3.72 GB）；zstd（原图）1.01× | 请用户看 |

两项收益都没有达到 1.5×，Step4 还慢了约一倍，任何一条都足以判定不通过。

**替代方案「原始数据保持 OME-TIFF，只有衍生品用 NGFF」值得在 A2 里考虑**：
- Step1 显示校正通道的第 1 层，今天是运行时从第 0 层归约（`reduce_corrected`）；改为预先存一份第 1 层之后，同一路径**快 22 倍**（冷 0.207 s → 0.009 s）；
- 两者结果逐位相同；
- 每个通道只多 12 MB（第 1 + 2 层），生成一次用 2.7 s。

这不是本块的决定，是否纳入由 A2 的申请和用户决定。

## 2. 条件

- 机器：WSL2，16 核，约 10 GB 内存，ext4 虚拟盘。两种格式都用 8 个读线程；NGFF 侧关闭 Blosc 自带的线程。
- 数据集：
  - 合成大图 `synthetic_2x2_mirror.ome.tif`：3.72 GB，sha256 `b5f73eec…d164`；
  - 原图 `cropped_region.ome.tif`：0.93 GB，sha256 `fe3be2ba…75e5`；
  - 开跑前两个 sha256 都已核对。
- NGFF 副本：
  - 用 zarr 2.18 写 0.4 版：轴 c / y / x，y / x 的单位为 micrometer；每层 `scale = [1, PhysicalSizeY × H0 / HL, PhysicalSizeX × W0 / WL]`；分块 (1, 512, 512)；`dimension_separator = "/"`；带 omero 通道名。
  - **三份副本的自检都通过**：版本、轴、路径、每层唯一的 scale 变换及其语义、形状、分块、omero，以及每层 8 个抽样窗口与 TIFF 逐位相同。
- **「冷」只是 WSL 客户机层面的冷**：
  - 每次冷读前做 `sync` + `posix_fadvise(DONTNEED)`，`fincore` 确认驻留为 0。例外是一次 TIFF fusion 冷读前还剩 20 KB 驻留。
  - Windows 宿主机很可能仍缓存着 vhdx，所以冷、热两组数字相差很小。**这些数字不是物理盘的冷读**；等外接 SSD 可用后再补（v2.1 §2.3）。
- 每项：1 次不计时的预热，3 次冷，3 次热。表中是 3 次运行的中位数。

## 5. 补充（不在预注册之内，不参与判定）

目的：看 Step4 慢一倍的原因是**格式**还是**读取器实现**。
做法：NGFF 的「直接读取器」读每个分块文件的字节，在同样的 8 线程池里用 Blosc 解码，相当于 NGFF 版的 `TiffTileReader`。它与 zarr 读取的结果已核对：10 个随机窗口加 1 个边缘窗口，逐位相同。

| 合成大图，冷 | TIFF | NGFF（zarr，预注册） | NGFF（直接读取器，补充） |
|---|---|---|---|
| step4 总耗时 | 23.3 s | 45.6 s | **45.9 s** |
| roi2048 单次中位 | 13.46 ms | 10.35 ms | **7.2 ms** |

解读：
- **Step4 慢不是 zarr-python 的开销**，换成直接读取器也一样慢。
- 它跟着压缩后的数据量走：lz4 副本的压缩数据是 TIFF LZW 的 2 倍，耗时也是 2 倍。
- zstd 体积与 TIFF 相当，但解压更贵，结果同样慢一倍。
- 在这类 29 通道 uint8 数据上，Blosc-lz4 / zstd 都没有 TIFF-LZW 那样「体积小、解码便宜」的组合。换编解码器（例如 imagecodecs 的 LZW 或 Blosc2）可能改变结论，但会带来别的工具读不了的问题（申请 v2 裁定 2 已排除），而且超出本块范围。
- 随机 ROI 读的差距主要来自读取器实现：直接读取器比 TIFF 快 1.87×。这属于读取器优化，不是格式收益，对 OME-TIFF 同样适用（`TiffTileReader` 已经证明了这种做法）。
