**范围：** 本轮唯一的生产改动是 `Step1GpuBinding` 对"同一 GUI 线程、同一调用栈内同步返回的 scheduler cache hit"的接收方式。scheduler、provider、raw cache、GPU texture cache、GPU layer、shader、mount、host、viewer binding、Tissue Preview、shared camera、Step0、Overlay/Fusion、Intensity、coarse/fine 预算、coarse 原子发布一律未动。G3.2a.3 的 throttle 与 G3.2a.4 的落点去重原样保留。G3.2b/c/d 与 G4 未启动。

## 1. 旧的热缓存返回为什么仍然逐块显示

离开 patch A 后，A 的 fine display plane 按既有"离开视口即有界丢弃"的规则被释放，但底层的 scheduler raw cache 和 G1 的 GPU texture cache 仍然持有它的数据。返回 A 时四个请求全部在调用栈内同步命中缓存——然而 binding 的 callback **无条件**把结果转成 `Qt.QueuedConnection` signal，于是四个结果分四轮事件循环到达，每到一块就发布一次 descriptor。用户因此看到 coarse 之后四块逐步恢复，感官上像重新计算。

修复前实测（真实 `TileScheduler`、真实 raw cache、生产 GPU mount、公开 `mount.show_patch()`）：

| 返回 A 的观察项 | 修复前 |
| --- | ---: |
| scheduler 请求 | `4`（全部 cache hit） |
| provider 实际读取 | `0` |
| raw texture 上传 | `0` |
| GPU submit（总） | `5` |
| `show_patch()` **返回瞬间**已在屏的目标瓦片 | **`0 / 4`** |
| 自然 Qt paint 次数 | `2` |
| **第一次自然 paint** | **`0 / 4`，不完整** |
| coarse-only / partial 的自然 paint | **`1`** |

## 2. 修复：只批处理"同一调用栈内同步返回"的那一批

`_request()` 多了一个**只属于调用方栈帧**的可选列表 `collector`。callback 只有在同时满足两个条件时才把结果放进这个列表：

1. 仍处在 `scheduler.request(...)` 这一次调用之内（一个局部标志，在 `finally` 里立刻关闭）；
2. 当前线程就是 binding 的 GUI 线程。

其他任何情况——worker 线程、或调用返回之后——一律继续走原有的 `_tile_result_received` queued signal。结果接收逻辑拆成 `_apply_result(payload, publish=...)`；`_accept_result` 这个 slot 仍是异步结果的唯一入口，只是转调它并 `publish=True`。`_plan_fine_for_channel()` 在发完本次缺失请求后，把同步批次逐个 `publish=False` 地应用，最后由调用方（`update_viewport` / `refresh_display` / coarse 完成分支）**发布一次**。

没有新增缓存、timer、线程池、队列、coalescer、scheduler 或状态机；没有保留任何跨事件循环的 pending 状态；没有重新引入 C4.5c 的 waiting epoch、latest pending spec 或 callback 去重生命周期。只处理一个调用栈内已经同步返回的批次。

**同步与异步的准确分界：**

| 结果来源 | 路径 |
| --- | --- |
| raw cache 在 `request()` 调用栈内、GUI 线程同步返回 | 进本次局部列表 → 批末统一应用 → 调用方发布一次 |
| worker 线程送达（冷读、校正计算） | `_tile_result_received` queued signal → GUI 线程 `_accept_result` → 逐块发布 |
| `request()` 返回之后才到达的任何结果 | 同上，queued signal |
| shutdown 的同步错误回调 | 进批次但走既有错误分支，不发布错误像素 |

## 4. 混合命中

一个同时覆盖"已缓存的 A"和"从未读过的冷地"的视口：`show_patch()` 返回时已缓存的那一半**一次性**回到屏上（且该批只发布一次），冷的那一半随后由 worker 逐块补齐，已同步命中的 key 不会被再次请求；全部到齐后与 C1 屏幕参照差 `≤1 LSB`，`fine_budget_refused` 为空。

## 5. 线程归属证据

`test_a_cold_patch_still_arrives_tile_by_tile_from_its_worker` 把读取挂起，逐块放行，并用探针记录**每一次** `_apply_result` 调用所在的线程：全部是 GUI 线程。冷 patch 在 `show_patch()` 返回时一块都没有（证明它没有被误当成同步命中），随后逐块改善（`seen` 单调递增）。worker 线程从未直接调用 `_accept_result`、`_publish_current` 或 G1 layer。旧来源与旧 generation 的迟到结果仍由既有 fence 拒收（`test_two_fast_far_landings_…`、`test_results_from_a_superseded_binding_revision_are_refused` 保持通过）。

## 8. 测量限制与诚实边界

- 首帧证据的取法：在返回调用**之前**装好 paint 观察 → 调用公开 `show_patch()` → 让调用返回 → 才放开一次自然 Qt 事件循环 → 捕获第一次自然 paint 时的实际内容。**没有**在每个 cache hit 后主动 `processEvents()`，**没有**用高频 `grabFramebuffer()` 驱动绘制，**没有**只断言 descriptor 最终完整，**没有** monkeypatch scheduler 的私有 cache 或 heap。
- `grabFramebuffer()` 只在离开 A 之前与返回之后各用一次作为像素 oracle，**它会强制绘制**，已标注。
- 离屏平台不做缓冲交换（`frameSwapped = 0`）；paint 事件是真实的 Qt 呈现信号，但**不是显示器 input-to-photon 延迟**。
- **本轮只消除"数据已在 scheduler raw cache 与 GPU texture cache 中、但 display plane 因离开视口被释放"这一条返回路径上的视觉回放。** 它**不**解决：首次冷读、corrected product 归约、新通道第一次 coarse/fine 串行、真实磁盘 I/O、G3.2b 的来源重绑冻结、G3.2c 的 ROI 边界、显示器呈现延迟。raw cache 一旦淘汰，真实读取仍然必要。
- 合成台架没有 corrected product，校正归约成本仍未测（属 G3.2b）。
