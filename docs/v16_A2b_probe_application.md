## 1. 要回答的问题

「在 TMA 之前，把规范原始存储换成 NGFF 值不值」（v2.3.1 §1）。

两种格式各用适配自己布局的读取层，下游科学计算完全相同，按预先写好的采纳规则（v2.2 §5.6.4，行不变）判定 (a) 采用 NGFF 或 (b) 不采用（v2.2 §5.7）。

## 2. 起点：A0 学到的东西（只读核对）

- A0 的 NGFF v0：分块 (1, 512, 512)、通用 zarr 读取器，Step4 扫描冷 1.95×、热 2.55× 慢于 TIFF。A0 补充实验里写了一个 NGFF 直接读取器，**同样慢**。
- A0 的解读：耗时跟着**压缩后的数据量**走。lz4 副本的压缩数据是 TIFF-LZW 的 2 倍；zstd 体积相当，但解压更贵。
- **新发现（本次只读核对）**：A0 写 NGFF 时用的是 `Blosc(..., shuffle=Blosc.SHUFFLE)`（`scripts/bench_v16_a0_storage.py:132`）。这是**按字节重排**，而切片是 uint8，一个像素只有一个字节，所以它实际上什么都没做。Blosc 自带的 `BITSHUFFLE`（按位重排）对 uint8 图像通常能明显压小体积，而体积正是 A0 找到的瓶颈。它仍是 Zarr v2 支持的 Blosc 编解码器；是否真的能被别的工具正确读取，不靠推断，而由通用 zarr 读取器的独立读取验证来确认（§4.1）。见裁定 2。
- 交互读取（viewer）方面 NGFF 已经快 1.1–1.5×，但 A0 自己也指出，差距主要来自读取器实现，而不是格式；同样的做法 TIFF 也能用。这正是 v2.3.1 裁定 3（TIFF 同样优化、取较好的一方比较）要处理的问题。

## 4. 做法（只写脚本和临时副本，不改产品代码）

### 4.1 布局（NGFF）

- 第 0 层分块 (1, 512, 512)、(1, 1024, 1024)、(1, 2048, 2048) × Blosc-lz4 / Blosc-zstd，clevel 5（v2.3.1 §3 第 5 项，共 6 种）；第 1 层及以上保持 (1, 512, 512)。
- **裁定 2（新增）**：在 C1 选出的最佳分块上，再加 BITSHUFFLE 的 lz4 / zstd 两种，共 8 种布局。
- 写法沿用 A0：NGFF 0.4，轴 c / y / x，每层 scale，`dimension_separator="/"`，omero 通道名；写完先做 A0 那套自检（每层抽样窗口与 TIFF 逐位相同）。
- **每种布局（包括 BITSHUFFLE 的两种）都必须通过独立读取验证**：用通用的 `zarr.open(...)` 读，不经过我们自己的直接读取器；每层抽样窗口的像素与 TIFF 逐位相同。只有自己的读取器能读的布局，一律不算。

### 4.2 读取器（v2.3.1 §3 的封闭清单）

| | NGFF | TIFF |
|---|---|---|
| 基线 | 通用 zarr 读取器（A0） | **产品路径**：viewer 用 `RawTileProvider`，Step4 用 `TiffTileReader`，fusion 用 `OMETIFFLoader` |
| 适配读取器 | 按块对齐遍历；直接读块字节、在线程池上并行解码；预读下一块；有上限的块级 LRU 缓存 | **同样几类优化**：Step4 在 `TiffTileReader` 上加预读和块缓存（它本来就按块并行解码）；viewer 的随机 / 平移读用按 TIFF 分块直接解码的读取器（并行解码 + 块缓存） |

- **资源预算两边相同**（审核意见 1）：两种格式、每种读取器都用 **8 个读线程、预读 1 块、块缓存上限 512 MiB**；Blosc 自带的线程关闭；这些数字写进每条结果。
  - TIFF 的产品路径维持产品自己的设置（`TiffTileReader` 本来就是 8 线程；viewer 的读在 probe 里同样用 8 线程调用）；它是「原样」基线，不调参。
  - 不做单边调参。如果以后要试别的线程数 / 预读 / 缓存，必须对两种格式用同一个预先写好的小网格（例如线程 4 / 8 / 16 × 预读 1 / 2 × 缓存 256 / 512 MiB），各取自己的最佳。本次不做，只用上面那一组。
- 每个比较行的基线都取 **TIFF 两个数字中较好的那个**：min(产品路径, 同类优化)，两个都报告。
- TIFF 优化如果比产品路径更快，只记进待办（可能的 TIFF 读取器改进），v16 不实现。

### 4.3 测量（v2.2 §5.6.3，与 A0 相同的种子和路径）

- **viewer**：冷 / 热的随机 ROI 512² / 2048² / 4096²；第 0 / 1 / 2 层视口平移；切换通道。
- **Step4 端到端**：cropped_region 上的产品量化，只换原始读取器。**科学结果必须逐位相同**：h5ad 的 `X`、`layers`、`obs` 数值列、`obsm`，CSV 数值，细胞顺序，类别和字符串字段。只排除记录读取器、后端、路径、耗时、commit 的来源字段，并列出排除了哪些。
- **Step4 原始扫描**：cropped_region 和合成大图（合成大图没有分割，只测扫描）。
- **Step1 fusion（审核意见 2，方案 B：跑完整 fusion）**：在 probe 脚本里同步运行产品的 `FullFusionWorker`，fusion 设置取自 test1 副本记录的那一份，输出写到临时目录。
  - 一次用 TIFF 源（产品的 `OMETIFFLoader`），一次用 NGFF 源（一个只提供 `read_region(..., normalize=False)` 的薄 loader，背后是 NGFF 读取器）。fusion 算法、窗口、参数完全相同。
  - 比较完整 fusion 的耗时；**两次产出的 fused 像素必须逐位相同**（数组逐位比较，不看来源字段）。
  - 这样量的是「换成 NGFF 之后 Step1 到底快不快」，而不是某个孤立读取器快不快。
- **其他**：磁盘 ÷ 源、导入耗时、峰值 RSS。
- **像素校验（oracle 不变）**：NGFF 读出的像素与 TIFF 逐位相同，每种布局、每种读取器都查。
