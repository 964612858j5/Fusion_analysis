# Step1 G3.2b.4B2C：GPU 接管期间停止旧 ExploreController 的不可见瓦片请求

**日期：** 2026-09-21 · **分支：** `v15-interactive-channel-workspace`
**起止 HEAD：** `9d78d1c`（未提交；未 reset/checkout/restore/clean/stash/rebase/amend）

## 0. 结论摘要

GPU 层确认初始化成功后，旧 `ExploreController` 不再为**自己那些不透明度为 0 的
ImageItem** 读取瓦片；它继续是唯一的相机、鼠标、`jump_to` 执行者和
`interaction_event` / `gesture_quiet` / view-rect 发布者。

**确定性计数（两次独立运行、两种 arm 顺序、1 通道与 4 通道，结果完全一致）：**

| | 修复前 | 修复后 |
| --- | ---: | ---: |
| controller-only 请求（冷 Patch，每次） | `29–37` | **`0`** |
| controller-only 请求（冷 Tissue，每次） | `18–22` | **`0`** |
| provider 读取，5 次冷 Patch 合计（1 通道） | `224` | **`64`**（**-71 %**） |
| provider 读取，5 次冷 Tissue 合计（1 通道） | `128` | **`26`**（**-80 %**） |
| provider 读取，5 次冷 Patch 合计（4 通道） | `416` | **`256`**（**-38 %**） |
| provider 读取，5 次冷 Tissue 合计（4 通道） | `206` | **`104`**（**-50 %**） |
| **binding 请求** | `12/16/12/12/12`、`6/6/4/6/4` | **逐项不变** |
| **可见瓦片 / view rect / target level / GPU 上传** | | **逐项不变** |

**诚实结论（重要）：本块证明的是"少读了多少"，不是"快了多少毫秒"。**
1 通道下把 arm 顺序对调后，墙钟中位数没有可辨差异（Patch `183.7 → 184.8 ms`，
Tissue `90.3 → 92.3 ms`）——因为 12–16 块瓦片根本没有把 8 个 I/O worker 占满，
多出来的 32 次读取跑在空闲 worker 上。4 通道下中位数有改善
（Patch `946.1 → 796.6 ms`、Tissue `538.7 → 382.0 ms`），但单次方差极大，
且**测量期间本机另有窗口在跑测试套件**，因此**不作为已验证的加速主张**。

**一个确定性的额外收益：热返回真的还是热的。** 4 通道下修复前回到已准备好的
patch 仍要读 `66` 块、回到已落过的 Tissue 点仍要读 `34` 块——那些永远不上屏的
瓦片把有用的瓦片挤出了 512 MiB raw cache；修复后三项热返回**全部 0 读取**。

同一台架、同一真实切片与真实 cuCIM 产物，GPU backend 成功，冷 Patch 与冷 Tissue
各一次，按 generation 把请求分成两类：

| | 冷 Patch | 冷 Tissue |
| --- | ---: | ---: |
| scheduler 请求总数 | `44` | `28` |
| binding RawKey | `12` | `6` |
| **controller-only RawKey** | **`32`** | **`22`** |

| GPU 上传 | `12` | `6` |

**controller-only 非零，台架确实复现了问题。**

## 2. 请求 gate 的位置与作用范围

### 2.1 公开方法

`viewer/explore_view.py::ExploreController`

```python
@property
def viewport_requests_enabled(self) -> bool: ...
def set_viewport_requests_enabled(self, enabled: bool) -> bool: ...
```

**默认 `True`。** 新增的状态只有一个布尔 `self._viewport_requests_enabled`。
没有新增 scheduler、worker、线程池、timer、queue、registry、token、cache、
request authority 或状态机。

### 2.2 它挡住什么

在与既有 `self._suspended` **完全相同的判断位置**加一个条件：

| 方法 | 挡住的东西 |
| --- | --- |
| `_issue_raw_requests()` | 当前层可见批次（单一入口，因此也挡住它调用的下面几项） |
| `_issue_raw_underlay()` | level+1 raw underlay |
| `_issue_raw_prefetch_ring()` | 一圈 prefetch ring |
| `_issue_settled_request()` | settled / precise 批次（`set_selection` 也直接调它） |
| `_issue_directional_prefetch()` | 方向性预取 |
| `_start_floor_job()` | corrected floor（与既有 `_suspended` 一样置 `_floor_pending`，延后而非丢弃） |
| 精层 cache-serve blit | 已缓存 corrected 瓦片的重新提交 |

### 2.3 它绝不碰什么

ViewBox 与相机、鼠标、`jump_to`、`_motion_timer`、`_settle_timer`、
`interaction_event`、`gesture_quiet`、`selection_context_changed`、
`overview_prepared`、任何相机 / view-rect 查询（Tissue Preview 的视框来源），
以及**任何别的消费者用自己的 generation 向共享 scheduler 发出的请求**。

**它不是 `suspend_for_production`：** 不锁相机、不写状态文字、不 join floor 线程、
不排空 scheduler。这一点有专门的门（见 §6 的
`test_closing_the_supply_does_not_lock_the_camera_or_post_a_badge`），
变异 M5 把 gate 改成用 `suspend_for_production` 实现时它转红。

### 2.4 取消在途工作时如何不误伤 GPU

关闭时只取消**这个 controller 自己的** generation：

```
self.scheduler.cancel_generation(self.view_generation)      # ("raw", n)
self.scheduler.cancel_generation(self._settled_generation)  # ("precise", n)
self._cancel_directional_prefetch()                         # 既有方法
self._overlay.cancel_inflight()                             # ("dapi_raw", n)
```

这些 token 与 `Step1GpuBinding` 的**不可能相等**：binding 的 token 是
`("step1-gpu-binding", id(binding), tier, revision, channel, epoch, serial)`，
第一个元素就不同；scheduler 只按相等性比较 token。**没有触发停止条件 #6。**
已经开始的读取自然跑完，但其结果不会再启动下一圈 underlay / ring。

### 2.5 重新开启

`set_viewport_requests_enabled(True)` 对**当前**视口**恰好重新规划一次**
（`_issue_raw_requests()`，前提是有 `_current_bbox` 且没有被 overview 阻塞），
用户不需要额外移动或缩放。重复调用返回 `False` 且不再发第二轮
（门 `test_the_switch_is_idempotent_and_re_issues_only_once`）。

## 3. mount 何时关、何时开

`ui/step1_viewer_mount.py`：

| 时机 | 动作 |
| --- | --- |
| `_start_gpu_backend()` —— **在 `layer.initialized` 确认之后**，紧接 `set_marker_visible(False)` | 关闭 |
| GPU 初始化失败 | **不关闭**；backend 如实为 `cpu-fallback`，controller 照常供给自己的图层 |
| `_stop_gpu_backend(restore_controller=True)` | 重新开启（并对当前视口重新规划一次）——**当前没有任何调用方走这条路**，见 §3.1 |
| `_stop_gpu_backend(restore_controller=False)` —— 来源重建与 `close()` | **不重新开启** |
| `restore_legacy()` | **不重新开启**（它显示的是旧 Patch widget，并且下一行就把 whole-slide host 隐藏了） |
| `deactivate()` / `activate()` | **不动**：离开 Step1 不重新打开隐藏 controller 的请求；回来只让 GPU binding 恢复一次 |
| source rebuild | 旧 stack 按既有生命周期销毁；新 stack 的 controller 在 GPU 再次接管成功后关闭 |

接线是一个静态小方法 `_set_controller_viewport_requests(controller, enabled)`，
对没有该方法或 C++ 侧已消失的 controller 宽容返回——这是性能门，不是正确性门。
**`ui/main_window.py` 未改动。**

### 3.1 B2C.1 收口：三处生命周期错误（复核发现，已修）

第一版把"停掉 GPU backend"一律当成"controller 的图层又是画面了"，这在三处都不成立。
复核指出后逐条核实，**三条都属实**：

| 路径 | 第一版的错误 | 收口后 |
| --- | --- | --- |
| `_gpu_source_changed()` | `_stop_gpu_backend()` 重新开启旧 controller，**而下一行 `viewer.open()` 就把它销毁**——等于让一个正在下场的 stack 抢新 stack 的 scheduler | `restore_controller=False`，**不唤醒** |
| `close()` | 同上，**关闭过程中又发起一轮读取** | `restore_controller=False`，**不唤醒** |
| `restore_legacy()` | 注释写"旧 renderer 即将上屏"——**概念错了**。它显示的是 `self._legacy`（旧 **Patch** widget），并且**下一行就 `self.host.setVisible(False)`** 把 whole-slide host 连同 ViewBox 一起隐藏 | **完全移除**那次重新开启 |

**第一版的三条门把这个错误行为写成了契约**，已一并改正（见 §6）。

`_stop_gpu_backend(restore_controller=True)` 保留，但**当前 mount 没有任何调用方走它**：
`open()` 与 `_gpu_source_changed()` 到达 CPU renderer 时用的都是**全新 stack**，其 controller
的开关本来就是默认 `True`。它作为"同一 stack 真正交接给 CPU whole-slide renderer"的记录在案
的入口保留并加门，如实说明它今天不是产品路径。

（GPU 启动失败的路径本来就不受影响：开关只在 `layer.initialized` 确认之后才拨下，失败时从未拨过。）

   **读取量下降 38–80 %、controller-only 请求归零、热返回恢复为零读取**。
2. "冷"= 每个 arm 一个全新窗口与全新 viewer stack，arm 内每次落点都是该 arm
   从未访问过的区域。**未清除 OS page cache**，因此没有任何数字被称作磁盘冷读。
3. GUI 心跳最大间隔是事件循环跑不动的时长，**不是** input-to-photon 延迟。
4. 真机仍需验收：本块**不宣称真机通过**。

## 11. 真机验收步骤

1. 进入 Step1（GPU 接管），点击一个从未访问过的 Patch，再在 Tissue Preview
   空降到一个从未访问过的区域——**画面内容、落点、缩放、是否一次完整清晰
   出现，都应与之前完全相同**；
2. 连续平移与缩放：跟手程度、Tissue Preview 视框跟随应与之前完全相同；
3. 回到刚才看过的 Patch：应一次完整恢复；
4. 多通道（4 个以上 cuCIM 通道）下重复 1–3，观察首次准备是否更快；
5. 若 GPU 不可用而走 CPU fallback：旧 renderer 应照常出图，不需要额外移动相机。
