## 2. Full Image 修复前为什么没有准备两个方法

两件事叠加，缺一不可：

1. **没有挂载。** `Step0ExploreTab` 从未构造过协调器。
2. **就算挂上也不够。** `prefetch_policy.hot_order()` 的第一行就是 `seen = {center}`——
   它**按设计排除当前通道**。这在 Compare 是对的（三栏前台已经在准备它），
   在 Full Image 是错的：**Full Image 只有一个面板**，一次只显示一种方法，
   另一种方法没有任何人准备。

`hot_order(1, 3) == [0, 2]`，`HOT_METHODS == ("tophat","cucim")`。

## 3. 是否修改了 MultiChannelPrefetchController，为什么

**改了，两处，都是最小扩展。**

### 3.1 `include_center`（默认 `False`）

**既有接口缺了什么：** 宿主可以决定 `specs` 里有哪些通道、什么顺序，但
**中心通道在排序规则里被事后丢掉**，而 `HOT_METHODS` 不是按通道可寻址的。
没有任何公开方式表达「当前选中通道的当前视野，同时准备 TopHat 和 cuCIM」。

```python
order = list(prefetch_rules.hot_order(center, len(self.specs)))
if self.include_center:
    order.insert(0, center)      # 第一个，排在每个邻居之前
```

**默认 `False`**，所以唯一的既有调用方（compare strip）的计划、邻居顺序、
优先级与今天逐项一致。`viewer/prefetch_policy.py` **未改动**（SHA-256 不变），
`hot_order` 的语义没有动。

### 3.2 generation token 唯一化（缺陷修复）

`TileScheduler` 的契约写明 generation token 是 **opaque**，并且
「调用方可以用带命名空间的元组，使两个独立计数器永不冲突」。协调器却用了
**每实例从 0 开始的普通整数**，而 `cancel_generation` 在共享 scheduler 上
**永久**标记该 token 过期。

于是：离开 Step0（`stop()` 取消当时的 token）→ 回到 Step0（新实例从 0 开始）
→ 新计划发出的请求命中**已经过期**的 token → 全部 `cancelled`。

**实测缺陷现场：** 往返后当前通道第二个方法 `0/3` 驻留，
`hot_tiles_requested = 12`、`hot_tiles_completed = 6`、`hot_cancelled = 6`，
而 `settle_aborted = 0`、`hot_batches = 1`、计划正确（`center CD20`，
`plan [('CD20',0), ('CD3',1)]`）——**不是计划错了，是 token 被提前判死。**

修复：模块级 `itertools.count()`，token 为 `("hot", n)`，每实例唯一。
门：`test_a_remounted_coordinator_does_not_reuse_a_cancelled_generation`。

## 4. 通道点击后具体准备哪些 key

Full Image（`include_center=True`）：

```
for channel in [当前通道] + hot_order(当前通道, N):      # 中心优先
    for (method, base_param) in (("tophat", radius), ("cucim", sigma)):
        for (tx, ty) in snapshot.visible_tiles:          # 当前视野，仅此
            CorrectionKey(source, channel, TileAddress(grid, snapshot.level, tx, ty),
                          method, (effective_param(base_param, level, ds),),
                          algorithm_version, quality)
```

**只有当前视野的瓦片**，在**当前显示层**上；范围就是既有策略允许的
i-1/i+1/i-2/i+2 邻域加中心。没有全片扫描、没有 corrected pyramid、
没有写回 TIFF/Zarr、没有改 manifest/handoff。

参数来自页面的 `_compare_hot_specs()` ——与 compare strip **同一个 provider**，
即 `_effective_correction_params()`，与面板真正渲染用的是同一个答案。

## 5. 前台与后台的请求顺序

- 前台（用户看得见的那一种来源）走 controller 自己的请求路径，优先级
  `RAW_CURRENT_BASE_PRIORITY = 200` / `PRECISE_CURRENT_BASE_PRIORITY = 100` 一带。
- 后台准备走 `HOT_PRIORITY_BASE = 5000 + hot_index`，即**既有的后台档**，
  在共享 scheduler 的 min-heap 里排在所有前台之后。**本块没有改这些数字。**
- 中心通道排第 0 位，邻居从第 1 位开始——只影响 `include_center=True` 的宿主。
- 物理并发仍由既有 `HOT_INFLIGHT = 2` 限制；快速换通道由既有
  `_on_selection_context_changed` → `_abort_hot()` → `cancel_generation` 失效。
- 校正计算全部在 compute worker 线程；协调器的结果处理经 queued signal 回到
  GUI 线程。**没有在 GUI 线程做校正，也没有在切步骤/关窗时 join 长任务**
  （`stop_hot()` 只取消 generation，不等待）。

门：`test_the_visible_source_is_served_before_the_background_neighbour`
（视口静置时显示的方法已经完整）。

## 6. 方法热切换是不是零新计算、零实际读取

**真实切片（`biopsy.ome.tif`，level 0，35 块可见瓦片，CD22/CD4）：**

| 六次切换累计 | 修复前 | 修复后 |
| --- | ---: | ---: |
| provider `read_region` | **0** | **0** |
| provider `read_tile` | **0** | **0** |
| corrected **tile** 计算 | 67 | **32** |
| corrected **floor** 计算 | 80 | **45** |
| corrected cache 命中 | 742 | 484 |

| 每次切换墙钟（到当前视野全部驻留） | 修复前 | 修复后 |
| --- | --- | --- |
| 逐次 (ms) | **434.5** / 77.9 / 44.5 / 59.4 / 52.0 / 34.1 | **103.9** / 97.8 / 52.4 / 55.5 / 27.2 / 55.3 |
| 首次 | **434.5** | **103.9**（**-76 %**） |
| 中位 | 55.7 | 55.4 |

**诚实结论，逐条：**

- **零实际读取：成立。** 六次切换的 provider 读取增量在两侧都是 `0`——原始瓦片
  早已在 raw cache 里，切换方法不会重新读盘。
- **零新计算：不成立，而且本块无法在白名单内做到。** 切换仍然触发两类计算：
  1. **当前视野本身的 corrected 瓦片：已经不再重算**（门
     `test_switching_between_the_two_methods_reads_the_prepared_cache` 断言
     被切换到的那一批可见 key 的计算次数**不增加**）；
  2. **控制器自己的 level+1 回退批次**（`_issue_settled_request` 的
     "intermediate corrected fallback" 加一圈 ring）和 **corrected floor**
     （`_start_floor_job` → `compute.correct_array`，**没有自己的缓存**，按
     `_floor_ctx` 每次方法变化都重算）。协调器只准备 `snapshot.level`，
     也没有任何公开方式为"未被选中的方法"预备一个 floor。
- 因此本块把首次切换从 `434.5 ms` 降到 `103.9 ms`，**而不是降到 0**。
  剩下的两项要动 `viewer/explore_view.py`（回退层策略 + floor 生命周期），
  **超出本块白名单，未实施**，最小方案见 §12。

合成台架（4096 方片，8 块瓦片）同向但幅度小得多且噪声大
（首次 `123.0 → 86.3 ms`），因为合成瓦片的校正本身只要几毫秒；真实切片的
数字才是结论。

## 7. Full Image / Compare 往返

`Step0ExploreTab` 的 stack、scheduler 和 corrected cache **在往返中存活**：
隐藏（进入 Compare）再显示，`tab.stack is stack_before`，已准备的瓦片
**一块都没有重算**，相机不漂移。门
`test_coming_back_to_the_full_image_reuses_what_it_prepared`。

**既有架构边界（本块未改，也不应改）：** Full Image 与 Compare **各有**自己的
scheduler 和 corrected cache——`build_compare_stacks` 的注释写明共享会让两个模式
互相淘汰、并让 `suspend_for_production` 的"等到空闲"变成"等另一个模式也空闲"。
所以"往返复用缓存"成立于**各自模式内部**，不是跨模式共享一份缓存。

## 8. 快速换通道与换数据集

- **快速换通道**：`controller.selection_context_changed` → 协调器
  `_on_selection_context_changed` → `_abort_hot()` → `cancel_generation(旧)`，
  队列清空、已开始的工作靠 `notify_on_stale_completion` 归还并发额度。
  **既有机制，本块未改。**
- **换数据集**：`set_dataset()` 先 `_discard_stack()`（本块在其开头加了
  `stop_hot()`），新 stack 带新 scheduler 和新 cache；`source_identity` 不同，
  所以 `CorrectionKey` 不同，旧数据集的结果不可能被命中。门
  `test_another_dataset_never_hits_what_this_one_prepared`
  断言两次 source 不同、scheduler 不同、stack 不同。**没有新增身份或 authority。**

## 9. 生命周期与"隐藏的 Step0"

用 **Qt 自己的显示生命周期**作为门，不新增信号、step registry 或第二套"active"：

| 时机 | 动作 |
| --- | --- |
| `_build()` 成功 | `start_hot()` |
| `show_source()` 暖路径 | `start_hot()` / `refresh_hot()`（specs 未变即 no-op） |
| `showEvent` | `start_hot()` |
| `hideEvent` | `stop_hot()` |
| `release_for_production()` | `stop_hot()`（在 suspend **之前**，让它的排队工作按自己的 generation 取消，而不是被 scheduler drain 等出来） |
| `resume_from_production()` | `start_hot()` |
| `_discard_stack()` | `stop_hot()`（先于 teardown，它持有即将关闭的 controller 与 scheduler） |

`start_hot()` 在 **无 stack / 已 released / `not self.isVisible()`** 时拒绝。

**这条门对真实产品成立，已单独验证：** `MainWindow` 把四个步骤放在
`QStackedWidget` 里，实测 `setCurrentWidget(step1)` 会把 `hideEvent` 投递到
Step0 页面的**后代** widget（`after switch away: ['show','hide'] visible False`）。
门 `test_switching_steps_really_delivers_a_hide_to_this_widget` 把 tab 放进一个
真实 `QStackedWidget` 并切换页面，断言切走后 `tab.hot is None`、切回后恢复——
而不是只调用 `tab.hide()` 证明槽接上了。

C4.5b 的隐藏 Step0 行为未改动（未触碰 `ui/main_window.py`）。

## 12. 未解决的部分与最小追加方案（**未实施**）

方法切换仍然重算两样东西，都在 `viewer/explore_view.py`：

1. **level+1 回退批次**（`_issue_settled_request` 的 intermediate corrected
   fallback + 一圈 ring）。协调器只准备 `snapshot.level`。要覆盖它就得把
   控制器的回退策略（`intermediate_corrected_fallback` 开关、
   `_viewport_shrinking` 守卫、ring 尺寸）**在第二个地方重新实现一遍**——
   这正是 `AGENTS.md` 第 5 条要避免的漂移，所以没做。
2. **corrected floor**（`_start_floor_job`）。它没有缓存，也没有公开的
   "为一个未被选中的方法预备 floor"入口。

最小方案（**需追加授权**）：给 `ExploreController` 一个只读的公开入口，
让宿主能说"为方法 M 预备 floor / 预备回退层"，由现有 `_floor_gen` 与
`_settled_generation` 机制承接；不新增缓存、线程或状态机。影响面是四个页面
共用的 `explore_view.py`，风险与回退方式需单独评估。
