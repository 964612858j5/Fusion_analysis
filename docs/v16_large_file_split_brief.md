**耦合**：
- 455 个方法共用 `self` 上的几百个属性，各段之间直接互相读写状态。
- `step0_page.py` 有 52 行 import，声明了 7 个 Qt 信号；`main_window.py` 有 69 行 import。

**测试对内部实现的依赖**：
- 59 个测试文件直接调用 `Step0Page` 的私有方法。

把方法搬到别的模块后，这些替换只对原模块里的名字生效，被搬走的代码会悄悄绕过它们。这是机械拆分里最大的隐藏风险。

## 4. 选项

### 4.1 怎么拆

| | A. 机械拆分（只搬代码） | B. 组件化 |
|---|---|---|
| 做法 | 按功能把方法搬到若干新模块（mixin 或辅助模块），由 `Step0Page` / `MainWindow` 组合；方法名、签名、信号、构造 / 销毁顺序、对外导入路径都不变 | 抽出自己持有状态的对象（如 compare 控制器、校正面板、Save 协调器、工作区管理器），彼此通过窄接口交互 |
| 行为 | 不变 | 会变（状态归属移动） |
| 耦合 | **不减少**：仍然共用 `self` 的状态；收益是文件好找，单次改动和审核的范围变小 | 真正降低 |
| `_build_ui` | 需要单独处理：语句顺序、局部变量、信号连接时机都有讲究，不是单纯搬方法 | 同左 |
| 估计 | `step0_page` 3–4 天，`main_window` 3–4 天（含全量回归、真机冒烟） | 2–3 周，高风险 |

| v17（计划原定） | 能结合真实 TMA 负载来设计 | TMA 早期开发仍在大文件旁边进行 |

## 5. 风险与防护

**风险**：
- 测试替换的模块全局失效（见 §2）。
- 多重继承下方法重名、MRO、无参 `super()` 出错。
- 循环导入。
- Qt 信号必须声明在 `QObject` 子类本体上。
- 构造和销毁顺序被打乱。
- 把"搬代码"演变成"顺手改设计"。

**防护（codex 建议，作者同意）**：
- 每个功能段单独一个提交，可单独回退。
- 方法名、签名、装饰器、信号声明、构造 / 销毁顺序、对外导入路径一律保持不变。
- 逐个确认被测试替换的名字仍然生效。
- 不引入通用的兼容或代理机制。
- 用 AST 逐个比对方法体，查出意外改动。注意：这只能发现改动，**不能证明等价**，因为搬到别的模块后全局名字的查找位置变了。
- 验收：现有回归、A1 零漂移与 A7 零回写两项不变量、真机冒烟（载入、Save、取消、关闭、compare）。

## 6. 防止以后变乱

codex 与作者一致的判断：真正的风险不在 A9 的规模，而在**流程编排与状态归属一点点漏回页面回调**。

建议：
- 在审核中严格执行"新流程放新模块，页面只做接线"。
- 加一个"增长报告"检查：每次回归列出两个大文件新增的行数和位置。
- **不设硬性行数上限**，因为那会逼出为凑数而做的随意拆分。
