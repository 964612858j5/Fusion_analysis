## 二、Phase A：先定义，再证明（不改 Step0 Save）

### 2.1 现有 coarse 瓦片的精确定义（从代码读出，不是假设）

- 瓦片矩形：`y0=ty*512`，`y1=min(y0+512, level_shape_h)` —— **最后一行/列瓦片是不完整的**
  （`ui/step1_viewer_host.py::_level_rect`）。
- **stride = `round(raw.level_downsample(level))`**，来自 OME 金字塔自己的层形状，
  **不是 `2**level`**：用户切片是 `52560 → 13140 → 3285 → 821`（每级 ÷4，末级取整），
  有效倍率 `64.02` 被四舍五入成 `64`。
- level-0 矩形 = 瓦片矩形 × stride，因此相位恒为 0。
- 每个格子 = 以 **level-0 原点**为锚的一个 `stride × stride` 块内**有效样本**的均值；
  `valid = counts > 0`；ROI 外值 0 且 invalid（上层画成 NaN）；
  **存储的 0.0 是样本**（polygon mask 写的就是 0）；float64 求和、float32 输出。

### 2.2 独立候选与现有实现逐格比对

候选实现**按定义独立重写**（不调用生产归约函数），并**按 Step0 写盘的 4096 瓦片顺序累计**。
五个合成用例：ROI 起点不对齐、起点对齐、边长都不整除、含零值带、金字塔倍率为 2。

| 指标 | 结果 |
|---|---|
| `valid` 不一致的格子 | **0**（全部用例） |
| 有限值 | **逐位相同**，`max|Δ| = 0.0` |
| NaN / +Inf / −Inf 模式 | **完全一致** |
| 经**现有 C1** Overlay 与 Fusion 合成 | **RGB 最大差 0 LSB、alpha 完全一致、valid 完全一致** |

## 三、Phase B：Step0 写 L0 时顺带产出

### 3.1 身份与完成标记（防止旧 L0/旧 L3 混用）

1. **静态字段**（方法、参数名与值、`bg_correction_algo_version`、ROI 名与 bbox、`source_shape`、
   stride、format 版本）逐项比对；
2. **每次真正重算才新铸的 `source_identity`**（uuid4）写入该通道 **L0 attrs**，同一值写入 **L3**；
   Step1 两边逐项比对。它正是 `Step1SourceTable.identity_token()` 已经在读的字段，
   **没有另建来源权威**。**增量 Save 跳过的通道不会走到这一步**，其 token 与 L3 原样保留。
3. **产品 token 为空 → 永不使用任何 plane**：老产品（没有 token）继续 runtime 归约。
4. **覆写某通道 L0 之前先删除该通道的旧 L3**；L3 的像素与身份写完之后**最后**才写 `complete`。
   取消 / 异常 / 半写入留下的 sidecar 一律被拒绝。
5. 全新（非增量）Save 删除产品时**连同 sidecar 一起删除**；取消的全新 Save 同样。

### 3.2 写盘

`WsiCorrectionWorker` 在**已经算出 corrected tile、正要写 L0 的那一刻**把同一批像素
（**polygon mask 之后**，与写入 L0 的完全相同）累加进 `_CoarsePlaneAccumulator`：
按 level-0 全局原点对齐、处理 ROI 非对齐起点与跨 4096 瓦片的块、边块按真实样本数归一。
**从不在写完 L0 后重读整片**。
coarsest level / stride 由 `coarsest_level_stride()` 从**切片自己的金字塔**读出；
读不到就**不写 sidecar**（不猜 stride），旧路径继续有效。

### 3.3 Save 的实际代价（**合成 `/tmp` 项目**，8704×6144，两通道，交替顺序各 3 次取中位）

| | 中位 |
|---|---|
| 不带 plane 的 Save | 714.0 ms（三次 923.3 / 696.2 / 714.0） |
| 带 plane 的 Save | 795.3 ms（三次 792.5 / 795.3 / 795.3） |
| **额外** | **+81.3 ms（+11.4 %）** |

| sidecar 体积 | 38.6 KiB/通道，占产品 **0.02 %**（真实区域上为 1.5 MiB/通道） |

**如实记录：** 第一次配对测得 **−149.7 ms**（即「带 plane 更快」），那是噪声不是提速，

### 更正（复核指出，属实）

本报告初稿写的「第一次自然 paint 与『完整』同一时刻（差 0.1 ms）」**不成立**：
`…_4e_endtoend.json` 里**有 plane 的三轮中有两轮 `first_natural_paint_after_complete_ms`

## 六、旧产物的限制（必须按这个说法理解）

- **本功能实施前写出的旧产物**没有 `source_identity`，因此只要它们未经重算或显式补建，
  **Step1 不会为它们启用 plane**，首次启用仍然是 runtime 归约、仍然慢。
- 补建脚本 `scripts/build_corrected_coarse_l3.py` 对无 token 的产品**主动跳过并说明原因**；
  只有显式 `--stamp-product`（写产品 attrs、不碰像素）才能补建。
  **本块没有对任何真实项目运行过补建或 `--stamp-product`**，只在 `/tmp` 合成项目上验证过。
- 因此 **Phase A 的真实产物加速数字（11 589 → 7.4 ms、9 188 → 2.5 ms）是"读取代价"的对照，
  不能当作 Phase B 给现有项目的现成提速**：那些数字是在一个补建出来的 plane 上测的，
  而在本块最终的严格 token 规则下，同一个 plane 会被拒绝，直到该产品被重新 Save（或显式补建）。
- 产品运行时**不会**自动补建、不会自动迁移、不会写用户项目。
