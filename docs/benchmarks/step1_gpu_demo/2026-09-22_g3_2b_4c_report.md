## 二、测量了什么，以及每个数字不是什么

真实 `Step1WholeSlideMount` / `Step1ViewerHost` / `build_step1_stack` / `RawTileProvider` /
`Step1TileProvider` / `TileScheduler` / `ExploreController` / `Step1GpuLayer` /
`Step1GpuBinding`，真实 GPU（`NVIDIA GeForce RTX 4090`），真实切片与 **Step0 真实写出的
cuCIM 产物**；入口只用产品自己的公开路径：
`state.set_display_visible(channel, True)`（Step1 行上的那个勾）、`mount.show_patch()`、
`mount.sync_source()`。台架与窗口替身沿用 G3.2b.4 的同一套，所以数字与那一块可比。

- **GUI 心跳**是 GUI 线程上的 5 ms `QTimer`，其最大间隔 = 事件循环最长无法运行的时间。
  它**不是**输入到光子的延迟。
- **自然 paint** 是挂载 GPU widget 上的 Qt 呈现事件，**不是**屏幕光子；且只在**没有**调用
  `grabFramebuffer()` 的地方计数。**本诊断脚本没有为测量强制取过帧**；唯一的一次
  `grabFramebuffer()` 是生产 `_start_gpu_backend()` 自己为确认 GL 上下文而做的，
  发生在被测的勾选动作**之前**，不参与任何一段计时。
- **"冷"**指进程内首次访问。**OS page cache 未清空**（需要 root，且会干扰其他窗口），
  因此下面**没有任何数字可以叫做冷磁盘读取**。
- **数据集不是用户的真机。** 两个真实项目全程只读；绝对毫秒不得当成用户真机的 6 秒。

### 3.5 「来源重绑」与「Step0 Save 本身」是两件事（本块只测了前者）

- **测到的是：来源重绑，且 cuCIM 产物已经在盘上。** 台架把 window 的决策由
  `CD22=original` 改成 `CD22=cucim`，再走公开的 `mount.sync_source()`；
  读的是**用户自己的 Step0 早先写出的**产物。这对应用户轨迹中「Step0 存完之后回到 Step1」
  的那一段。
- **没有测的是：Step0 Save 本身**（cuCIM 校正计算 + 写 `corrected_channels.zarr`）。
  它属于 Step0，既不在本块白名单内，本块**一次也没有运行过**，
  因此**本报告中没有任何数字可以归给 Step0 Save**；用户真机的 6 秒里是否还包含这一段，
  本块无法回答。
- **一个必须写明的依赖：** `load_overview()` 读的是**当时被选中的那个通道**。
  本台架选中的是 CD22（= 刚存成 cuCIM 的那个），这正是产品场景；
  若当时选中的是 original 通道，这次读取会便宜得多（对照：原始通道最粗层读取中位 9.6 ms）。
  **这个变体本块没有测。**

## 四、结论：钱花在哪里

### 4.0 对既有判断的更正（用户 2026-09-22 裁定）

G3.2b.1 曾判断「cuCIM 来源重绑的主导 GUI 冻结是 `TileScheduler.shutdown()` 在 GUI 线程
join 在途读取」。**按本块这条轨迹，该归因需要更正：** join 实测 **1.3 ms**
（demo 与用户本人切片各五轮，范围都是 1–1 ms），冻结的是 `build_step1_stack()` 里同步调用的
`ExploreController.load_overview()`（demo **2 063 ms**，用户切片 **9 497 ms**，
后者占该段的 **97.6 %**）。
本报告与 `docs/step1_gpu_demo_plan.md` 均以此为准；旧判断不再作为后续方案的依据。

**同一个成本被付了两次，都是「corrected 产物没有金字塔，要读粗的就得把整区域归约一遍」：**

1. **重绑时**：`ExploreController.load_overview()` 在 **GUI 线程**上同步做一次 → 窗口无响应 2.2 s。
2. **勾选时**：binding 的**完整 coarse 事务**是最粗层的**一整块**（本数据集 1 块），
   在 worker 线程上做一次 → 2.4 s。

**而当前视口真正需要的瓦片早就准备好了。** Patch 相机下 12 块目标层瓦片每块 3.7–23.7 ms，
**27.4 ms 全部到手**；画面却到 **2 421.6 ms** 才出现 —— 等待中的 **98.9 %** 与当前视口无关，
它在等整区域的粗层背景。这不是优先级或调度问题（coarse 与 fine 在同一 scheduler 上并行，
fine 从未被 coarse 挡住 I/O），而是**发布规则**：
`Step1GpuBinding._publish_current()` 要求首次出现的通道**先有完整 coarse**，
这正是「新通道一次完整清晰出现」验收契约的实现方式。

### 已否定的假设

| 假设 | 证据 |
|---|---|
| 重绑冻结主因是 scheduler join | join **1.3 ms**，冻结在 `load_overview()` 2 063 ms |
| 等待是当前视口瓦片的 provider I/O | 视口 12 块 **27.4 ms** 全部到手 |
| 存在重复读取 / 无关请求占用 | 重复读取 `{}`，legacy 请求 **0**，迟到拒绝 **0** |
| 瓶颈在 GPU 上传或绘制 | 上传 13、submit 14；完成到自然 paint **0.1 ms** |
| 4A 之后首个 cuCIM 已经不慢 | 4A 把它从 ~8.3 s 降到 ~2.4 s，**但 2.4 s 仍是全部等待** |

## 六、最小扩围方案（均未实现，等待裁定）

**方案 1 — 让当前视口先完整出现（唯一落在本块白名单内的方案）
　　——用户 2026-09-22 裁定：暂不采用。**

- **先更正本报告初稿的一处措辞错误：** 初稿把改动写成「首次出现的条件由『完整 coarse 已发布
  **且** 视口 fine 齐』改为『视口 fine 齐 **或** 完整 coarse 已发布』」。**这句话是错的**，
  照它字面实现会放出只有 coarse、fine 未齐的**模糊首帧**，直接违反已验收的
  「一次完整清晰出现」。本意是：**保留**「首次出现必须视口 fine 齐」这一条不动，
  只把「必须先有完整 coarse」这个**前置条件**去掉
  （`ui/step1_gpu_binding.py::_publish_current()` 中 `if not coarse: continue` 那一行），
  coarse 缺席时提交 `ChannelSource(coarse=(), fine=…, selected_level="fine")`；
  `ui/step1_gpu_layer.py` 不需要改（`coarse` 默认即空元组）。
- 实测收益：Patch 相机首次勾选 **2 421.6 ms → 约 30 ms**（demo）、
  **8 682.6 ms → 约 40 ms**（用户切片）；全片相机目标层就是粗层，**没有收益**。
- **用户不采用的理由（记录在案）：** 即使按更正后的写法，只凭视口 fine 上屏也会
  **在随后平移时失去完整粗层背景保证**。该方案**不再作为本线的候选**，
  除非用户另行提出。
- 回退：本方案未实施，无需回退。

**待裁定问题 A — GPU 接管时，是否还需要同步读取那个不可见 controller 的 overview？**
（用户 2026-09-22 指定为独立裁定项，本块只提供事实，不实施）

只读核实到的事实：

1. `ui/step1_viewer_host.py:385` 的 `build_step1_stack()` **无条件**同步调用
   `controller.load_overview()`，且它发生在 `_start_gpu_backend()` **之前**——
   建栈时还不知道 GPU 会不会接管。
2. `load_overview()` 的 docstring 自己写着「Used at startup, where a blocking read is
   fine because there is nothing on screen yet」，并且**已经存在**一个不阻塞 GUI 的同类入口
   `switch_overview_for_current_channel()`（命中则同步 memcpy，否则后台读、先清像素）。
3. GPU 接管成功后 `set_marker_visible(False)` 把 `overview_item` 的**不透明度设为 0**
   （`viewer/explore_view.py::set_marker_visible`），4B2C 之后该 controller 连请求都不再发。
   也就是说：**这次同步读出来的像素，在 GPU 接管成功的路径上从不显示。**
4. **尚未核实、动手前必须先查清的**：`load_overview()` 还会固定 `_display_lo/_display_hi`
   并（`ensure_floor=True` 时）触发 `_ensure_corrected_floor()`；Step1 GPU 路径的显示窗口
   来自 draft spec 与 `_request_gpu_seed()`，**看起来**不依赖它，但本块**没有**验证过
   去掉/延后这次读取不会改变任何显示数值或 CPU 回退行为。
- 收益（若可去掉/延后）：重绑 GUI 最长无响应 **demo 2 235 ms、用户切片约 10 s → 预计几十 ms**。
- 代价与风险：`load_overview` / `build_step1_stack` 都在**本块白名单外**，且是 Step0 Full Image
  与 CPU 回退共用的入口；必须先回答第 4 点，再决定是「GPU 接管时跳过」还是「改成后台读」。

**待裁定问题 B — corrected 粗层如何避免每次都把整区域归约一遍？**
（用户 2026-09-22 指定为独立裁定项，本块只提供事实，不实施）

- 现状：corrected 产物没有任何比 level-0 更粗的表示，所以「要一块粗瓦片」＝「把整区域按
  stride 归约一遍」。G3.2b.4A 已经把这次归约本身优化了 2–10.79×，**它仍然是全部等待**：
  demo 2.4 s、用户切片 **7.2–8.7 s**，且**每次新建 stack 都要重付一次**
  （raw cache 随 stack 一起销毁；同一 stack 内重复勾选是 0 读取 / 2.9–4.4 ms）。
- 可能的方向（都需要单独授权，且都不在本块白名单内）：Step0 写盘时附带粗层/金字塔或 sidecar；
  或在 Step1 侧持久化一次归约结果并给出失效规则（=新增缓存权威，须明确批准）。
- 代价/风险：产物格式或缓存权威的变化、Step0 写盘时间与磁盘占用、版本兼容与失效规则。
