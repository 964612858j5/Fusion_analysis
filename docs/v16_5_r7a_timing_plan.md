## 0. 背景（已核实）
- 从第 3 步回到第 1 步后，第一次 `composed=1` 的那一帧 `draw_ms` 为 218–338 ms：倍数 2.0 下 12/12 次都有，倍数 1.315 下也有。
  - 倍数 1.315 时它落在切回后的等待期；倍数 2.0 时回来后一直 `composed=0`，到第一次拖动才合成，正好撞上拖动。
- 这一帧图块上传、推迟、显存增长都是 0，所以排除了"读图块、传图块"。但页表和参数表的上传（`render.upload`）还没排除。
- 现有 `draw_ms` 包括：构表、上传表和参数、准备目标、整次合成、标签、blit。它不是显卡上的执行时间。
- 校正通道一个图块约 9–10 ms 的读取时间也没有细分。这个数字决定 R7b 第一步先做哪一项。

## 2. 加的记录（默认关闭；沿用 R6 的开关：tile trace 开且 `BLOCK01_A9_DRAW_LOG=1`）
**合成分段**（Rust 新小模块 `frame/phase_time.rs`，不超过约 200 行）
- 按代码里的实际顺序分 6 段，在现有调用处包计时，不搬动任何调用；CPU 时间都记：
  1. 构表：`vt.sync_pages` + `vt.sync_meta`，纯 CPU；
  2. 准备目标：`render.ensure_targets`；
  3. 上传表和参数：`render.upload`（只在需要重新合成时调用）；
  4. 整次合成：`render.compose`；
  5. 标签：只在有标签时；
  6. blit。
- 另记"剩余时间"= 本帧 `draw_ms` − 已分类各段之和，避免把构造参数、绘制列表等未分类的成本算到某个 GL 调用上。
- 合成是一次画完所有通道（着色器内部遍历），不按通道分开计时，也不为计时改成多次绘制。
- 第 2–6 段另加 GL 计时查询（`GL_TIME_ELAPSED`，OpenGL 3.3 核心），非阻塞采集：
  - 每段一个查询，结果留到之后自然发生的帧里取；
  - 取之前先查 `QUERY_RESULT_AVAILABLE`，没好就留到下一次；
  - 查询池容量固定（例如 64 组），满了就跳过并记"缺失"；
  - 不用 `glFinish`，不为取结果多画一帧；
  - 查询池放在每个窗口现有的 GL 资源容器（`viewer.rs` 的 `Gpu`）里，随上下文创建；
  - 上下文还在时（`release_gl`）删除查询对象；上下文已经没了时（`forget_gl`）只丢弃句柄，不调用任何 GL 删除，未取回的结果记为"缺失"；
  - 结果带原来的帧号。
- 附带轻量信息：
  - 本窗口 GL 初始化次数（现有 `attaches`）；
  - 本帧目标是否重建（`ensure_targets` 的返回值）；
  - 本帧合成行数。
- 记录名 `fphase`，带帧号和窗口标记，只在 `composed=1` 或总时间 > 20 ms 时记。

**读取分段**（Rust，按真实调用链加）
- 一个图块读取的阶段分布在 4 个文件里，各自记 wall 时间和线程 CPU 时间（`CLOCK_THREAD_CPUTIME_ID`）。两者之差包括 I/O 等待和线程没被调度的时间，报告里不全算成磁盘等待：
  - `zarr_v2.rs`：读文件（`std::fs::read`，不是 pread）、字节数、块数；
  - `blosc.rs`：LZ4 解压，以及 unshuffle（现有 SSE2 路径）；
  - `reduce.rs` / `step1_tile.rs`：矩形拷贝、归约、NaN/有效区处理、打包成图块；
  - `pool/worker.rs`：汇总上面各段，算出"未分类时间"，写进现有 `read` 记录的附加字段，并标明来源（校正 / 原图）。
- 原图（TIFF）读取同样记"读文件 / 解压 / 打包"三段，便于对照。这三段的边界在 `reader.rs`，只在那里加计时。
- **同条件的解压实现比较**（供 R7b 第一步选型，诊断用，不进产品）：
  - 用同一批真实校正块（每个通道 20 块、5 个通道），release 构建，单线程，输出同样的 4 MiB 浮点；
  - 比较三种实现：现有 Rust 实现、`lz4_flex`（只换 LZ4 部分，容器和 unshuffle 用现有代码）、C 库 blosc（库内线程数固定为 1）；
  - 每块重复 20 次取中位数，报告每块 ms 和吞吐。
  - 代码放在 `examples/blosc_bench.rs`（已有的诊断程序，不随产品发布）；两个库只作为开发依赖（`[dev-dependencies]`）加进 `Cargo.toml`。

**规则**
- 只加记录，不改顺序、预算、缓存或任何决策。
- 定向测试：
  - 开关前后稳定画面逐像素相同；
  - 关时没有新记录；
  - Rust 单元测试通过；
  - 查询池满、上下文释放后重建时不出错。
- **诊断开销**：在同一场景下比较 关闭 / 只开 CPU 分段 / 开 CPU+GPU 分段 三种情况的每帧画图时间和截图更新间隔，各 3 次。开销明显时，结论只用开销最小的那组，并在报告里说明。

## 3. 测量
- 用户真实项目副本，私有只读挂载（同 R6 §12.2，含挂载证据和原项目完整核对）。
- **S3a 重测**（两档倍数 × 3 轮 × 3 种 = 18 次）：
  - S3a：去第 3 步，在第 3 步里来回各划 1 次，回第 1 步；
  - S3a-静：去第 3 步不拖，停同样时间，回第 1 步（回答问题 3）；
  - S3a-ctl：同样的来回划在第 1 步里做（R6 的对照）。
- **两次回切都要真正触发合成**：每次运行切换两次（去、回、去、回）。每次回到第 1 步后：
  - 先等第一次 present；
  - 再做同样的一次小相机操作（划 1 次 200 像素），确认出现 `composed=1` 并记下它的分段；
  - 再停 1 秒（从这次合成的 present 算起），然后进入下一段。
  - 只截第二次回来后的拖动；两次回切的分段都报告，用来分清"一次性"还是"每次都有"。对照组做同样的步骤。
- **读取分段**：真实项目冷读 S1、S2 各 2 轮，加 OME-TIFF 冷读 S1、S2 各 2 轮对照，两档倍数。
- 注入迟到超过 8 ms 仍判测量失败（规则不变）。失败的那次照样保留，它的合成分段照样分析、照样报告。
