# Step0 G3.2b.4B1.1：当前通道双方法准备的真实状态，与 Full Image / Compare 缓存复用

**日期：** 2026-09-21 · **分支：** `v15-interactive-channel-workspace`
**起止 HEAD：** `9d78d1c`（未提交；未 reset/checkout/restore/clean/stash/rebase/amend）

## 0.1 更正（2026-09-21，由 G3.2b.4B1.2 复核指出）

**本报告原先写 corrected floor「没有任何缓存」，这是错的。** 仓库早已有
`ExploreController._floor_cache`（`viewer/explore_view.py:2321`），一个
`_floor_cache_limit = 8` 的 `OrderedDict`，配套 `_floor_cache_key()` /
`_remember_floor()` / `_restore_cached_floor()`，来自
`7d7bb5a perf(viewer): cache the corrected floor, so flipping methods recomputes nothing`
与 `a609c26 fix(viewer): a cached floor cancels the work that was owed for it`。

本报告观察到的「每次切换都重算 floor」是真实的，但**原因不是没有缓存**，而是：

1. 每次测量都切到一个**新通道**，该通道另一种方法的 floor 从未算过，第一次必然 miss；
2. 缓存是**每个 controller 各一份**，Full Image 与 Compare 互相看不到；
3. HOT 只准备 corrected tile，**不为另一种方法提前准备 floor**。

真正的缺口因此是「首次使用另一方法」与「跨 controller」，不是缓存缺失。
下文凡出现「没有缓存」的表述，均以本节为准。

## 4. 路径 B：为什么之前重算，改了什么

**之前：** `build_default_stack` 与 `build_compare_stacks` 各自
`LRUByteCache(RAW_CACHE_BYTES)` / `LRUByteCache(CORRECTED_CACHE_BYTES)`。
两份实例互不相识，所以 Full Image 算好的 corrected tile 在 Compare 一次都命中不了。

**改了什么（§十三.6/7）：**

| 对象 | 是否共享 | 拥有者 |
| --- | :--: | --- |
| raw `LRUByteCache` | **是（借用）** | Full Image (`ExploreStack.owns_caches=True`) |
| corrected `LRUByteCache` | **是（借用）** | Full Image |
| `overview_store` | 是（既有，本块未改） | Full Image |
| scheduler / provider / `CorrectionCompute` / controller / ViewBox / generation | **否** | 各自 |

**为什么 scheduler 仍然分离：** 共享它会让 `suspend_for_production` 的
"wait until idle" 变成"等另一个模式也空闲"，即在 GUI 线程上等别人的工作
（停止条件 #1/#6）。这一条没有改。

**一个回归，已修并加门（如实记录）：** 第一版把 `caches=` 无条件传给
`CompareStrip._stack_factory`。那是一个 seam——多个测试台架和任何早于本块的
builder 都还是旧签名，多给一个参数会在 `ensure_built` 的 `try` 里抛出，被报成
"Compare could not be opened"。实测 `test_step1_shared_camera.py` 两条门因此转红
（`_compare_camera()` 返回 None）。收口：借用改为**提供而非强加**——
`_factory_takes_caches()` 用 `inspect.signature` 判断（显式 `caches` 参数或
`**kwargs` 都算接受），不接受的 builder 自己建自己的缓存，行为与以前一致。
新增两条门：旧签名 builder 仍能打开 Compare、`**kwargs` builder 能拿到缓存。

**实现沿用既有的借用范式**——`overview_store` 早就是"Full Image 拥有、Compare 借用"，
本块把同一范式扩到两个 LRU：`CompareStacks.owns_caches`、`ExploreStack.owns_caches`，
默认 `True`，只有被注入时才是 `False`。**没有新增 cache 类型、manager、registry、
authority 或状态机**，`viewer/caches.py` 一字未改。

**预算没有提高，反而降低：** 原先两个模式各自最多各一份（2 GiB + 2 GiB），
现在两个模式共用一份。

### 实测（真实切片，A/B 只差 `ensure_built(caches=…)` 一个参数）

| | 私有缓存（before） | 借用缓存（after） |
| --- | --- | --- |
| raw cache 同一对象 | `False` | **`True`** |
| corrected cache 同一对象 | `False` | **`True`** |
| scheduler / provider / controller 同一对象 | `False` / `False` / `False` | `False` / `False` / `False` |
| strip 自认拥有缓存 | `True` | **`False`** |
| **进入 Compare 的 corrected tile 计算** | **30**（level 2:18, level 1:12） | **12**（level 1 only，**-60 %**） |
| 进入 Compare 的 floor 分块 / 耗时 | 56 / 457.2 ms | 38 / 280.2 ms |
| 返回 Full Image 的 corrected tile 计算 | 0 | 0 |
| **strip teardown 之后 Full Image 仍驻留** | 45/45 | **45/45** |

消失的 18 块正是 Full Image 已经持有的那一层；剩下的 12 块是 Compare 自己的
level+1 回退层，Full Image 从未算过它——**这就是"只补真正缺失的 tile"**（§九.7、§十三.10）。

**诚实说明：** 进入 Compare 的墙钟两侧都约 6.1 s，但那是本基准里固定的 6 s
`drain()` 主导的，**不是可比的加速指标**；本块用**计算次数**作为结论，不用这个墙钟。

## 5. 按 §八 停止并上报：corrected floor

**tile 缓存共享不能解决 floor。** floor 由 `_start_floor_job` →
`compute.correct_array` 产生，**其实有缓存（见 §0.1）**，只是每个 controller 各一份，且从不为另一种方法提前准备。实测每次方法切换 13–31 个分块、**中位 220.9 ms**；进入 Compare
另有 38–56 个分块、280–457 ms。

- **为什么 tile 全命中了还在等：** 用户看到的"重新计算"里，当前视野的 corrected
  瓦片确实是 0 重算；等待来自 floor 与 level+1 回退层，它们走的是另一条路径。
- **最小 floor 复用接口（未实现）：** 给 `ExploreController` 一个只读的公开入口，
  让宿主能按既有 `_floor_ctx`（`(source, channel, method, effective_params, level,
  stride)`）存取一张 floor 数组；两个模式共用一份即可，与 tile 缓存同一个拥有者模型。
- **内存成本：** 一张 floor 是一个降采样到 `_floor_level` 的 float32 全片数组。
  本演示切片在 floor level 上约为 `1217×1362×4 B ≈ 6.6 MB`/(通道×方法)；用户那张更大。
  若不设上限会随通道数线性增长——**需要一个明确的字节预算，属于新增缓存**。
- **生命周期风险：** floor 与 `_floor_gen`/`_floor_pending` 耦合，且在 GUI 线程读
  `_overview_arr`；跨模式共享要保证换数据集、换参数时按 key 自然失效。
- **回退方式：** 不注入即回到今天的行为，一行。

**本块没有实现它，按 §八 与停止条件 #4 停下等待用户裁定。**
