## 1. 现状（已核对代码）

### 1.1 标签
- Step3 用自己的一个 `Step1WholeSlideMount(labels=True)`（`ui/main_window.py:1910-1917`）。
- Rust 一律不用：`_decide_rust` 见到 `labels_wanted` 就拒绝，原因是 "this viewer draws masks"（`ui/step1_viewer_mount.py:343-344`）。没有测试固定这条拒绝。
- **规划和读取**：`Step3LabelBinding`（`ui/step3_label_binding.py`，569 行）。
  - **拖动中也在规划**：每个 `interaction_event` 最多每 33 ms 规划一次（`MOTION_INTERVAL_MS`，`:285-295`），停手（`gesture_quiet`）时再规划一次；
  - 规划可见块加一圈，中心先，有预算；
  - 一个读线程用 Python zarr 读 `<u4` 标签（第 0 级是 Step2 写的掩膜，粗级是 `label_pyramid` 的 Blosc lz4）；
  - 每收到一块（GUI 线程的 `_accept`），就重建整个 `LabelSnapshot` 并交给画布的 `set_labels`（`:483`、`:548-569`）；
  - `dispose()` 默认等读线程最多 **10 秒**（`:239`），挂载关闭时调用。
- **Python 的标签绘制**（`_compose_labels`，`ui/step1_gpu_layer.py:2568-2640`）：
  - 目标：`ids`（R32UI）和 `shown`（RGBA8）；`shown` 和 `final` 共用模板缓冲（`_ensure_label_targets`，`:2543-2566`）；
  - 没有可见的层，或还没有视口时，`_shown_ready = False`，呈现 `final`；
  - 先把 `final` 原样复制到 `shown`（NEAREST），计数 `label_compositions` 加 1；
  - ROI 剪裁框整个在屏幕外时只复制、不画标签；
  - 每层：
    - 先在 `ids` 上清零，按平面顺序画 id 图：**不裁剪、不混合**，后画的平面覆盖先画的，包括它的 0；
    - 再画到 `shown`：多边形 ROI 时开模板（等于 1，不写模板）；有剪裁框时开剪裁；混合用 `FUNC_ADD` 和 `BlendFuncSeparate(SRC_ALPHA, ONE_MINUS_SRC_ALPHA, ONE, ONE_MINUS_SRC_ALPHA)`；
    - 参数：`u_mode`（轮廓 / 填充）、`u_radius = label_radius(width, 设备像素比)`、`u_color`、`u_alpha`；
    - 层按快照里的顺序画（细胞核层在最后）；
  - 画完关混合、恢复剪裁和模板状态；
  - `paintGL` 在 `_shown_ready` 时呈现 `shown`，否则呈现 `final`（`:1898`）。
- **标签纹理**：`_LabelTextureLru`，每个平面一张 R32UI 纹理（NEAREST，CLAMP），预算 256 MB（`GPU_LABEL_TEXTURE_BYTES`）。着色器 `ui/shaders/step1_gpu_labels.frag`（103 行，两遍，`usampler2D`，用 `step1_gpu.vert`）。
- **Rust 现在**：
  - 没有任何标签代码；zarr 只读 `<f4`；
  - 呈现时总是把 `final` 复制到 Qt 的帧缓冲（`render/output.rs:10`）；
  - `Step1CoreLayer` 的 `labels_enabled = False`，`set_labels` 和 `readback_label_ids_for_test` 抛错，`label_stats` 返回空，没有 `readback_shown_for_test`。
- **测试只测 Python 画布**：
  - `test_step3_label_render.py`：9 条像素测试；
  - `test_step3_label_binding.py`：20 条，不画像素；
  - `test_step3_label_mount.py`：3 条生命周期测试。

### 1.2 `gpu_memory` 和隐藏释放
- 接口：`hidden`、`gpu_bytes()`、`release_to_coarse()`、`set_smooth()`。
- 释放入口：
  - `release_hidden` 只在两处调用：Step2 分割开始（`ui/step2_page.py:3060`）和预分割开始（`run_job.py:69-75`）；
  - `on_layer_active` 在恢复时调用，Python 画布还在提交画面、显存块数增加时调用（`step1_gpu_layer.py:1527-1530`），超过 `VIEW_VRAM_TARGET`（5 GB）就释放隐藏的画布。
  - 释放别的画布时，会让那个画布的 GL 上下文成为当前上下文。
- **Python 的 `gpu_bytes`**（`:1358-1369`）计入：通道纹理、数组块、标签纹理、合成目标（每像素 4×16+4+1 字节）。**不含** `shown` 和 `ids`。
- **Python 的 `release_to_coarse`**：只保留上一次画面在画通道的最粗级块，删掉合成目标；**标签纹理保留**。
- **`Step1CoreLayer` 已注册**，三个方法都有，和 Python 有三处不同：
  1. `release_to_coarse` 保留**所有**通道的最粗级块；
  2. 新建显存块时**不**做压力检查；
  3. `set_smooth` 值没变也会重推显示设置。
- 另外：`dispose()` 返回的统计是写死的 0；没有任何测试在 Rust 画布上调用这三个方法，也没有运行中切换平滑的 Rust 测试。

### 1.3 资源档位
- `core/resource_tiers.py` 只是常数。EDGE 档的内存目标 12 GB、上限 14 GB；显存目标 5 GB。
- Python 路径有两个 CPU 缓存：原始 512 MB、校正 2 GB。
- Rust 只有一个 512 MB 缓存，其中：
  - 校正块也放在里面；
  - 结果队列（最多 1024 块）从中扣最多一半；
  - 规划器手里保留的块（`held`，按视野修剪）和缓存共用存储（`Arc`），没有单独计数；
  - 正在解码的块不计。
- 显存额度和 Python 相同（1536 MB）。
- Rust 模式下 Python 的两个缓存对象仍会建出来，但调度器推迟启动，所以不占内存。

### 1.4 montage
- montage 在另一个标签页（"Pre-seg Results"），和整片视图不会同时显示，但两个画布可以同时存在。
- 它自己建一个 Python `Step1GpuLayer`：
  - 走逐平面的程序（`step1_gpu.frag`），不是整片用的虚拟纹理程序（`step1_gpu_vt.frag`）；
  - 两份着色器都只在纹素比屏幕像素大时平滑（`step1_gpu.frag:20-24`、`step1_gpu_vt.frag:153-156`），但取样范围不同：逐平面绘制在图块边上取不到相邻图块的像素，虚拟纹理可以跨图块取样；
  - 所以平滑打开时，图块边上的像素两者不同，**Python 里 montage 和整片视图本来就不逐像素一致**，也没有测试比较两者。
  - montage 有自己的 GPU 像素测试（`test_step1_montage_view.py` 约 :491 起）。
- Rust 模式下打开 montage：
  - 仍建 Python 画布，各自一个 GL 上下文；
  - 两个画布都注册在 `gpu_memory`，都收到 `set_smooth`；
  - montage 画布从不标记为隐藏，所以 `release_hidden` 不释放它（Python 模式下也一样）。

### 1.5 回退
- 已有的回退都是"开始时不用 Rust"或"绑定层发现不支持就换"：
  - 初始化或清单失败；
  - 通道不在片子里；
  - 采样器装不下。
- 换法：`_rust_unsupported` 停掉 Rust 画布，在**同一个**镜头、控制器和视图上建 Python 画布；旧的 Python 调度器到这时才第一次启动（`DeferredScheduler`）。
- **没有运行中回退**：
  - 读图出错（`pool.rs:216`）只计数、记 `last_error`：不通知，不重试；这块要等下一次规划才会再请求，画面不动时可能永远不再请求；
  - 画图出错只打日志；
  - GL 上下文丢失后会在下次初始化时重建，但重建失败不会通知挂载（可能留下空白画面）。
- 从"决定回退"到"真正换掉"之间，Rust 画布还在显示，没有东西阻止它再画一帧。
- 关闭：Rust 读线程是分离的，`close()` 不等待；总方案"关闭程序时最多等一个有限时间"没有实现。

## 2. R3 要做的

### 2.1 标签由 Rust 画

**数据交接（L1，总方案的有条件例外，见 §8 第 1 条）**
- 规划和读取仍由 `Step3LabelBinding` 负责，Rust 负责纹理、合成和呈现。
- 这偏离了总方案"标签作为 Rust 图源"（§5.1 第 1 条）和"Rust 负责性能核心"（§2 契约 1）。理由和条件：
  - 拖动中标签最多每 33 ms 规划一次；每收到一块，GUI 线程重建一次快照；
  - 这部分已有 20 条测试；
  - **先实测，再定**（§5 关口 6）：L1 做完后，在真实 biopsy 带标签的 Step3 上测拖动和缩放；
  - 测的量：
    - 每次交接在 GUI 线程上的时间；
    - 每帧标签上传和合成的时间；
    - 标签读线程造成的界面心跳间隔变化；
    - 手势响应：和"同一视图不显示标签"相比；
  - 达标条件：
    - 交接、上传、合成三项合计，每帧 95% 线不超过 2 ms；
    - 超过 50 ms 的响应次数不增加；
  - 不达标就停下报告，建议改做 L2。
- **交接时复制**：`set_labels` 在调用时把每个平面的 uint32 数据复制进 Rust 自己的内存（一个 512×512 平面 1 MB），不借用 numpy 的内存，所以之后的延迟上传不依赖 Python 对象还活着。复制计入交接时间。
- 同一平面（按平面身份）已有纹理或已复制过的，不再复制。
- Rust 里的标签副本有上限：256 MB，按 LRU 丢弃，和标签纹理预算相同。丢弃后再需要时，从绑定下一次交来的快照里重新复制（绑定每次交的是完整快照）。

**Rust 新增**
1. `label_store.rs`：
   - 每个平面一张 R32UI 纹理（NEAREST，CLAMP），和 Python 一样，这样着色器可以逐字节拷贝（`usampler2D`）；
   - 按平面身份做键，LRU，预算 256 MB；
   - 只在 GUI 线程、上下文当前时上传。
2. `render/labels.rs`：完全按 §1.1 列出的 Python 顺序和状态画：
   - 目标 `ids`（R32UI）、`shown`（RGBA8，挂 `final` 的模板缓冲），随尺寸变化重建；
   - `final` 复制到 `shown`；
   - 每层先画 `ids`（不裁剪、不混合，按平面顺序，后者覆盖前者包括 0），再画到 `shown`（模板、剪裁框、分离混合、半径按设备像素比取整）；
   - ROI 剪裁框在屏幕外时只复制；没有可见层时不画 `shown`；
   - 画完恢复 GL 状态。
3. **呈现**：`render/output.rs` 改成"标签已合成就呈现 `shown`，否则呈现 `final`"，测试读回也分两个。
4. 着色器 `step1_gpu_labels.frag` 逐字节拷贝进 crate，纳入现有的"拷贝必须相同"测试。
5. `py/labels.rs`：
   - `set_labels(层列表)`，每层带平面（身份、uint32 数据、世界矩形）、样式、颜色、透明度、宽度；
   - 只改标签时不重合成通道：`image_submissions` 不变，`label_compositions` 增加，同 Python；
   - `readback_label_ids`、`readback_shown`（测试用）、`label_stats`（键同 Python）。

**Python**
- `Step1CoreLayer` 实现 `labels_enabled`、`set_labels`、`label_stats`、`readback_label_ids_for_test`、`readback_shown_for_test`；
- `_decide_rust` 去掉"画标签就拒绝"；
- `_start_rust_backend` 成功后照常调用 `_start_label_binding`。

**备选 L2**（只在 L1 不达标时做）：标签的 `<u4` zarr 读取、规划器、读线程都搬进 Rust。工作量多 3–4 天。

### 2.2 `gpu_memory`
1. `release_to_coarse` 和 Python 同义：只保留上一次画面在画通道的最粗级块，删掉合成目标；标签纹理保留。
2. **压力检查**：新建显存块后调用 `gpu_memory.on_layer_active`。
   - 但不在 `paintGL` 里直接调用：释放别的画布会切换当前上下文，所以记一个标记，绘制结束后用下一轮事件循环调用；
   - 调用完后，下一次绘制照常由 Qt 把本画布的上下文设为当前。
3. `set_smooth` 值没变就不做事。
4. `dispose()` 返回真实统计。
5. `gpu_bytes`：
   - Rust 按实际分配计，包括 `shown` 和 `ids`（Python 不计这两个）；
   - 记入接口文档，说明两边差这一项。

### 2.3 资源档位（CPU 缓存，按规则 4 需要授权）
- 缓存按来源分两个额度，和 Python 相同：原始 512 MB、校正 2 GB。
- 结果队列另设固定上限 256 MB（加原有的 1024 块上限），不再从缓存额度里扣。
- 进程里 Rust 部分的总上限 = 原始缓存 + 校正缓存 + 结果队列上限 + 读线程工作内存 + 规划器手里有、但已不在缓存里的块 + 标签副本（256 MB）。
  - 读线程工作内存：每线程不超过 32 MB。组成：
    - 校正现算的一片数据（≤ 400 万像素 × 4 字节 = 16 MB，`MAX_REDUCTION_ELEMENTS`）；
    - 正在解压的一个数据分块（1024×1024×4 = 4 MB）；
    - 输出块的和与计数（513×513×16 字节 ≈ 4.2 MB）；
    - 结果块（≤ 1 MB）。
  - 6 个线程合计 ≤ 192 MB。以后改片的大小要同时改这个数。
  - 块用 `Arc` 共享：同一块在缓存、队列和规划器里只按一份计；
  - 规划器手里的块受视野限制（目标层加粗层），另外计出它的最大值；
  - `cache_stats` 分项上报这几部分和合计；
  - 测试：20 通道和校正通道各跑一个场景：
    - 分项合计不超过算出的上限；
    - 进程实际内存（RSS）的增长也不超过这个上限。
- 依据：Python 路径用的就是这两个额度；加起来 2.5 GB 多，在 EDGE 档 12 GB 内存目标之内。
- 标签纹理不计入通道准入（同 Python），只计入 `gpu_bytes`。
- 显存额度不变。

### 2.4 montage 共存
- 不改 montage，仍用 Python 画布；它自己的 GPU 像素测试在 Rust 模式进程里照常通过（像素不变）。
- 新增真正的双画布测试（Rust 模式，同一进程）：
  - 整片视图已在用 Rust 时，打开 montage 标签页，montage 出图；
  - 两个画布都在 `gpu_memory` 里，总量是两者之和；
  - 切换平滑，两个画布都按新设置重画；
  - 来回切换标签页后，整片画面和切换前逐像素相同；
  - 隐藏的整片画布在 `release_hidden` 时释放，montage 画布不受影响；
  - GL 无错误。
- **不做** montage 与整片视图的逐像素比较：Python 里两者本来就是不同的绘制程序，平滑时图块边上的取样也不同（§1.4）。这一条改变了总方案的要求，见 §8 第 3 条。

### 2.5 运行中回退

**读图出错**
- 出错时写一次通知字节，让 GUI 及时看到。
- 同一块最多重试 2 次：在下一次规划时重新请求，间隔至少 200 ms，所以画面不动时也会重试。
- 计数：
  - 每块的失败次数，这块读成功就清零；
  - 全局"连续失败"次数，任何一块读成功就清零。
- 触发：当前画面需要的某一块用完重试仍失败（共 3 次），或连续失败 8 次。阈值是常数，测试可改。

**其他触发**
- 画图报错。
- GL 上下文丢失后重建失败。

**回退顺序**（总方案 §5.3）
1. 出错的这一帧不呈现；
2. 在绘制回调里只记下原因，所有后续动作放到下一轮事件循环，不在绘制中途换画布；
3. 立刻隐藏 Rust 画布，不再画，避免混入半幅画面；
4. 停通知；
5. 通知 Rust 读线程退出，不等待；
6. 当前上下文里释放 GL；
7. 标签绑定：通知它的读线程退出，**不等待**（回退时 `dispose` 的等待改为 0），线程交给下面的"关闭中线程"登记；
8. 在同一镜头上换成 Python 画布（同 R2 的换法），新建标签绑定。

**两个"完成"分开计**
- 回退完成：Python 画布开始画；
- 线程结束：后台陆续结束。

**关闭程序**
- 现状：正常退出时主窗口关闭 Step3 的挂载（`ui/main_window.py:7330`），走到标签绑定的 `dispose()`，默认等读线程 10 秒。
- 改为：
  - 标签绑定的 `dispose()` 只通知读线程结束，不再等待，把线程交给"关闭中线程"登记（Python 和 Rust 两种画法都这样，见 §8 第 5 条）；
  - Rust 读线程保留句柄，也登记；
  - 程序退出时，所有登记的线程合计最多等 1 秒，超时就记录后放手。
- 测试走真实的关闭路径：主窗口打开 Step3（带标签，两种画法各一次）后关闭，退出等待不超过 1 秒，日志里线程都已结束或被记录。

**测试**
- 用故障注入开关 `BLOCK01_RUST_TEST_FAULT`（只在测试里用）在读图、绘制、重建三处注入错误，走真实的计数和阈值逻辑，不直接调用回退。
- 读图：
  - 同一块失败 2 次后成功，不回退；
  - 第 3 次失败，回退；
  - 7 次连续失败后成功，不回退；第 8 次连续失败，回退；
  - 画面不动时也能达到阈值。
- 每种回退：
  - 回退后画面稳定且是 Python 画的；
  - 中间没有呈现过失败帧；
  - 原因写进 `_rust_refused`；
  - 旧调度器启动；
  - 带标签时标签照常出现；
  - Rust 读线程最终归零；
  - 退出等待不超过 1 秒。

## 8. 需要用户决定的事
1. **标签采用 L1**（只把纹理、合成、呈现搬进 Rust，规划和读取留在 Python），作为总方案的有条件例外：做完先实测（§2.1），不达标就停下报告，再决定是否做 L2。推荐 L1。

3. **总方案"montage 和整片两套合成必须逐像素一致"改为"测共存，montage 像素不变"**（§2.4）。理由是 Python 里两者本来不是同一绘制程序。
