## 2. 计数窗口修正

```python
# 之前（错）
computed_before = set(tile_computes)
...
recomputed = [k for k in tile_computes[len(computed_before):] ...]

# 现在
computed_mark = len(tile_computes)
...
recomputed = [k for k in tile_computes[computed_mark:] ...]
```

**为什么这是真 bug 而不只是风格问题：** `len(set(...))` 只在「没有任何 key 被算过两次」时
才等于 `len(list)`。一旦有重复，切片起点会**偏早**，于是**切换之前**做的计算会被算到切换头上，
门会以错误的理由变红（或在别的排列下以错误的理由变绿）。

**如实说明其今日影响：** 今天这条门是**侥幸通过**的 —— 该 rig 下确实没有 key 被算过两次
（那是另一条门 `test_the_same_correction_key_is_never_computed_twice` 的断言，不该成为
本门的隐含前提）。所以修正**没有改变今天的结论**，它移除的是一个隐藏依赖。
全仓复查确认同样写法**没有第二处**。

## 3. 新门一：首次方法切换不重新读取 raw

`test_the_first_flip_re_reads_no_raw_for_the_finished_picture`，四条轨迹参数化
（TopHat→cuCIM、cuCIM→TopHat、Original→TopHat、Original→cuCIM）。

**范围写死，不含模糊余量：** 断言对象是**画面真正由之构成的**瓦片 ——
当前层可见集 + level+1 **覆盖集**。前瞻 ring 的 raw **确实会读**（HOT 从不准备它，
它也不属于这一帧），所以它是**按构造排除**的，不是靠一个容忍值；ring 本身由
`test_the_lookahead_ring_is_the_only_level_plus_one_work_left` 守着。

断言两件事：

1. 切换窗口内，`provider.tile_reads` 里**没有一条**落在这一帧的任何瓦片上；
2. 切换窗口内，该通道的 `provider.reads`（整层 `read_region`，即 floor 与 gain
   calibration 的输入）**一条都没有** —— floor 本来就该是缓存命中。

**观察方式不改变被观察的路径：** 用的是 rig `_Provider` 自己已有的 `tile_reads` /
`reads` 记录，没有包装、没有替换读取函数。

**这道门不能靠「匹配不到任何东西」而通过：** 门内先断言同一个匹配器在 arrive 阶段
**确实能找到**这些瓦片的读取记录，然后才断言切换后为零。坐标约定、通道、字段顺序
写错都会在这一步被抓住。

**结果：四条轨迹全部通过**，切换窗口内帧内瓦片 raw 读取 = 0、整层读取 = 0、floor job = 0。

## 4. 新门二：切换后的画面与未优化前逐像素一致

`test_the_flipped_picture_is_identical_with_and_without_preparation`，四条轨迹参数化。

**参照系是「本条工作线之前」的真实行为**，而且只走公开 API：
`open_full_image(with_hot=False)` —— 不装 HOT specs provider 时 `start_hot()` 直接返回、
什么都不在后台准备，于是它的切换从零算 floor 和瓦片。两次运行：

- 同一条数据集路径（`providers` fixture 按路径发放同一个 `_Provider`），
  所以两边 **source identity 完全相同**，下面可以连瓦片的完整 `CorrectionKey`
  一起断言，而不是为一处差异开脱；
- 各自建自己的 stack、scheduler、caches、pools，**参照运行算出来的东西无法交给准备运行**；
- 同一个相机、同一组参数、同一个 `show_source` 入口；
- 两边都等到画面真正画完（floor ready 且 ctx 匹配、可见集全部驻留且全部入池）。

**比的是屏幕上的东西，不是缓存：** 逐项比较

- 每个可见瓦片 `ImageItem` 的 `image` 数组（`np.array_equal`，逐像素）、
  `levels`、颜色表 `lut`、`boundingRect` 放置、`isVisible()`、以及它的 `CorrectionKey`；
- corrected floor 的 `image`、`levels`、`lut`、放置、可见性、ready、level、stride；
- 每层显示增益表 `_level_gain`；
- 仍在透出的 RAW 瓦片集合；
- 钉住的 overview 的可见性与是否有像素。

**这道门不能靠「比了个空」而通过：** 先断言参照运行至少有 4 块入池瓦片带像素、
至少有一块真的可见、floor 像素非空，然后才进比较。

**修掉一处我自己写的空断言（如实记录）：** 初稿里有一项 `raw_layer_visible` 读的是
`ExploreView.raw_underlay_item` —— **这个属性根本不存在**，于是它在两边都是 `False`，
比了等于没比。已换成 `_update_layer_visibility()` 真正驱动的两个图层：RAW 瓦片池里
实际可见的条目集合，与钉住的 `overview_item`。

**结果：四条轨迹全部通过**，逐像素、逐放置、逐映射一致。
