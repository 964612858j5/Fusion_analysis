### 0.3.3 根因：**那一帧只有 DAPI，而 DAPI 是 `original`（raw）通道，raw 只按 bbox 裁**

`submissions.jsonl` 在抓取前后的提交里，通道集合始终是 **`['DAPI']`**；
该项目的 `correction_config.json` 里 **没有任何 corrected 通道**（`channel_decisions` 全为 original）。

关键的不对称：

- **corrected 通道**由 Step0 写盘时用多边形掩膜置 0（`ui/step0/search_ctrl.py:2424`
  `out[~poly_mask[...]] = 0`），所以多边形之外是黑的；
- **raw/original 通道**在 `viewer/step1_source.py` 里**只按 bbox 裁**
  （`clip_to_roi`），该文件**通篇没有任何多边形逻辑**（唯一的 "polygon" 是一句注释）。

而用户这次画的 ROI 是 **9 点不规则多边形**，其面积只占外接矩形的 **79.4 %**

于是屏幕上：**DAPI 铺满整个矩形**，其中约 **20.6 %（约 2 700 万个 level-0 像素）**

**这正是 G3.2c 按规格实现的行为**（裁到 `roi_bbox_fullres`，
本块明确"不做多边形精确裁切"），也正是用户看到的画面。
**因此：bbox 裁切在真机上已验证生效（框外 0 像素），而用户的诉求需要多边形裁切——
这是本块范围之外的另一件事。**

### 0.3.4 不做修改，先提扩围（最小方案）

**建议方案（最小、可回退、只动显示）：** 在 `ui/step1_gpu_layer.py` 内，

**回退：** 不传多边形即回到今天的矩形裁切。
**另两条不推荐：** 在 `viewer/step1_source.py` 给 raw 读取加多边形掩膜（改科学读取规则，
且影响 CPU 路径）；或让 Step0 额外写多边形掩膜产物（改产物格式）。
**以上均未实施，等待裁定。**

## 二、坐标与换算（先核实，不猜）

沿公开路径核实的事实：

1. **来源表**：`Step1SourceTable.roi_bbox()` 返回 level-0 的 **`(y0, y1, x0, x1)`**。
2. **层的矩形**：`ViewportSnapshot.world_rect` 与 `RawPlane.world_rect` 都是
   **`(x0, x1, y0, y1)`**（`_validate_snapshots` 解包即为此序）。**两者顺序不同**，
   mount 只转换这一次。
3. **屏幕方向**：`ui/shaders/step1_gpu.vert` 给出 `v_screen_uv`，
   `step1_gpu.frag`（PASS_SOURCE）里
   `world.y = u_view_rect.w - v_screen_uv.y * (w - z)` ——
   即 **framebuffer 的底行对应最大的世界 y，世界 y 向下增长**；
   `readback_rgba_for_test()` 再 `flipud` 成 C1 的左上行序。
4. **像素中心规则**：像素 `i` 的中心世界坐标为 `x0 + (i+0.5)·step`。
   保留「中心落在 bbox 内」的像素——与管线其他地方「这个像素是哪个样本」的口径一致。
5. **DPR**：裁切按 `viewport.physical_size` 计算，与 FBO 尺寸同一坐标系。

## 三、为什么不需要改 shader

最终图像由 `_finalize()` 的一次全屏 pass 写进 `final` 目标。裁切因此可以完全用
**`glScissor` + 一次全清**表达：

- 先在 **scissor 关闭**下把 `final` 清成 `(0,0,0,0)`；
- 再打开 scissor 到 bbox 的像素矩形，执行原来的 draw；
- 立即关闭 scissor（后续 pass、下一次 submit 和 `paintGL` 的 blit 共用同一 GL 状态）。

这样 **bbox 外必然 alpha=0**（被清掉且没有被画到），**bbox 内与裁切前逐像素相同**
（同一个 pass、同一段 shader、同一批纹理）。
**没有修改任何 shader 文件，也没有新增 uniform。** 若将来要做多边形裁切，
那才需要片元级判断——本块不做，也没有为它预留机制。

`roi_scissor_box()` 是纯函数，可独立测试；它与逐像素暴力枚举在 4 000 组随机
（视口、bbox、尺寸）上**完全一致**。

## 七、限制与未决

1. **像素粒度，不是亚像素抗锯齿。** 边界按「像素中心在不在 bbox 内」判定：
   边界像素要么整块保留、要么整块清掉，**不做边缘羽化**。
   这正是「bbox 外 alpha 必须为 0」与「bbox 内像素不变」两条要求同时成立的唯一方式。
2. **只裁矩形 bbox，不做多边形精确裁切**（本块明确排除）。ROI 多边形内部之外、
   bbox 之内的区域仍按现有规则绘制。
3. **CPU fallback 未改**：它走 `Step1ComposedLayer` 的既有路径，本块一行未动，
   因此 CPU 回退下的边界行为与从前相同。
4. **不得记为真机通过，且真机已报告仍然失败（见 §零）。** 以上全部是 offscreen
   （`QT_QPA_PLATFORM=offscreen`）真实 GPU 上下文下的 FBO 与合成输出；
   本轮**未能复现**用户看到的越界。最可能但**未证实**的解释有两条：
   其应用进程早于 `ui/step1_gpu_layer.py` 的写入时间 18:29:50 启动（跑的是没有裁切的旧代码）；
   或该次运行落在**未裁切的 CPU 回退**上。
5. **CPU fallback 仍未裁切**（本块范围明确排除）。若真机确认 backend 是 `cpu-fallback`，
   那是另一块的工作：要裁切 `Step1ComposedLayer` 的像素路径属白名单外，**须先裁定再实施**。
5. 本块**未触碰** G3.2b.5A 的 Patch 晃动诊断线、`viewer/step1_source.py`、Step0 与科学来源规则。
