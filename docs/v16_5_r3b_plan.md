  - 总方案 `docs/v16_5_rust_viewer_plan.md` §5.1 第 1 条（标签 `<u4`、Blosc lz4，作为 Rust 图源）和契约 1（性能核心归 Rust）。

## 1. 现状（已核对代码）

- **R3 的 L1 实测（A9 §52.4）**：
  - 每次 `set_labels` 的 95% 线 3.8 ms（第一轮 4.5 ms），其中数据交接 2.6 ms（第一轮 2.8 ms），门槛 2 ms；
  - 交接的中位数 0.16 ms，超标来自"新到一个 1 MB 标签图块"时的两次复制，Python 约 1.3 ms，Rust 约 1.1 ms。
- **`Step3LabelBinding`**（`ui/step3_label_binding.py`，581 行）做的事：
  1. **跟随镜头**：每个 `interaction_event` 最多每 33 ms 规划一次（`MOTION_INTERVAL_MS`，:297），停手时再规划一次；跳转立即规划。
  2. **规划**（`_plan`，:332-427）：
     - 用控制器快照的层级和可见图块，加一圈；
     - 以可见范围的中心按距离平方排序，中心先。距离相同时，顺序由 Python 集合的遍历顺序决定，没有明确规则（:358）；
     - 要读的顺序是：可见-细胞、可见-细胞核、一圈-细胞、一圈-细胞核；
     - 目标层以外、仍压在视野下的旧层图块保留；
     - 预算 256 MB 算的是"常驻 + 在读 + 已到未收"（读线程取任务前核对，:489）；规划时超了，按"先丢最远的旧层，再丢一圈，再丢离中心最远的可见块"处理，并给出状态说明。
  3. **金字塔**：缺金字塔时先建（`ensure_pyramid`，`core/step3_masks.py:658`，可取消）。写不进运行目录就建在内存里（:693），这一结果是建好之后才知道的。建好之前什么都不读，连第 0 级也等。
  4. **读取**：一个读线程调用 `read_label_tile`（:715-756）：
     - 第 0 级读掩膜，减去外接框原点；粗级读金字塔对应层，减去该层原点；
     - 超出部分填 0；金字塔里没有的层给全 0 块；
     - 世界矩形按每轴不取整的比例算。
  5. **丢弃**：镜头移走后不再需要的排队请求丢弃（`stale_dropped`）；结果到达时，先看是不是旧数据源（`late_dropped`，错误也一样），再看是否还需要。
  6. **交出**（`_push`，:560）：每接收一块就重建整个快照交给画布。顺序：旧层先，离目标层越远越先，目标层最后；同层按行、列。
  7. **其他**：
     - 暂停：放开镜头、清空队列、取消在建的金字塔，恢复时重建；
     - 新数据源：换"代"，旧的全部作废（数据源会在已有绑定上更换，`ui/step1_viewer_mount.py:626`）；
     - 样式改变：颜色、透明度、粗细、轮廓或填充只重画；把隐藏的掩膜重新打开会重新规划，缺的块会读（:151）；
     - 状态：`mask_status`（有无数据源、粗级为什么不画、是否在建、`unavailable_here`、预算说明、错误）和 `stats`。
- **存储格式**：已核对的 11 份真实掩膜（`analysis_pipline/outcome`、`Chaofan` 下 9 份、`test_Tonsil` 1 份）和 R3 建的金字塔，都是 zarr v2、`<u4`、1024 分块、Blosc lz4、字节重排（shuffle 1）、无过滤器、`.` 分隔符、填充值 0。
- **Rust 现有的 zarr 读取**（`zarr_v2.rs`）只接受 `<f4`，拒绝过滤器（:41）、`/` 分隔符（:47），按位重排拒绝（`blosc.rs:81`），输出是 f32。
- **镜头**：Rust 绑定已把控制器快照的层级、第 0 级视野范围、序号交给核心（`set_view`）。核心用同样的网格规则算可见图块（R2 起和 Python 逐像素一致）。

## 2. 要做的

### 2.1 Rust：标签图源和读取
1. `label_source.rs`：每种掩膜（细胞 / 细胞核）的清单，Python 交来：
   - 第 0 级 zarr 路径、外接框原点、形状；
   - 金字塔各层（层号、路径、原点、形状），只限建在磁盘上的金字塔；
   - 打开时核对每个数组的 `.zarray`。必须满足：`<u4`、二维、C 顺序、无过滤器、`.` 分隔符、Blosc lz4、字节重排或不重排、整数填充值。任何一项不符，这个查看器的标签整体改用 L1（§2.6）。
2. `zarr_v2.rs`：加一条输出 `u32` 的读取，和现有 `f32` 读取分开：
   - 同一套解压，按 4 字节复制，不经过浮点；
   - 缺块填 `.zarray` 的整数填充值；
   - 校正数据的 `f32` 路径和它的填充语义一行不改。
3. `label_read.rs`：`read_label_tile` 的完整语义（§1 第 4 项），一次请求内每个分块只解压一次。

### 2.2 Rust：规划
`label_plan.rs`：重现 `_plan` 的完整语义，按 (代, 种类, 层, tx, ty) 作键。
- **距离相同时的顺序**：两边都改成"距离，然后 ty，然后 tx"。Python 一侧只在排序键上加这两项，这是对现有 Python 行为唯一的改动：只影响距离相同的块谁先读，见 §8 第 5 条。
- 要读的顺序保持：可见-细胞、可见-细胞核、一圈-细胞、一圈-细胞核。
- 保留旧层的规则、预算三级丢弃、预算说明的措辞都不变。
- 预算口径和 Python 相同：常驻 + 在读 + 已到未收，不超过 256 MB。读线程取任务前预留这块的字节；读完、出错、过期、作废、关闭，每条路径都释放预留。

### 2.3 Rust：读线程、常驻块、交给绘制
- **读线程**：标签单独 1 个读线程（同 Python）。
- **锁**：自己一把任务锁加一个条件变量，从不嵌套线程池的队列锁或缓存锁。
- **结果**：放进有界结果队列；读完写一个通知字节，和通道图像共用通知。
- **取结果**：绘制时不阻塞地一次取完。到达时先核对代（旧数据源的结果、包括错误，直接丢弃，计 `late_dropped`），再核对是否还需要（不要就丢弃，计 `late_dropped`）。
- **唤醒**：等预算的读线程，在暂停、换数据源、关闭、预留释放时都会被唤醒。
- **关闭**：线程句柄交给 R3 的关闭中线程名单，程序退出时共用那 1 秒。名单现在是线程池私有的，新增一个对外的登记函数（`pool::register_closing`），等待逻辑不变。
- **常驻块**：规划保留的块存进 R3 的 `label_store`（就是绘制用的副本）。规划释放一块时，副本立即删除，不再等内存压力。读线程临时内存按实际分块大小算：读一块（边长 T）最多涉及 (T + 分块高) × (T + 分块宽) × 4 字节的解压数据，加上输出块本身；用打开时读到的分块大小算出，计入 R3 的内存上限。
- **交给绘制**：顺序同 `_push`，用 R3 的 `render/labels.rs`，绘制部分不改。

### 2.4 Python：薄绑定 `ui/step3_core_labels.py` 的 `CoreLabelBinding`
- 对挂载暴露和 `Step3LabelBinding` 相同的接口：`set_sources`、`set_style`、`style`、`mask_status`、`stats`、`pause`、`resume`、`paused`、`sources`、`dispose`、`status_changed`、`level_shapes`、`tile_size`、`update_viewport`。
- 镜头：核心在每次 `set_view` 时规划，见 §2.5。
- 留在 Python 的只有：
  - **金字塔建造**：只在缺金字塔时、一次性，Python 线程跑 `ensure_pyramid`，可取消。这个线程在关闭时登记进关闭中线程名单。暂停时取消、恢复时重建，同现在。
  - 状态文字的拼装、样式。
- `stats` 的键不变。`pushes` 的含义改为"核心把新块交给绘制的次数"，写进接口文档。

### 2.5 节奏
- 核心在每次 `set_view` 时都规划，和通道图像一致，不再有 33 ms 节流。
- 读请求照样按"还要不要"丢弃。
- 新到的块在下一帧画出，不再有交接。

### 2.6 何时用 L1（Python 规划读取、Rust 画）
以整个查看器为单位，在下面三个时刻判断：
1. 设数据源时（`set_sources`）；
2. 金字塔建好时；
3. 数据源被更换时。

只要有一种掩膜满足下列任一条件，这个查看器的标签就改由内部的 `Step3LabelBinding`（R3 的 L1 路径）负责：
- 金字塔建在内存里；
- §2.1 的格式核对不通过。

切换时：
- 先让核心停止标签规划和读取（清空它的标签数据源，读线程丢弃在手的任务），再建立 L1 绑定；
- 样式、暂停状态和当前数据源（含刚建好的金字塔）原样带过去；
- 状态里写明原因。

之后再换成 Rust 能读的数据源时，L1 绑定关闭（不等待，线程登记），回到核心读取。整个查看器回退到 Python 画布时，照旧用 `Step3LabelBinding`（R3 已有）。

### 2.7 读错误
- 标签块读错：状态立即显示错误（同 `_last_error`），这一块不画，通道画面照常，不触发整个查看器回退（同 Python）。
- 新数据源清掉错误。

## 3. 比对契约

### 3.1 规划比对
- 用一个确定的测试装置，把同一串事件交给两边的规划：镜头快照、常驻集合、在读集合、已到未收集合、预算，包括预算不够的情况。
- 比较：
  - 要读的块和顺序；
  - 保留的块；
  - 释放的块；
  - 队列内容；
  - 预算说明。
- Python 一侧在线程停住的绑定上直接设置这几个集合后调用 `_plan`。这是测试手段，不改产品行为。
- 在两边都采用 §2.2 的排序规则之后，要求完全相同。

### 3.2 读取比对
- 对随机的层和块，Rust 读出的 uint32 和世界矩形与 `read_label_tile` 逐值相同。
- 包括边缘、超出、原点不为 0、金字塔缺层、缺块。

### 3.3 像素比对
- 同一组镜头下，稳定后 Rust 规划读取的标签画面和 Python 路径逐像素相同（id 图和呈现画面）。
- 范围：合成数据、凹多边形 ROI、biopsy 加真实细胞掩膜（整片、中等、最细三个视野）。
- 中间过程（旧层在目标层到齐前垫底）由 §3.1 的保留集合和 §2.3 的交出顺序保证，不靠像素。

### 3.4 "已稳定"的判定
在 R3 的条件之外，再要求核心的标签队列为空、没有在读的块、规划要的块都已常驻并已上屏。

## 7. 风险
- **规划细节多**：用 §3.1 的确定性比对兜底，不靠肉眼。
- **读线程和规划的竞争**：沿用线程池已验证的做法（规划写入集合，开工前核对，到达时再核对）。
- **两条标签路径并存**：切换时机限定在 §2.6 的三个时刻，状态写明原因。

## 8. 需要用户决定的事
1. 标签单独 1 个读线程（同 Python），不和通道图像共用线程池。推荐。
2. 去掉 33 ms 的运动节流：每次镜头变化都规划，和通道图像一致。推荐。
3. 金字塔建在内存里或掩膜格式不符时，这个查看器的标签用 L1（Python 读、Rust 画）。推荐。
4. 授权新增 Rust 的标签规划器、读线程和常驻缓存（规则 4）。
5. Python 标签绑定的排序键加上"行、列"：距离相同的块从此有固定的先后顺序，原来由集合遍历顺序决定。这是对产品默认路径的一处微小改动，只影响同等距离块的读取先后，不影响画面结果。推荐，否则两边的规划无法严格比对。
