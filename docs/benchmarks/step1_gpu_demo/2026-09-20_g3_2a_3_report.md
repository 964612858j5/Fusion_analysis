## 1. 拖动冻结：原因、修复与前后证据

### 原因（只读核对后确认）

`_interaction_event()` 对每个非 `NAVIGATOR_JUMP` 事件都调用 `self._motion_timer.start(...)`。Qt 的单次 `QTimer.start()` 会把正在运行的 timer 的 timeout **往后推**，所以只要相机还在动（事件间隔 < 33 ms），timeout 永远不到；而 timer 一直 active，`not isActive()` 也为假，于是整段手势里只有**第一次**事件做了一次更新。

`viewer/explore_view.py` 早已给这一类 bug 命名并避开：

> THROTTLE, not debounce: restarting the timer on every range event means it never fires at all while the camera keeps moving … Leaving an already-running timer alone makes it fire every MOTION_MS *during* motion instead.

### 修复（最小）

复用同一原理：`NAVIGATOR_JUMP` 立即处理并直接返回；其他运动事件**只在 timer 未运行时**才立即更新并启动 timer，已经在跑的 timer 不再被重启。33 ms 配置未动，没有新增 timer、线程、事件总线、coalescer、缓存或调度器，共享 `ExploreController` 未碰。

### 前后证据

用真实 Qt 事件循环驱动的连续拖动（每 10 ms 一步，约 1.9 s，全程不 `processEvents()` 打断、不等待事务完成）：

| 指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 相机步数 | `188` | `187` |
| 手势期间 GPU submit 次数 | **`6`** | **`108`** |
| submit 用过的**不同**相机中心数 | **`1`** | **`93`** |
| 最后一次 submit 的中心 | `518.0`（起点） | `1622.0`（跟到终点） |
| submit 最大间隔 | `5.1 ms`（然后就再也没有） | `38.7 ms`（≈ 一个 33 ms 窗口） |
| provider 读取增量 | `7` | `7`（未增加） |
| raw texture 上传增量 | `5` | `15`（拖进了新区域，属应有工作） |

修复前：相机从 `(262,262)` 走到 `(1384,1384)`，GPU 用的视口始终停在起点，松手后才跳到终点——与用户描述完全一致。

**热区拖动**（在已加载区域内来回，1 s）：`140` 次 submit，**provider 读取增量 `0`、raw 上传增量 `0`**。跟随相机没有带来任何新的读盘或纹理上传。

**手势内的真实像素采样**（明确标注为强制 `grabFramebuffer()`）：同一次未松手的拖动中，在相机 `x0 = 542 / 764 / 986` 三点各取一帧，得到 **3 张互不相同**的图像（sha256[:16] `b1d1281390855ac7` / `6a5b631a40539987` / `173c05ac2a8780d1`）。

**呈现侧观测：** 挂载 widget 收到 `284` 次 Qt paint 事件；`frameSwapped` 为 `0`，因为离屏平台不做缓冲交换。**这两个数字都不是显示器的 input-to-photon 延迟**，本报告不作此声称。

## 2. 其余问题：已测事实与未确定原因

### A. 首次进入与"停下后仍不清晰"

合成台架（3 级金字塔）**没有复现**。首次进入、不做任何手势：目标 level `1`（该缩放下正确）、可见 `9` 块、fine 全部 `9/9` 就位、`fine_budget_refused` 为空、无额外读盘、画面非空。

**未确定原因。** 台架与真机的差别是金字塔深度与读取成本（真机 4 级、冷读 22–75 ms/块）。可能仍在但本轮未证实的路径：目标 level 选择、`gesture_quiet` 之后的最后一轮 epoch、以及校正通道的归约（本台架没有 corrected product，**这一类成本完全没有测到**）。需要真机或带 corrected product 的数据集才能定位，不在本轮授权内。

### B. 连续远距离空降

两次快速连续点击（真实 `mount.jump_to_point`）：两次都被接受、相机都在调用内改变、各自在调用内完成 1 次 submit 并请求 4 块 fine，调用耗时 `4.1 ms` / `6.6 ms`。**"第二次无反应"在热缓存下没有复现。**

把读取人为压到 120 ms、并用**生产默认的 8 个 I/O worker** 重测（冷缓存、每次落点 24 块读取）：

| 点击 | 请求 | 实际读取 | 目标上屏耗时 |
| ---: | ---: | ---: | ---: |
| 1 | 44 | 24 | `327.0 ms` |
| 2 | 44 | 24 | **`390.7 ms`** |

第二次比第一次慢约 `64 ms`，但**没有卡死**。机制与 scheduler 自己的契约一致：`cancel_generation()` 只丢弃尚未开始的排队项，**已经开始的读取一定会跑完**，所以第二次落点的瓦片要等第一次被放弃的读取让出 I/O worker。真机上冷读 22 ms/块、视口 12–40 块，这个等待会放大到几百毫秒，用户可能读成"没反应"。**这是有证据的假设，不是已证实的根因**；确认需要真机。未修改 Tissue Preview 视框链的任何代码。

### C. patch 往返与取消/重新启用

同来源、同显示参数：

| 操作 | scheduler 请求 | provider 读取 | raw 上传 | GPU submit |
| --- | ---: | ---: | ---: | ---: |
| patch A | 4 | **0** | **0** | 6 |
| patch B | 1 | **0** | **0** | 3 |
| patch A（返回） | 4 | **0** | **0** | 6 |
| 取消通道 | 0 | **0** | **0** | — |
| 原地重新启用 | 4 | **0** | **0** | 6（合计） |

**结论：往返与重新启用没有重复读盘，也没有重复上传纹理。** 看起来"重复加载"的是 scheduler 请求数与 GPU 重绘：请求命中 raw cache 同步返回，纹理按 plane identity 命中 G1 的 512 MiB LRU。重复请求 ≠ 重复读盘；GPU 重绘 ≠ 重新跑 cuCIM。**注意：本台架没有 corrected product，因此"校正粗层归约"这一类成本本轮无法测量**，它属于 G3.2b 的范围。

### D. 新通道首次出现

台架时间线（读取近乎瞬时）：`enable` 返回 `149.5 ms` → 完整 coarse 完成 `155.0 ms` → 首块 fine `155.0 ms` → 目标视口 fine 完成 `155.2 ms`；9 块 coarse + 4 块 fine，13 次读取、13 次上传。

**串行等待确实存在且是设计使然**：一个通道的 fine 只在它的**完整 coarse 事务**落地后才开始规划（`_accept_result` 的 coarse 分支）。真机上这段等待 = 完整 coarse 的块数 × 冷读时间，之后才轮到 fine。演示数据集实测：

| 真实读取成本（`/sda1/Fusion/benchmark/tonsil/…Tonsil.ome.tif`，tile 512） | 冷读 | 第二次读 |
| --- | ---: | ---: |
| 最粗层（level 3）一块 | `74.65 ms` | `1.49 ms` |
| level 0 一块 | `22.36 ms` | `0.91 ms` |

该数据集最粗层只有 1 块，所以 coarse 串行约 `75 ms`；随后目标层 12–40 块在 8 个 worker 上约 `35–110 ms`。**这是读/解码成本，不含校正归约。**

## 4. 最小后续建议（均需追加授权后才实施）

1. **远距离连续空降的 I/O 让位**（对应 B）。建议先在真机确认；若确认，最小方向是让被放弃落点的**尚未开始**的读取更早出队（已由 `cancel_generation` 做到）并复核 `io_workers` 是否适配演示分辨率。**需要授权**，且触及共享 scheduler 配置，不在本轮白名单。
2. **新通道 coarse→fine 串行**（对应 D）。最小方案是：完整 coarse 仍**原子发布**不变，但在 coarse 事务进行的同时就为该通道排入当前视口的 fine 请求（仍按 G2.1 的 `200` 优先级排在 coarse 之后），这样 coarse 一落地 fine 已在路上。**需要授权**（改变供给顺序）。不得以隐藏画面、旧来源冒充、取消 coarse 原子性或新建预取系统替代。
3. **校正归约成本**（对应 C/A 的缺口）。需要带 corrected product 的数据集才能测。**属 G3.2b，不在本轮**。
4. **首次进入/永久模糊**（对应 A）。本轮未复现，建议在真机上开启本脚本的诊断字段复测。**只需数据，不需要代码授权。**
