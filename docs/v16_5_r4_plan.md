## 2. 测量规则（对所有批次）

**测量用的旧版本副本**
- 复制 `final_root` 为 `a9_bench/r4_final_root`。
- 只把其中的两个测量工具换成当前版本：
  - 测试驱动 `scripts/a9_drive.py`：补上"激活主窗口"；
  - 它启动的注入工具 `scripts/a9_xwheel.py`：带逐次发送记录，驱动从自己所在的目录启动它。

  产品代码一行不动。
- 两个版本每轮都要在日志里有 `a9.activate ok=True`，否则这一轮算测量失败。

**清缓存**
- "冷 / 热"指操作系统的文件缓存。每轮都重启程序、重新打开项目。
- 冷读：每次启动程序前、每次冷读重试前，都清这份图像文件的缓存（`a9_drop_file_cache.py`）。
- 热读：每个场景先用 Rust 跑 1 轮预热，不计入结果。20、3、69 通道各预热一次。

**屏幕检查**
- 每轮前后各跑一次呈现间隔检查：最小的 QOpenGLWidget 连续呈现 3 秒，相邻两帧间隔的中位数在 15.7–17.7 ms 之间、95% 线小于 20 ms，才算通过。
- 同时查一次锁屏状态。
- 这一轮之后的检查不通过，就把这一轮判为测量失败。
- 检查结果写进批测日志。

**测量失败和产品结果分开**
- 只有**另有独立证据**的，才算**测量失败**，可以重跑：
  - 屏幕检查不通过；
  - 窗口没激活（日志里没有 `a9.activate ok=True`）；
  - 注入工具 `a9_xwheel.py` 自己记录到没送进目标窗口：
    - 发送时指针下的窗口不是目标窗口；
    - X 报错；
    - 找不到目标窗口。

    要在注入工具里加上逐次记录（发送时指针所在的窗口和错误），三方相同。
  - 程序没能打开项目，并且原因在测量这边，日志里能看到（例如场景文件路径错、显示器连不上）。
- 下面这些都**不算**测量失败的证据：
  - 画面没变：可能是程序卡住，也可能是变化在采样横带以外；
  - 程序没收到输入记录：程序这边收到 X 事件的记录 `a9.wheel_rx` 缺失，也可能是程序的问题；
  - Odon 控制接口还在应答。

  这些情况一律按产品结果计入。这条对三方相同，比较时照 §2 的统一算法算，不另开例外。凡是"我们不比 Odon 差"的结论依赖 Odon 的截断值（它那边是"没响应"或"超过窗口"），报告里在这一项旁边标"依赖 Odon 截断值"，并列出 Odon 那几轮的原始记录，由读者判断。
- 下面几种算**产品结果**，照实计入、不重跑：
  - 回退到 Python；
  - 产品报错、程序没能打开项目（原因在产品这边或查不清）；
  - 慢；
  - 截图窗口内没稳定；
  - 注入后没观察到画面变化。
- 每次重试都保留原记录（换目录名，不删），并写明原因。
- 同一轮重试 3 次仍失败，这一轮记为"缺失"，配对结果里标出来；不再加跑，不挑数据。

**每一轮、每种手势的停手稳定，只有三种记法**
1. **稳定于 X ms**：参考画面是最终画面，且在 X ms 后画面不再超出差异门槛。
2. **超过窗口**：截图窗口内没稳定，**或者参考画面不是最终画面**（还在加载，就是在窗口内没完成）。算作比任何稳定时间都慢。
3. **缺失**：这一轮因测量失败重试 3 次仍无效。

参考画面（停手后 2300 ms 的最后一张截图）是否最终，三方用同一条主判据：
- 时段：从"停手后 1500 ms"那张截图的**实际拍摄时刻**，到下一个手势的标记时刻；最后一个手势用结束标记。名义上约 1 秒，实际按记录的时刻算。
- 这段时间里，`a9_pixwatch` 记录不到画面变化，**并且**它在这段时间里确实一直在采样。

  它现在只在画面变化时写记录，被提前结束时连采样统计也不写。所以要改：每秒写一条采样计数。缺这段采样记录的，参考画面判为"不能确认"，按"超过窗口"计。

另加各自的旁证：
- Rust 和旧版本：程序内目标层完成的时刻早于最后一张截图（`a9_tiletl`）；
- Odon：最后一张截图之后它的加载状态为已完成。
  - 它现在记的是查询开始前的时刻，而查询是按计划时刻安排的。
  - 要改为同时记下查询的开始、结束时刻，和最后一张截图的实际拍摄时刻对照：查询开始不早于实际拍摄，才算旁证。

主判据和旁证都满足才算最终；主判据不满足，记为"超过窗口"；两者不一致的，单独列出。

**"超过窗口"和"没响应"的统一算法**（所有比较项都用：停手稳定、程序内完成、响应 95% 线、超过 50 ms 的次数；20 通道和 3 通道都用）
- 这类值叫"截断值"：只知道它比观察窗口长，不知道具体多少。排序时排在所有确定值之后。
- 中位数：按上面的顺序取中间位置。
  - 偶数个时取中间两个，两个都确定，就取平均；
  - 其中有一个是截断值，中位数就记为截断值。
- 95% 线：按同样的顺序取位置，落在截断值上就记为截断值。
- 比较两边：
  - 两边都是确定值：
    - 时间类（停手稳定、程序内完成、响应 95% 线）按数值比，差在一帧以内算持平；
    - 次数类（超过 50 ms 的次数，"没响应"的注入也算一次）按数值比，不给容差，多一次就是多。
  - 一边是截断值、另一边不是：截断值一方慢；
  - 两边都是截断值：无法判定。
- "缺失"（测量失败）不是截断值：缺失的配对两边都不用，只影响有效配对的数目。

**配对按轮次对齐**
- Rust 第 n 轮只和 Odon（或旧版本）第 n 轮配对。
- 一边缺失，这一对就缺失，两边都不用；不把剩下的轮次错位对上。汇总工具现在会错位，要改。
- 中位数取有效配对的两边各自的值，"超过窗口"按最慢算。
- 每个结论都写明用了几对有效配对。

**每种手势逐一核对**
- 通道数：在测量的手势时段里，3、20、69 通道分别占多数（看每帧记录的通道数），而不是看整轮。
- 每种手势的注入数和有响应的注入数都要报告。
- 没观察到画面变化的注入，记为"没响应"：
  - 算作比任何响应时间都慢，计入 95% 线和"超过 50 ms"的次数；
  - 三方同样处理。汇总工具现在会把它略去，要改。
- Odon：每种手势期间都有画面变化，而不只是整轮变化超过 50 次。

**报告精度**
- 50 ms 时的画面差异，同时列出所用截图实际在停手后多少毫秒。
- 首次可见变化注明是"采样横带的第一次变化"。

## 4. 及格线（需要用户确认，见 §6）

**20 通道，每种手势、冷热分开，判"不比 Odon 差"，两项都要满足：**
1. **停手稳定**：Rust 的中位数不比 Odon 晚超过一帧（16.7 ms），"超过窗口"按最慢算。逐轮胜负同时列出。
2. **手势中响应**：同一手势各轮合起来，Rust 的 95% 线不比 Odon 高超过一帧；每轮超过 50 ms 的次数，中位数不比 Odon 多。

只差在一帧以内的，记为"持平"，算通过，并在报告里标出。

**无法判定**：同一手势、同一冷热条件下，出现下面任一情况，记为"无法判定"，不算通过也不算失败，单独报告原因：
- 有效配对少于 4 对（共 5 对）；
- 任何一项比较两边都是截断值（§2 的统一算法）。

**3 通道，每种手势和旧版本比**（3 对中有效配对少于 2 对就记为"无法判定"），两项都要满足：
1. 截图稳定中位数和程序内目标层完整中位数，都不比旧版本慢超过一帧。另列出相对变化（例如 3 ms 变 12 ms 也会列出来）。
2. 手势中响应的 95% 线不比旧版本高超过一帧；超过 50 ms 的次数，各轮合计不比旧版本多。

**停手 50 ms 内看不出切换**：目标线，单独报告 50 ms 时的最差小块差异，不作为及格条件。

**69 通道**：只报告，不设及格线。

**已知可能的差距**
- 热读连续放大：截图稳定 83 ms，Odon 50 ms（§48.4）。
- 冷读受机械盘速度限制（§46.3）。

仍存在的，按 §0 报告差距和原因。
