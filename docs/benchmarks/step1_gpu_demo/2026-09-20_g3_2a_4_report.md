**范围：** 本轮唯一的生产改动是 `Step1GpuBinding` 里 jump / quiet 与既有 33 ms motion timer 的配合。33 ms 间隔、`ExploreController`、scheduler、provider、raw cache、GPU layer、shader、Step0、Tissue Preview、shared camera、Overlay/Fusion、Intensity、coarse/fine 预算与 coarse 原子发布一律未动。G3.2a.3 的 throttle 修复原样保留。G3.2b/c/d 与 G4 未启动。

## 1. 修复前：同一落点被规划三次

轨迹 A（真实 Qt 事件循环，公开入口）：连续拖动三步让 motion timer 处于运行中 → 在 timer 到期前经 `mount.jump_to_point()` 空降 → 之后 450 ms 只等待，不再有任何输入。

| | 修复前 | 修复后 |
| --- | ---: | ---: |
| 该落点（epoch `7`）被规划次数 | **`3`** | **`1`** |
| 规划的 epoch 轨迹 | `[4, 7, 7, 7]` | `[4, 7]` |
| 该落点产生的 scheduler 请求 | `7` | `4` |
| 落点后 motion timer 仍在运行 | 是 | **否** |

三次分别是：空降自己、遗留的 motion timer 到期、controller 的 `gesture_quiet`。每一次重复都会取消刚发出的 generation 并把同一批请求重新挂一遍。

## 2. 修复后 motion timer、jump 与 quiet 的准确关系

- **`NAVIGATOR_JUMP`**：先 `self._motion_timer.stop()`，再立即 `update_viewport(snapshot)`，然后返回。不等 33 ms，遗留 timer 不会再对同一位置触发第二次规划。
- **运动事件（PAN/ZOOM）**：完全保持 G3.2a.3 的 THROTTLE 语义——只在 timer **未运行**时立即消费并启动它；已在运行的 timer 绝不重启。**没有改回 debounce。**
- **`gesture_quiet`**：仍然记录最新 snapshot，然后 `_flush_motion()`；`_flush_motion()` 只在"最新 snapshot 与上一次已规划的不是同一个"时才规划。

### 为什么只靠 timer 状态不够（本轮新增的唯一一个值）

`isActive()` 在两种需要相反答案的情形下都为真：**有**一个更新的相机位置正在等 throttle 窗口关闭（必须规划），以及**没有**任何新事件、上一次事件已被立即消费（不该再规划一次）。timer 自己分辨不了这两者。

因此保存了一个**不可变、局部、只读比较用**的轻量值：`self._consumed_viewport = (source, snapshot.epoch)`。`epoch` 是 controller **已有**的字段，它在每个相机事件上自增，而 `_on_settle` 发出的 quiet snapshot 带的是**最后一个事件的 epoch**、不新增——所以比较它恰好就是"自上次规划以来有没有发生过新事情"。它只在 `update_viewport()` 里写一次、在 `_flush_motion()` 里读一次比较，没有演变成状态机、队列、registry、token 系统或第二套相机权威。

进入 Step1、不拖动不缩放不点 patch、静等 2 秒：目标 level `1`（该缩放下正确）、可见 `9` 块、**`9/9` 全部上屏**、`fine_budget_refused` 为空、`last_error` 为空、静置期间 `0` 次请求与 `0` 次读取。

**合成台架没有复现"首次进入整幅模糊"。** 它**没有**停在任何阶段：请求发出、结果到达、descriptor 与 GPU 提交都完成了。真机与台架的差别是金字塔深度（真机 4 级）与冷读成本（最粗层 `74.65 ms`、level 0 `22.36 ms`），以及台架**没有 corrected product**，因此校正归约这一段完全没有被执行过。**本轮不据此扩大生产修改**（根因不是 jump/quiet 重复规划）。

## 6. 仍未解决 / 需要追加授权的最小建议

1. **首次进入与"停下后仍不清晰"**（真机现象，台架未复现）。建议在真机上用 `scripts/benchmark_step1_gpu_interaction.py` 的 `D_first_entry_idle` 字段复测，它会直接给出停在"请求 / 到达 / descriptor / 上屏"哪一段。**只需数据，不需要代码授权。**
2. **校正归约成本**：需要带 corrected product 的数据集才能测。**属 G3.2b，不在本轮。**
3. **"为什么不能立即出现最终精图"**：确认的主要等待来源仍是"一个通道的完整 coarse 事务落地后才开始规划它的 fine"。最小方案——**coarse 原子发布保持不变**，但在 coarse 事务进行期间就为该通道排入当前视口的 fine 请求，仍按 G2.1 的 `200` 优先级排在 coarse 之后，于是 coarse 一落地 fine 已在路上。影响：I/O 公平性不变（优先级顺序不变）、首幅显示不变（仍是完整 coarse 一次出现，中央扩散不会复发）、显存增加至多一个视口的 fine（已在 48 MiB 单通道预算内）。回滚：撤销该一处规划时机即可。**本轮不实现，需用户另行授权。**
4. **远距离连续空降在真机上的 I/O 让位**（G3.2a.3 登记的 advisory）：已开始的读取无法取消，第二落点要等 I/O worker 让位；生产宽度 8 worker 下实测第二次慢约 `64 ms`。**涉及共享 scheduler 配置，需授权。**
