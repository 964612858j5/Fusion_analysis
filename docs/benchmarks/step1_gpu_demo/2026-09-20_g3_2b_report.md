# Step1 G3.2b：首次冷准备时间 + cuCIM 来源重绑卡顿

**日期：** 2026-09-20 · **分支：** `v15-interactive-channel-workspace` · **起止 HEAD：** `9d78d1c`（未提交）

**结论摘要：**

- **轨迹 A（首次冷准备）**：测到一处可在授权范围内消除的串行——一个通道的当前视口 fine 只在它的**完整 coarse 事务落地之后**才被请求。已按授权方向 3 实施最小修复；五次重复的中位数由 `123.22 ms` 降到 `110.31 ms`，串行的 fine 阶段由 `63.90 ms` 降到 `0.03 ms`，并且新通道不再经历"先糊后清"两段式出现。
- **轨迹 B（cuCIM 来源重绑）**：**触发停止条件 #1，未实施任何修复。** 主导的 GUI 冻结是 `TileScheduler.shutdown()` 在 GUI 线程上 join 正在执行的读取。实测 `sync_source()` 在 GUI 线程上耗时 `205.98 ms`，其中 `teardown + scheduler join` 占 `116.98 ms`，事件循环最长 `227.3 ms` 无法运行；这个时间与"当时在途读取的时长"成正比。消除它需要让旧 scheduler 后台退休或新增 worker/退休队列，属明确禁止项，已按要求停止并在下文提交最小方案，等待用户裁定。

## 1. 轨迹 B：cuCIM 来源重绑（停止并申请追加授权）

### 实测分段（真实公开入口 `mount.sync_source()`，读取被压到 150 ms 以制造在途工作）

| 阶段 | 毫秒 |
| --- | ---: |
| `source_moved()` 身份检查（含 handoff 读取） | **`0.18`** |
| `host.teardown()` → `controller.teardown()` → `scheduler.shutdown()` **join** | **`116.98`** |
| 新 stack 建立（provider/scheduler/controller/view） | `33.42` |
| `sync_source()` 在 GUI 线程上的总耗时 | **`205.98`** |
| **GUI 事件循环最长无响应间隔** | **`227.3`** |
| 新来源目标视口清晰 | `650.3`（自开始计时） |

来源身份确实改变（`handoff=rev-1` → `handoff=rev-cucim-1`），`any_old_source_pixel_published = false`——**旧来源像素一帧都没有进入新画面**。

### 卡在哪里

`ExploreStack.teardown()` 的文档就写明它"performs, in order, `scheduler.shutdown()` (which joins the worker threads)"。`TileScheduler.shutdown()` 的契约是"drain in-flight work"：**已经开始的读取一定会跑完**。于是 GUI 线程停在那里等，等多久完全取决于当时在途的读取有多慢。本台架把读取压到 150 ms 就得到 117 ms 的 join；演示数据集冷读一块 `22–75 ms`、8 个 I/O worker 同时在途，真机上再叠加 cuCIM 校正计算，就是用户报告的"长时间卡顿、Block01 无响应"。

### 为什么现有接口解决不了

- `source_moved()` 只要 `0.18 ms`，**不是**瓶颈——原先"GUI 线程打开校正产物元数据很慢"的假设被否定（在本台架条件下）。
- 新 stack 建立 `33.42 ms`，也不是主导。
- 唯一的主导项是同步 join。要让它不阻塞 GUI，只能让旧 scheduler 在后台退休（新增退休队列/worker），或改 `viewer/scheduler.py` 让 `shutdown()` 异步——两者都在禁止清单上（停止条件 #1、#2、#3、#5）。

### 最小方案（**需要用户追加授权，本轮未实现**）

1. **让旧 stack 在后台退休。** `Step1ViewerBinding.open()` 在来源移动时不再同步 `host.teardown()`，而是把旧 stack 交给一个只做一件事的后台退休调用；新 stack 立刻建立，GUI 不等。
   - 需要改的函数：`ui/step1_viewer_binding.py::open()`、`ui/step1_viewer_host.py::teardown()`（增加一个"不阻塞"的形态）。
   - 用户可见变化：切换 cuCIM 来源后窗口不再假死，新画面更早出现；旧数据的 I/O 会在后台多跑一会儿。
   - 风险：两个 scheduler 短时间并存，I/O 与内存峰值上升；必须保证旧 stack 的结果一个都不上屏（现有 source/generation fence 已经做到，本轮实测 `any_old_source_pixel_published = false`）。
   - 回滚：退回同步 teardown 一行即可。
2. **或者**改 `viewer/scheduler.py` 让 `shutdown()` 支持非阻塞形态——**更不建议**，它是四个页面共用的共享基础设施。

两条都超出本块白名单，按停止条件不予实现。

### 未测到的部分（诚实缺口）

合成台架**没有 corrected product**，因此 **corrected coarse 的读取/归约（cuCIM/tophat reduction）一次都没有执行过**，它的耗时本轮**完全没有测量**。要测它需要一个带 corrected Zarr 的合成项目；这属于本块之外的准备工作，未擅自进行。上面的结论只覆盖"来源重绑的骨架耗时"，不覆盖"校正归约本身有多慢"。

## 2. 轨迹 A：首次冷准备（已实施最小修复）

### 修复前的分段（受控读取延迟 40 ms，目标层 level 0，粗层 level 1）

`fine_requested_before_coarse_landed`：**五次全部 `false`**——当前视口的 fine 在完整 coarse 落地之前**一次都没有被请求**。

### 修复

在 `Step1GpuBinding` 内调整**已有请求的时机**，不新增任何东西：

1. `_plan_fine_for_channel()` 原本在"该通道还没有已发布的 coarse"时直接返回。现在只要该通道**有 coarse 事务在途**（`channel in self._coarse`）就照常规划它的当前视口 fine——于是 fine 与 coarse 并行加载。fine 仍按 G2.1 的规则以 `PRIORITY_FINE_DEFERRED` 入队，排在 coarse 之后，不会饿死 coarse。
2. `_publish_current()` 增加一条：**从未画过**的通道，如果它的当前视口 fine 还在途，就继续保持旧画面，不把它放进 descriptor。已经在屏的通道永远不受此限制（G3.2a 的逐块清晰化原样保留）。

于是新通道的出现从"完整 coarse → 一次出现（糊）→ 逐块变清晰"变成"旧画面 → 完整 coarse 与当前视口 fine 都就绪 → 一次以目标清晰度出现"。partial coarse 和 partial fine 都永远不会上屏。

### 五次重复（同数据、同视口、同通道）

| 指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| `fine` 在 coarse 落地前就被请求 | `false` ×5 | **`true` ×5** |
| 各次 channel-sharp (ms) | `123.63 / 122.56 / 123.22 / 113.92 / 170.95` | `151.02 / 74.69 / 110.31 / 74.34 / 150.74` |
| **中位数 channel-sharp** | **`123.22`** | **`110.31`** |
| 中位数 coarse 阶段 | `59.18` | `110.15` |
| **中位数 coarse 之后的 fine 阶段** | **`63.90`** | **`0.03`** |

中位数下降 `12.91 ms`（`-10.5 %`），退出门 A.3 的"中位数必须下降"成立。

**诚实说明：** coarse 阶段本身从 `59.18` 涨到 `110.15 ms`，因为 fine 现在与 coarse 争用同一批 I/O worker。净收益因此只有约 10 %，比"fine 阶段归零"看起来的幅度小得多。真正的改变是**视觉**上的：以前 59 ms 看到一个糊的通道、123 ms 才清晰；现在 110 ms 之前保持旧画面、之后直接是清晰的。本台架读取远快于演示数据集，绝对毫秒是下界。

| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 首次访问，冷 | `54.61` | 9 | 11 | 4 | 5 | `5.8` |
| 第二个 patch，冷 | `35.52` | 5 | 12 | 4 | 4 | `6.2` |
| 返回，热 | **`5.75`** | **0** | 4 | **0** | 1 | `7.0` |

热返回仍是 G3.2a.5 的原子恢复：零读盘、零上传、一次 submit。

### 来源未变时进入（未受影响）

`sync_source()` 返回 `False`、耗时 `0.1 ms`、不重建 stack/layer/binding、`0` 读取、`0` 上传、fine 一块不丢、最长 GUI 间隔 `5.2 ms`。**方向 1 无需修复：现有实现已经正确。**

## 3. 原始假设中被否定的

1. **"GUI 线程在 `source_moved()` 里打开校正产物元数据很慢"** —— 否定：`0.18 ms`。
2. **"新 stack 建立是主要开销"** —— 否定：`33.42 ms`，不到总数的六分之一。
3. **"同一来源进入 Step1 会重复重绑"** —— 否定：已经正确短路，`0.1 ms`、零副作用。
4. **"patch 往返会重新读盘或重算"** —— 否定（G3.2a.5 已测，本轮复测）：`0` 读取、`0` 上传。
5. **"首次冷准备的主要成本在 GPU 上传或绘制"** —— 否定：最长 GUI 间隔 `5.8–7.0 ms`，成本在 I/O 等待。

## 4. 为什么没有新增架构

本轮只改了两处**时机**判断（何时请求已有的 RawKey、何时把一个通道放进 descriptor），复用既有 `TileScheduler`、RawKey、generation、raw cache 与 GPU texture cache。没有新增 scheduler、线程池、缓存、预取框架、waiting epoch、latest pending spec、callback coalescer 或状态机；512 MiB 与 48 MiB 预算未动；G2.1 的 coarse 公平规则未动。唯一新增的状态是一个 `set`（上一帧画了哪些通道），只用于回答"这个通道是不是第一次出现"。

## 7b. G3.2b.1 复核收口：首次通道在 fine 失败/超预算时不得泄出 coarse

**复核指出的 blocker 成立。** 首次显示的放行条件原来写成 `channel not in self._fine`，即把"没有 fine 计划在途"当作"fine 已经完整"。这在两种正常产品情况下不成立：

- 当前目标层超过单通道 fine 预算 → 根本不会建立计划；
- 某个 fine 瓦片读取失败 → 计划被移除。

两种情况下"完整 fine"都没有准备好，而之后一次普通刷新就会把该通道的 coarse 放出去，违反已批准的"首次通道只有当前视口完整 fine 准备好后才能一次清晰出现；无法完成时 fail closed"。

**修正。** 放行条件改成真实的数据条件，新增只读方法 `_viewport_fine_ready(channel)`：完整 coarse 已就绪，**且**当前视口的全部目标层 RawKey 都已经存在于 `_published_fine[channel]`。不再从"计划是否在途"推断。没有新增状态、缓存、重试器或生命周期机制——`_viewport_fine_ready()` 只读既有的 `_latest_snapshot`、`_visible_keys()` 和 `_published_fine`。

**新增两条公开路径门：**

| 门 | 断言 |
| --- | --- |
| `test_a_first_channel_over_the_fine_budget_stays_off_the_screen` | A 已在屏；视口扩大到超出单通道 fine 预算；勾选 B：B 的完整 coarse 到手、`fine_budget_refused` 记录 B、`last_error` 说明、**没有**半请求；画面仍只有 A；再刷新三次仍然只有 A |
| `test_a_first_channel_whose_fine_tile_fails_stays_off_the_screen` | B 的完整 coarse 到手，视口 fine 一块成功、一块读取失败；**实证 partial fine 确实驻留**（`fine_tiles["B"] == 1`、`"B" in fine_channels`）而画面**仍然只有 A**；`last_error` 记录该失败；再刷新三次仍然只有 A |

**变异：** 把条件改回 `channel in self._fine` → 两条门同时转红。按 md5 精确还原。

## 7c. G3.2b.2：首次点击 patch 仍在后台启动旧 patch 加载器（已授权、已修复）

用户真机反馈："每个 patch 第一次打开到 viewer 的时间比空降到新区域准备图像的时间长很多"。

### 只读核实的结论

`ui/main_window.py::_select_preview_patch(idx)` 在调用 `mount.show_patch(...)`（相机锚点，与 Tissue 空降同一个 `host.jump_to`）之后，还会走三个分支，其中只有一个没有 whole-slide 守卫：

| 分支 | 条件 | 是否已有 `_step1_whole_slide_active()` 守卫 |
| --- | --- | --- |
| ① | 已缓存 → `_ensure_channels_cached()` + `_refresh_patch_preview()` | **两个函数各自开头都已守卫** |
| ② | 已有 loader 在跑 | 只改状态文字 |
| ③ | **首次访问** → `_start_loader_for(idx)` | **没有守卫** |

`_start_loader_for` 的三个调用点里只有这一个是裸的：`_preload_all_patches`（由 `_preload_debounce` 触发）在**启动处**已守卫，`_ensure_channels_cached` 在**函数开头**已守卫。`PreviewLoaderThread`（`workers/cellpose_worker.py:64`）以 `downsample=1` 读取该 patch ROI 的**全部所需通道**，与 GPU viewer 的瓦片读取抢同一批 I/O。

这解释了全部三个现象：首次 patch 慢（多一条全 ROI 多通道读取在后台抢 I/O）、第二次快（进入分支 ①，两个函数都已守卫）、Tissue 空降一直快（根本不经过这个函数）。

### 修复前后的实测

用真实 `MainWindow` 台架，把 `main_window.PreviewLoaderThread` 换成计数替身，在 GPU viewer 接管期间点击一个从未访问过的 patch：

| | 修复前 | 修复后 |
| --- | ---: | ---: |
| 首次点击 patch 构建的 `PreviewLoaderThread` | **1** | **0** |
| 同一次点击的相机锚点 | `jump_to(0, 0, 256, 256)` | 同左，未变 |
| Tissue 空降构建的 `PreviewLoaderThread` | 0 | 0 |
| 回到旧渲染器后首次点击构建的 loader | 1 | **1**（行为不变） |

### 修复

`ui/main_window.py` 一处分支，`else:` → `elif not self._step1_whole_slide_active():`，与旁边三处用的是同一个既有守卫。没有新增函数、状态、线程或缓存；`viewer/**`、scheduler、provider、GPU layer、Step0 及其他模块一律未碰。

### 门与变异

新增 `test_a_first_patch_click_starts_no_loader_behind_the_slide_viewer`：GPU viewer 接管时首次点击 patch **不得构建任何 `PreviewLoaderThread`**，但相机锚点照常；Tissue 空降同样不构建；**回到旧渲染器后首次点击仍然构建**（rollback 行为不变）。

变异 **M23**（把守卫去掉）→ 该门转红，`test_the_hidden_patch_path_stops_reading_while_the_slide_is_shown` 仍绿（它覆盖的是另外两条分支）。按 md5 精确还原。

## 8. 测量限制

- GUI 心跳是 GUI 线程上的 5 ms QTimer，最大间隔就是"事件循环跑不动"的真实时长；**它不是显示器 input-to-photon 延迟**。
- 合成金字塔的读取远快于演示数据集：绝对毫秒是**下界**，分段形状才是结论。真实读取成本另行只读实测（最粗层 `74.65 ms`、level 0 `22.36 ms`、二次读 `~1 ms`）。
- 台架**无 corrected product**，corrected 归约成本完全未测。
- 五次重复的离散度不小（`74–151 ms`），因此用中位数比较，并如实列出每一次。
